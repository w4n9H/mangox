Personal Agent Team 一个人装不下两个领域，不是因为它不够聪明，是因为台账只有一份。助理的整条闭环都压在「一本台账 + 一场会话 + 一套配置」上：把「保证 CI 是绿的」和「每月发票对账」塞进同一个助理，两件事会互相污染账本 —— 完成状态是混的，注入段是互相挤的，一轮的注意力是分裂的。所以拆成两级：main 有独立触发面（人 / 飞书 / cron），负责对一个目标长期负责、在外说话、找人拍板；worker 没有触发面，只能被派活，拿自己的台账、自己的会话、自己的模型，干一件事然后交活。派活不新造一套调度 —— 复用「到点叫醒」那条已经跑熟的路径：delegate 工具就是「给别人的 follow_up」，同样落一张定时表、同样由每分钟那一跳扫到期、同样先认领再落定。权限只有一条根：外发唯一出口只属于 main —— worker 不挂 feishu_attach、不发系统通知、不弹审批卡；它要说给人听的话只能写进回执，由 main 决定说不说。层级硬限 1 级，worker 的工具面里没有 delegate，`agent_delegations` 里也不存在 worker → worker 的边。

00结论先行VERDICT

为什么必须是「多个助理」而不是「一个助理更努力」。助理这个形态的价值在长程：它替一个要跑几周的目标持续在线，靠的是台账记住进度、注入段重建上下文、收件箱攒下待拍板的东西。这三样都是单数的 —— 一本台账、一份注入段、一个目标。所以当一个人有两个都要长期盯的目标时，问题的本质不是"忙不过来"，是账会记混。三条硬约束把结构推了出来：

约束为什么逼出了什么设计
① 一本台账只承载一个目标台账是「完成状态」的验收面，程序要能算出来。两个目标写进同一本，「哪些做完了」立刻变成人肉判断；注入段也会互相挤掉（预算就那么多字）每个助理各自一本台账、各自一场会话、各自一份模型配置 —— 拆分不是省上下文，是让验收面保持可算
② 一轮可能跑十分钟派活如果同步等，main 会被卡住整整一轮；它还占着一个并发名额，人在飞书里问一句也进不来。而真正需要等的活（查发票、跑对账）恰恰是最慢的派活只排时间不做事：delegate 立刻返回"已排上，最早 X 开始"，worker 到点自己起跑，结论落库，main 下一轮读回执
③ 对外说话只能有一个出口"两个助理同时往同一个飞书单聊发消息"会让人分不清谁在说话；更糟的是审批卡 —— worker 在后台跑，卡弹给谁？权限从这一条长出来：worker 结构性地没有 feishu_attach / 通知 / 审批；它要说的话只能进回执

⇒ 所以这不是"一个能派活的模型"，而是一个有队长、有分工、有交活回执的最小组织结构。它小到只有两级、只允许向下派、只允许队长对外说话 —— 这三条限制不是能力不足，是让"谁负责"永远有唯一答案。

一句话

把助理分成 main（有触发面，对一个目标长期负责，唯一能对外说话的那个）与 worker（无触发面，只能被派活，各带自己的台账与会话）。派活 = 给别人的一次定时唤醒：delegate(worker, goal, acceptance, after_minutes, due_by?, context?) 落 agent_delegations，由每分钟那一跳扫到期起跑 —— 复用 follow_up 已经跑熟的「先认领、被挡则顺延、任务没了就作废」。有活的 worker 不许再派（硬拒，不排队）；交活由 App 自动回叫 main（不占 main 的自主调度配额）；层级硬限 1 级；worker 的话只能进回执，想说给人听必须经 main。界面上：定时任务页只负责建与改，新增的助理团队页纯展示（队伍 · 状态 · 关系）。

01需求与边界REQUIREMENT

它替人做什么：让一个长期目标的执行面从"一个助理一次干一件"变成"一个队长把并行的几条活分出去"。真实的形状是：一个目标下面有几条互不依赖的活 —— 保证 CI 是绿的这条线里，既要盯冒烟、又要核对发版产物、还要月底出一份对账；它们共享同一个目标，但彼此不需要看对方的中间过程。

谁受益：①多领域的看守 —— 同一个「项目健康」目标下，构建、依赖、数据三条线各一个人；②慢活的并流 —— 对账要跑十分钟，main 不必等它，可以同时把「看看昨天那个 flaky 测试」派出去；③要独立模型的任务 —— 便宜活给便宜模型、关键活给强模型，配置本来就是分开的。

明确不做（含理由）：

  • 不做三级以上。worker 的工具面里没有 delegate，库里也不存在 worker→worker 的边。多一级就多一层"这笔钱算谁的"和"它为什么不回我"，而收益（再细分）在这台机器上看不出来。
  • 不做 worker 之间的横向对话。只有 main→worker 单向派活，worker 只能回执。两个模型互相聊是最容易变成"聊了很久什么也没定"的形状，而且没有终点判据。
  • 不做同一 worker 并行，也不排队。有活就硬拒并在回执里说清它手上是什么、什么时候完。排队会让时间语义全乱 —— 你说的是「1 分钟后启动」，实际是「等它手上那条完了再说」。
  • 不做同步等待式的派活。没有「等 worker 回来再继续」这一档。真需要等的活，等于不该拆出去。
  • worker 不对外发消息、不发通知、不弹审批卡。它只写台账与回执。这条是权限模型的根，详见 §05。
  • 团队页纯展示，不可编辑。归属在助理编辑器里改（一行下拉）。画板上不做拖拽 —— 拖拽一旦存在，就要处理"拖到一半 main 被停用"，而那些状态在图上是不可见的。
  • 不做跨组连线、不做自由画布。布局是固定的五条泳道（按状态分列），卡片在列内按时间排 —— 人不摆位置，否则每次进来都要重新认人。拖拽也不做：拖拽一旦存在，就要处理"拖到一半 main 被停用"，而那个状态在图上是不可见的。
  • 不做"模型改职责"，连提案也不做。职责与职责说明只有人能写：模型对它们是纯只读（list_workers 读，注入段读那 40 字）。原因不是"以后再说"，是这一层还没跑通 —— 职责写得准不准，要真派过几十次活才知道；在没有任何真实交活数据之前让模型去改它，改出来的一定是"什么都能干"。等 P3 跑过一段时间、手里有"派了但派错"的真实案例，再谈提案。

派活的生命周期

queued已排上：due_at 到了才起跑。有活时第二次派活直接被拒，不进这个态排队中
↓
running起跑了（那一场同时只跑一轮）。被闸挡（main 在跑 / 并发满 / 预算 / worker 停用）⇒ 原地顺延，仍是 queued，不消耗重试次数上限之外的东西在跑

五列 = 五档状态，卡片会换列。每条卡上必须写归属（第二行前半段），左边那一条竖线是 main 的身份记号 —— 泳道把"队伍"拆散了，这两个是唯一还能认出"谁是谁的人"的地方。左侧队伍列表点一下过滤整片泳道。

列内排序不是按名字，是按"最该被我看见的"：在跑按开始时刻（跑太久了的浮上来）、已排上按 due_at、等回执按交活时刻（等最久的在上）、空闲按 lastRunAt（最久没动的在上 —— "三天没派过活"能被人看见，靠的就是这一条）、停用按停用时刻。

列宽固定 150px、容器横向滚：压窄列会让"名字 + 归属"两行都折行，而两行都折行的卡片读起来是一团。也不做换列动画 —— 卡片在列间移动的几百毫秒里，点谁都是错的位置。

⚠️ 泳道把"队伍"拆散了，这是它唯一的真代价。补法只有两个，两个都要有：每张卡的第二行前半段写归属；左侧那一列队伍可以点，点一下整片泳道只剩它的人。少任何一个，二十张卡就是认不出谁是谁的。

身份与颜色分两个通道。身份走不占颜色的三样：卡头/卡片左侧那条 3px 竖条 + 名字 500 + 一个 main 徽标；颜色只表示状态（蓝在跑 / 黄等回执 / 灰空闲）。给身份再配一个色的话，同一张卡上就有两套色编码：main 用了蓝，那"正在跑的 main"就分不出是身份还是状态；而二十个 worker 各带身份色，整页变成一堵彩墙。

点一张卡 → 右侧检查器：职责与职责说明、role、模型、最近五次执行（时刻 + 结果）、台账「完成状态」摘要，底部两个动作「打开编辑器」「打开会话」。泳道只承担"谁在哪个状态"，细节不挤进来。

disabled_by_parentINTEGER01 = 它是因为 main 停用才跟着停的。这个标记存在的原因：main 重新启用时只恢复这些，不碰"你自己手动停掉的那个 worker"（否则启一次 main 会把你单独关的也拉起来）

派活表 agent_delegations

列语义
id主键。同时是回执关联键（与 agent_sent 用 id 当 ref 同一族做法）
from_task / to_task谁派的 / 派给谁。两条都是 task_id，索引在 to_task（"它手上有没有活"是最高频查询）
goal / acceptance / context工单三件。goal 与 acceptance 必填（见 §02 的失败教训），context 可空。落库前各自截断：800 / 400 / 1200 字
due_at什么时候起跑 = 派活那一刻 + after_minutes。App 侧算，不信子进程的钟
due_by最晚什么时候要（可空）。它与 due_at 的关系在工具入参处校验：due_at >= due_by 直接拒
statusqueued / running / done / failed / cancelled。五态，与 §03 那张流程图一一对应
attempts顺延次数（被闸挡住时 +1）。不用于判死：worker 忙四十分钟是正常的
note为什么被挡 / 为什么失败（闸的原话、桥的原话）。必须有：否则人只看到"没跑"，不知道为什么
summary交活时 worker 写的一句话结论（≤400 字）。main 的回执读它，不读全文
reported_atmain 成功收尾之后才标。标在"注入时"会让那一轮崩掉时回执永久丢失；标在"收尾时"是唯一诚实的位置（同 settleSent 的哲学）
created_at / started_at / finished_at三个时刻。画板的"在跑 N 分钟"= started_at 到现在的分钟数

为什么不并进 agent_followups

两者共享"到点叫醒"这一段（扫到期、认领、顺延、删任务连带清），看起来该合一张表 —— 但它们的语义与字段差得太远：follow_up 只有 why 与四态，派活有工单三件、两条时间线、回执消费与五种终态。合成一张会得到十几个 nullable 列，而每一列都要在两种语义下各解释一遍。

方案好处代价取舍
并表（action + payload）一次扫描、一套连带清理两套语义挤在一张表；dueFollowUps 这类查询全要加 action 过滤；统计"今天约了几条回看"变成按 action 数未采用
独立表每张表的列都只说一件事；状态机能各自演进tick 里两次到期查询、删任务时两处连带（要写成一处函数，不许复制）采用

⚠️ 顺带记一条 P15 的教训：那次"两表合一"是对的，因为两边是同一个语义（都是知识条目）；这次不是。判据是字段与状态机是否同构，不是"是不是都按时间触发"。

delegate 工具契约

参数约束
worker名字（字符串）。域层要求 worker 名字唯一 —— 列表按名字选人，重名就等于"A 和 B 都叫这个"
goal必填，≤800 字。"这一次要干什么"，不含长期职责（那是它自己的 prompt）
acceptance必填，≤400 字。"怎么算干完"。它会进 worker 台账的「完成状态」
after_minutes必填，0 ~ 10080（7 天）闭区间。0 = 下一跳就起（≤60 秒），不是"立刻"
due_in_minutes可选。最晚什么时候要。必须 > after_minutes，否则拒（"2 小时后开始、1 小时后要"是张没人能完成的单）
context可选，≤1200 字。相关文件路径、上次结论、约束。⚠️ 不传对话快照：fork 会把 main 整段历史塞进去，worker 分不清哪条目标是自己 的

拒绝的理由必须说得出（每条都带"下一步怎么办"）：

1
名字不存在
回一句可用名单（名字 + 状态），让下一轮能直接改对。只报"不存在"等于让它再猜一次
2
它是个 main
"它自己是一支队伍的队长，不能当 worker"。main 永远是 main，不提供"降级成 worker"这个动作
3
它被停用了
说清是被停用而不是"不存在"，并指出要么先启用、要么换人
4
它手上有活
硬拒，不排队。要说清手上那条是什么、什么时候开始 / 已经跑了多久 —— 否则模型下一轮还会再派一次
5
时间越界或自相矛盾
越界（<0 / >10080）与 due_in_minutes ≤ after_minutes 都要拒，且报实际值
6
本轮到量了
一轮最多派 2 条。理由与 follow_up"一轮一条"同族：一轮冒出五张单子 = 它在乱派，不是在分工
7
今天到量了 / 已关掉
配额三态生效。0 时连工具都不挂（给一个每次都被挡的工具，模型会反复试）

实现取舍：七条判据只在 App 侧，扩展只负责收

扩展（mangox-delegate.ts）只做三件事：读 MANGOX_DELEGATE_SPOOL 这个 env、校验形状（worker / goal / acceptance 非空、after_minutes 是整数）、往 spool 里追一行 JSONL。上面那七条一条都不在扩展里。

为什么：名单、谁手上有活、今天派了几条，全是库里的瞬时事实。把它们塞进子进程的 env 会随进程复用而冻结（本仓踩过同族：改了配置、进程被复用 ⇒ 助手照旧按旧名单拒，而设置页是勾着的）。两处各判一遍之后，"拒了"与"拒对了"就变成两件会分叉的事 —— 而派活拒错一次，代价是一整轮。

代价明写：模型是「下一轮」才知道被拒的（时间线里落那几行「派活没成: …」，P3 的回执注入再把它念给 main）。换来的是"判据只有一个产生者"，以及拒绝理由里能带上当场算出来的名单与起跑时刻。

两段注入

【你的队伍】（排进 main 的注入段，常驻） —— 每个 worker 一行，上限 12 个：

【你的队伍】
- 财务对账 · 查发票与月度报表 · 空闲
- 周报整理 · 汇总本周合并的 PR · 已排上 09:31
- 发版检查 · 核对 tag 与产物一致性 · 在跑 3 分钟
（每行中间那段 = 职责原文，一字不截 —— 所以要求 40 字以内写清。判据与边界在「职责说明」里，用 list_workers 取）

为什么只有职责 + 状态：这一段是每轮都付的固定成本。12 个 worker × 每行约 55 字 ≈ 700 字，已经是一份 SOP 的量级；把职责说明也塞进来会变成 3000 字，等于每轮先读一篇文档再干活。12 这个上限就是从这里倒推出来的。

【派活回执】（只在有没汇报过的终态时出现，排在输出契约之前）：

【派活回执】（最近 5 条，没汇报过的）
- 09:42 财务对账 交活了：11 月发票 3 处差异，见它台账「完成状态」
- 10:05 周报整理 没干成：模型超时，未重派
（汇报过就标掉；worker 的结论细节去吃 read_worker_ledger）

list_workers：名单常驻、简历按需

分工只有一句：注入段回答"有谁"，这个工具回答"他到底能干什么"。常驻那 40 字是为了让人名在上下文里一直存在（模型得先知道有这个人，才谈得上选谁）；完整职责是决策时才需要的信息，所以按需取。

list_workers()

- 财务对账 | 空闲 | 上次 11-22 交活
  职责：查发票与月度报表
  说明：差异要列单号与金额，别只给总数；月度那份带一页对比。

  职责：汇总本周合并的 PR
  （没写说明 —— 只有一句职责）

  （没写职责 —— 你只能从名字判断）

五条规则，每条都在挡一种具体的失败：

规则为什么
无参不设 status 过滤、不设 limit、不做 query 检索。12 个的规模下，参数只会让模型在"要不要带参数"上犹豫一次；而全量也就 3000 字出头，比一次犹豫便宜
必带状态不带的话它会派给一个正忙的，白挨一次拒（拒了才知道 "它手上有活"）—— 一次拒就是一整轮
缺口要分级说出来两档，不能合并：没有职责写「你只能从名字判断」（这是异常态，worker 本该必填）；有职责、没说明写「只有一句职责」。留白会让模型把这当成"这个人没什么特别的"，而说出来它才知道这是信息缺口，可以改派或先问人
只有 main 能调worker 的工具面里没有它 —— 它连 delegate 都没有，知道"还有谁"只会让它想找人而做不到
只读，两个字段都只能人改不提供 set_description / set_detail。一旦模型能改自己的职责，它会在被派活失败之后把自己写成"什么都能干"—— 那是最坏的一种自我宣传

容量账：12 个 ×（名字 + 状态 + 40 字职责 + 240 字说明）≈ 3000~3500 字，一次调用摊在需要它的那一轮上，不是每轮。这也是它和【你的队伍】的分界：那段是每轮 700 字，这一段是"选人那一次"的 3000 字。

否掉的三个备选：① 把职责说明塞进注入段（12 × 240 = 2880 字每轮付费，违反 context rot 那条）；② 语义检索 find_worker(query)（12 个的规模用不上，还会引入一层不该有的依赖）；③ 按名字取单人简历 worker_profile(name)（模型得先猜谁可能合适，猜错就是两次往返 —— 而一次拿全比猜两次省）。

read_worker_ledger

入参只有 worker 名字。返回：目标一行摘要 + 「完成状态」原文 + 最近 20 行，总长截到 1500 字。

为什么不返回整篇：一份台账五节写满是几千字，一个 main 巡五个 worker 就是两万字 —— 那是把"独立台账"的好处（各占各的窗口）又塞回一个窗口里。要看全篇就再要一次（分节取）。

连带与回收

动作它自己名下的 worker未完成的派活
删 main删行 + 删台账文件只停用，不删（enabled=0），parent_id 保留成悬挂值 ⇒ 它在画板上落进「未归属」区cancelled，note 写"main 已删除"
停 mainenabled=0全部停用，并打上 disabled_by_parent=1保持 queued：到期时 worker 停着 ⇒ 顺延；due_by 过了才 cancelled
启 mainenabled=1只启用 disabled_by_parent=1 的那些，并清掉标记顺延的自然会在下一跳起跑

停 workerenabled=0—保持 queued 顺延（可逆的操作不该毁掉一条活）

⚠️ 这五行的"连带"逻辑只许写一处（一个 applyTeamCascade），否则"改一条漏一条"是必然的 —— 与 deleteScheduled 那批连带同族。

⚠️ 派活单不随任务一起删，这一条与 agent_followups 正好相反（那张表是按 pending 扫的，留着会让 tick 每分钟扫到一条指向不存在任务的约定）。cancelled 的行必须留着：P3 那句"这个活没了"就是靠它送到 main 面前的 —— 删掉行，回执永远到不了。代价明写：行会随时间堆，保留期属于产品决定，将来按 agent_findings 同款处理。

05风险与边界RISK & BOUNDARY

根不变量

外发的唯一出口只属于 main。worker 的工具面里没有 feishu_attach、不发系统通知、不弹审批卡。这不是"配置上关掉"，是结构上不挂 —— 与"工具级弹卡在助理线上恒关"（P19）同一族做法。
它带来一个必须接受的代价：worker 发现"这事要人拍板"时，它自己叫不动人，只能写进回执等人。我们认这个代价，因为反过来（worker 直接找人）会让人收到一条他无法归属的消息，而审批的粒度就散了。

风险为什么会发生怎么防
main 与 worker 抢 computer helperhelper 是一个进程一个 scope；两边 scope 不同 ⇒ 互相 stop() 重启。现象是"微信点了一半助手消失了"到期时若 main 那场还在 runningTurns 里 ⇒ 顺延。代价：伪实时退化成"main 跑完立刻起"
委派把成本放大外部实测：多代理约是聊天的 15× token（Anthropic）。而派活一旦顺手，一个 main 一天能派二十次三道：每轮 2 条 / 每天 delegate_per_day（出厂 5）/ 同时 3 个 worker。worker 的预算各算各的（不合并拦截，合并会让人莫名看到"跳过"）
派错人职责写得含糊 + 名单只有那一句名单永远带状态；拒绝时返回名单；职责是必填（worker 建不出来就没有）；占位文案写"它负责什么，一句话"
回执被反复念回执如果在注入段常驻，模型每轮都会跟人汇报同一件事reported_at：main 那一轮成功收尾才标；失败则不标（丢了回执比重复更坏）
递归扇出worker 也想派活工具面不给 + 库里没有 worker→worker 的边（from_task 必须是 main，域层校验）
台账把窗口撑爆只读工具返回整篇1500 字截断 + 分节取；"最近 20 行"是刻意的粗粒度
孤立 workermain 被删后 parent_id 悬空停用 + 画板单列「未归属」；它不能被执行，但台账与历史都在（删了就不可恢复，而台账是历史）

门禁计划

新算例 T-TEAM（约 20 条，落在 scripts/smoke/cases/CaseAgentTeam.swift）。每条都要求能造出反例 —— 只写正例的断言在这套代码里等于没写。

算例判的是反例怎么造
①分级role 与触发面一致；worker 没有 cron 入口；parent_id 单值让 role 由 assistantId != nil 派生 ⇒ 应红
②名单12 个上限、职责原文照搬不截断、状态五档正确、不出现职责说明（实际落成 2 条 check ㉒㉓）把职责说明也塞进名单 ⇒ 字数超预算应红（夹具按 12×40 字满格搭，半格时泄漏也照样绿）
③拒绝七条拒绝理由各自说得出（实际落成 4 条 check ⑫⑬⑭⑮：派给谁 / 名单 / 有活 / 额度与顺序）去掉"它有活"那道判 ⇒ 第二次派活会成功，应红（实测 1 红：⑭）
④到期due_at 到点起跑；被闸挡则顺延且 attempts+1；worker 删了 cancelled把顺延改成"直接置 failed" ⇒ 应红
⑤回执消费注入一次 → 标 reported_at → 第二次不再出现；失败收尾不标（3 条 check ㉔㉕㉖：真回合 / 空回合 / 一次 5 条）去掉 produced 那道判 ⇒ 空回合也标，应红（实测 1 红：㉕）
⑥回叫worker 交活 ⇒ main 有一条 0 分钟唤醒；不占 main 的 follow_up 配额回叫写成记 followUpsPerDay 扣减 ⇒ 应红
⑦连带删 main 只停 worker；停/启联动只恢复 disabled_by_parent把"启 main ⇒ 全启"写成无过滤 ⇒ 手动停的那个被拉起，应红
⑧工具面worker 没有 delegate / feishu_attach；有 follow_up / note_proposal给 worker 挂上 feishu_attach ⇒ 应红
⑨只读两件list_workers：12 个上限、缺口分两级提示、必带状态；read_worker_ledger：1500 字截断、未归属拒、含「完成状态」（4 条 check ㉗㉘㉙㉚）去掉那两句提示 ⇒ 应红（它会静默把"没写"读成"没什么特别"）；超长时从尾部硬截 ⇒ 尾巴一行不剩，应红
⑩顺延main 在跑 ⇒ 派活不顺延起跑（runningTurns 判据）去掉那条判 ⇒ 两个回合同时要 helper，应红（或至少 started_at 重叠）

已知缺口（写在这里，别当成忘了）

  • 团队页零门禁。它只读状态画行；"画得对不对"归眼睛。唯一能自动验的是"@State 快照与库一致"，但那属于视图层探针，不在本版。
  • worker 手动试跑不进 cron、不进飞书，但它会不会写 agent_delegations 还没定 —— 我倾向不写（它不是一次派活，没有 from_task），代价是画板上看不出"这个 worker 刚才被人手动跑过一次"。
  • 亮色板。团队页与列表行都要动颜色，而 run.sh 的算例只认 enum Dark ⇒ 动手前先建亮色算例，否则是"看不出来但版式崩了"。
  • 词表增量约 24 条（团队页标题 / 五档状态 / 拒绝理由 / 编辑器的归属、职责与职责说明各一段，含两段占位提示）。状态词有一半在注入面也要用，注意注入面的那份恒中文、不进词表（与 SentKind.tag 同族）。
  • 扩展那半边没有门禁。mangox-delegate.ts 的三个工具只有真 pi 进程跑得起来，而本仓没有 TS 解析门（node --check 只认 CommonJS，对 ESM 静默退 0）。所以真正会进上下文的字节全部由 Swift 渲染好再交给扩展打印（§04「两段注入」与两个只读工具那一节）—— 扩展只剩"读 env / 校验形状 / 追加一行 / 打印一段现成文本"。这条边界是刻意的：判据要留在能被断言的地方。
  • 不做的两件：worker 之间横向对话；"自动重派失败的活"。前者没有终点判据，后者会在同一个坑里烧三次。

06执行计划PLAN

六个阶段，每个阶段自己就能跑绿、自己就能提交。顺序不是"从简单的开始"，而是每一步都为下一步提供可验证的地基：数据层先落地（否则后面每改一次列都要动测试），派活闭环在没有一行界面的情况下先跑通（那时它已经能干活了，只是要你在飞书上跟它说话），注入排在工具之后（先教它用一个不存在的工具是反的），界面排最后（它是唯一只能靠眼睛验的部分，等后端全绿再动，返工最少）。

阶段做什么结束判据能单独发版
P1 数据与域无行为变化 助理行六列（role / parent_id / description / description_detail / delegate_per_day / disabled_by_parent）+ 派活表 agent_delegations + 域层四条不变量（main 无 parent · worker 必须有 parent · 深度恒 1 · 名字唯一）+ 一处 applyTeamCascade T-TEAM ①（分级与唯一）、⑦ 的域层半边 技术上可以，但建议与 P2 一起发 —— 只增列没有价值
P2 派活闭环没有界面也能用 delegate 工具（七条校验）+ 到期起跑 + 顺延口径（不按次数判死）+ done / failed 与 summary + 交活回叫（0 分钟唤醒，不占配额）+ worker 工具面（去掉 delegate / feishu_attach） T-TEAM ③④⑥⑧⑩ 可以，而且这一阶段结束就该用真飞书跑一次：让 main 自己派人，看回执能不能按时回来
P3 注入模型才真知道有队伍 【你的队伍】+【派活回执】两段 + reported_at 的消费时机（成功收尾才标）+ list_workers（名单 40 字 / 简历全量）+ read_worker_ledger（1500 字截断） T-TEAM ②⑤⑨ 可以 —— 但必须排在 P2 之后
P4 列表页建与改 职责与职责说明两个输入框（在名字下面） + 归属下拉 + worker 独立一行 + 3px 身份竖条 + 五档状态小字。职责对 worker 必填：没填存不下去 视图层无门 ⇒ 亮/暗各看一次 + 本地化四道 可以（这之前 worker 只能通过域层接口建）
P5 团队页泳道 · 纯展示 统计行 + 队伍筛选 + 五条泳道（列内按时间排）+ 检查器 + 「未归属」区 亮色算例先建，然后亮/暗各看一次 + e2e_probe + 词表 可以
P6 打磨可以永远不做 worker 手动试跑 · main 会话里的派活事件卡（点进 worker 会话） · 检查器的最近五次执行 —— 可以

三条不许跨阶段提前做的事

  • 表只增列，不删不改名。P1 之后任何一次"改个列名更顺"都会让旧版 App 打开新库直接崩（已发版 tag 的用户还在跑）—— 这条是 P11 立的硬规，不因为这次是新表就放宽。
  • 界面不许先于工具。先把卡片画出来、再补 delegate，中间那几天你会看到"点得动但点了没反应"，而那种状态最容易被当成 bug 报回来，也最容易被顺手用假数据糊过去。
  • 亮色算例必须先于 P5 的任何颜色改动。run.sh 的视觉算例只认 enum Dark（P16 的既有缺口）⇒ 泳道那套颜色在亮色下崩了，门是绿的。
最可能被真跑推翻的四个数

这些数字现在是估的，P2 结束那次真实往返之后要重估一次：worker 上限 12（注入预算倒推出来的）、每轮 2 条派活、同时 3 个 worker、每天 5 条。四个都在一张表里改，改完要重算【你的队伍】那段的字数预算 —— 那段是每轮都付的固定成本。

每个阶段的完成定义

不是"代码写完"，是三件事同时成立：双门禁绿（冒烟 + xcodebuild，各零 warning）+ 至少一条新判据造过反例并真的变红 + 一次 commit（不打 tag，tag 单独决定）。反例这一条最容易被跳过，而跳过它等于这个阶段的判据全是"看起来对"。
