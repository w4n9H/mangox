一句话

门 1 的答案把门 3 一起答了，而且答案比问题更大 —— 「目录固定成 ~/.mangox/note 或 <项目>/.mangox/note」不只是给写入设了个边界，它让"归属"变成了位置的同义词：写进全局根就是全局、写进项目根就是项目，不需要第二个维度。
连带效果是三处减法：① 作用域维度不再需要设计（位置即归属）· ② 逐库写入策略 writePolicy 不必存在（目录固定 ⇒ 不会有"别人的仓库"这个问题 —— 那正是原方案里必须逐库声明的原因）· ③ 提案不能落盘、要落表（落盘会被自己的扫描器当成笔记扫进 prompt，见 §03）。

①
门 1 是这一版最大的简化。原方案要在 KnowledgeBase 上加一个三档 writePolicy 并逐库声明 —— 现在整条不需要了。收窄的代价是丢掉「挂任意目录做只读资料索引」这个能力（§01 末尾明写）；换来的是这一区只剩一种实体、一个归属规则、一条写入路径。
②
提案必须落 DB，不能落 _proposals/ 目录 —— 这条有可验证的理由。扫描契约只挡 hasPrefix(".") 与 excludedNames = {node_modules, .build, DerivedData}（Models/KnowledgeBase.swift:65-78, 97）；_proposals 不在其中（下划线不是点、也不在排除名单里）⇒ 提案文件会被当成笔记扫进索引、每轮进 prompt。改成一张 note_proposals 表，目录里因此只会有笔记。
③
门 2 的答案把 P11.3 那条判断钉死了。「知识库区里面就是笔记的概念，不存在知识条目」⇒ 这一区彻底脱离 KnowledgeItem 的语义（没有 status、没有 layer、没有 trigger/counterfactual）⇒ P11.3 的守卫 8 / 11 / 14 与四条护栏一条都不在这条路径上。叠上门 4（dream 自带阀门）⇒ P11.3 继续冻结，且这次不是"先不做"，是"没有交集"。
④
补上第四个面：消费。前三个形态都在回答"笔记怎么产生"（写 / 更新 / 审），没有一个回答"产生之后怎么被用"。而现状是：这一区进 prompt 的只有文件名清单（indexBlock），KnowledgeBaseDoc 连 mtime 都没有，段头还写着「以下是挂载的知识库」，那是"外部只读资料"的语境。⇒ 本版把索引块升级成「文件名 · 摘要 · 陈旧」（⚠️ 来源标记刻意不进索引块 —— 见 §03 那条注与 §05 风险表），并写死一条红线：每轮算出来的东西只能进易变段。

01需求说明REQUIREMENT

要做什么 —— 让「用得越久、它越懂你」在 MangoX 里有可观测的产出：知识三区要承接得住「从对话里长出来的东西」，且任何一条知识都能被问出「它多久没变了」「它凭什么是对的」。

现在为什么不行 —— 三区各有一个不同的洞，都不是「界面不好看」：

  • 常驻区（本版不动） —— persona pack 三份 md，是全库唯一在真正起作用的载体。它能工作恰恰因为它是手写的（有人对它负责）。这条现状本身就是证据，不是巧合。
  • 自定义区 —— 闸门建好了，上游是空的。 KnowledgeStatus 有 pending / active 两态，左列也把待审候选排在最前（KnowledgeView.swift:425）。但实测 pending 0 条、source='session' 0 条 —— 审核面在对空气说话。
  • 知识库区 —— 只读，且看不见时间。 Models/KnowledgeBase.swift:6-8 明写「App 只读不写，只做两件事 —— 让 agent 知道它存在（索引）、告诉它去哪读（路径）」。而扫描产物 KnowledgeBaseDoc 只有 relativePath + depth 两项 —— 连 mtime 都不扫。⇒ 从对话里长出来的东西没有落地处；腐烂在结构上不可观测。

谁受益、在哪个场景受益 —— 三个具体场景，都不是假想的：

  • 跨会话的连续性：今天 PROJECTS.md（10-12 已按 §04 A 移除）里写着 Mangopi CLI 在 P2，而它已经走到 P3。要让 agent 不拿旧状态当当下事实，这份笔记得有人更新 —— 而更新它的只能是「记得去更新它的人」。
  • 刚纠正过的事不必再纠正：同一类错误在一个会话里被纠正两次、下个会话又被犯一次 —— 而那个纠正没留下任何东西（session 来源条目 0 条）。
  • 写下的东西真的会被用：那条唯一的条目是「任何回复以『老哥』称呼我」，落在 kind=fact / layer=ondemand / enabled=0 —— 它一次都没进过 prompt。用户写了、以为生效了、实际静默失效。

明确不做什么（放末尾，各带理由）：

  • 不做任意目录挂载 —— 这是本版收窄的代价，必须明写：原知识库区能挂任意目录做只读索引（成套资料有自己的生命周期：可能是 git 仓库、可能别人在维护）。收窄成两个固定根之后，这个能力没了。理由：留着它，"笔记"与"只读资料索引"就是两种语义挤在一区里，正是 P11 一路上在删的东西（sensitivity 档、shared 字段都这么删的）。若将来要"外部资料索引"，那是另一个功能，不是这一区。（⚠️ 且扫描器不跟符号链接，KnowledgeBase.swift:99-101 ⇒ 软链进不来，"复制进去"是唯一绕法。）
  • 不做条目 ↔ 笔记的桥（不给"把知识条目导出成笔记"之类的动作）—— 桥 = 漂移源：同一份内容在 DB 行与文件里各有一份之后，"哪份是当前值"这个问题会立刻长出来。两个载体各自完整，比中间架一座桥便宜。
  • 不做 GUI 笔记编辑器 —— 外部十家里的笔记类载体全部是明文 md + 外部编辑器（Claude Code 用 /memory 打开系统编辑器，Obsidian 实践者直接用文件）。App 内只提供"新建 / 改标题 / 改正文"的最小面，深度编辑交给系统默认编辑器（给一个「在 Finder 中显示 / 用默认应用打开」的入口）。
  • 不做向量检索 / 语义召回，也不做每轮自动检索 —— 判据是规模：总预算 Tune.knowledgeTotalCharLimit = 64000，笔记均 800 字 ⇒ 约 80 篇以内的全文都装得下，而实测条目 1 条、笔记 1 份。给不存在的量级建索引，是在解决"我没有的问题"。但"检索"这件事本身要留一个口子：agent 主动调 note_search 工具（第一版 = 朴素子串，产物进会话消息流、不碰注入块）。它是"笔记多到装不下"时唯一正确的形态 —— 而那时它已经在了。
  • 不自动删任何知识 —— 外部十家零先例（§02 A）。
  • 不让 LLM 判「这条知识对不对」 —— 判据不是"不可靠"，是不可变红：模型打出的"正确性"没有任何造反例能让它红，因此它不是判据、只是装饰。
  • dream 第一版不做编辑器 —— Claude Dreams 官方明说它做不了逐行手术（§02 A）。
  • 探针层只留接口（门 5）—— 现在没有笔记可挂，"笔记 → 探针 id"的映射会是空表。只允许 frontmatter 里出现 probe:，本版不解析。

  • 为什么提案落 DB 表而不是落 _proposals/ 目录 —— 这条不是审美，是会出错的：扫描契约只挡 hasPrefix(".") 与 excludedNames 那三个名字（Models/KnowledgeBase.swift:65-78, 97），_proposals 两头都不占 ⇒ 提案文件会被扫成笔记、进索引、每轮吃 prompt 预算，而且它是"未采纳的东西"，出现在注入里正是本版最不能接受的事。落表还顺带解决了另外两件：提案是带状态的对象（待审 / 已采纳 / 已丢弃），文件系统不表达状态；以及"输入永不被改写"这条不变量，靠 base_hash 比对比靠"文件没被写"更容易断言。
  • 为什么用 mtime 当陈旧度权威，不读 PROJECTS.md 里那个手写的 updated: —— 那份文件本版按 §04 A 移除，但它本身就给出了答案：它自造了 updated: 协议，结果是 20 天没人改它，而且没有任何代码读它。判据是"不可忘改"：系统维护的时间戳没人能忘，手写的字段只要忘记一次就永久说谎。⚠️ 代价明写在 §05：git checkout / 复制 / 备份还原都会改 mtime，那个方向上它反而会说"刚更新过"。
  • 为什么项目笔记根放在 <项目>/.mangox/note/ 而不是 DB 里加一列 —— 位置即归属会让"这个根在哪"变成可推导的，而 DB 列是第二真源。同族先例：凡是能由位置/结构推出的，不要再存一份。
  • 为什么不把 writePolicy「留着以后用」 —— 留着它就得给每个根写一遍"能不能写"，而两个根都是我们的目录，答案永远相同。这正是 P11 删 sensitivity 时用的判据：两个东西永远同值 ⇒ 其中一个没有信息。
  • 为什么不让 agent 直接写笔记（只有 dream 提案 + 人采纳） —— ① 外部十家里"自动写入"的三家官方都不推荐把它当可靠载体（提炼 ④）。② 单写者带来一个免费的礼物：并发写坏文件（提炼 ⑥）在这条路径上根本不会发生 —— 写盘只发生在"人点采纳"的那一刻。③ 判据：本版没有"agent 必须立刻写盘"的场景；等真出现了再加，别预付。
  • 为什么不做"每轮按用户输入自动检索" —— 它技术上最直接（query 现成，没有"agent 不知道怎么搜"的循环依赖），但产物只能进易变段（§03 红线），且命中率完全取决于用户这次怎么措辞。而"agent 主动调 note_search"这条路产物进会话消息流，连注入块都不碰 —— 同一件事，后者的架构代价是零。这两条的关系不是备选，是配套：工具路需要 agent 知道"有什么可搜"，而那正好由索引块的摘要行提供。
  • 为什么不做条目 ↔ 笔记的桥 —— 桥两侧的"当前值"会立刻分叉，而分叉的消解机制（谁的赢？）又要新设计一套。两个载体各自完整、互不引用，比架桥便宜。

一句话

每日 dream 的两道裁剪（36 小时窗口、单会话 4 万字）都是为"一天里好几场、每场各分一点"设计的；要对一场做完整整理，两道都得松。做法是给会话行多一个入口：点开 → 看清楚 → 确认 → 一次性整场提炼，预算 256k，跑完不动每日那轮的时间窗口。

①
36 小时只是候选范围，真正的瓶颈是那 4 万字。本机最大的一场（A2F7F694…，794 事件 / 40 回合 / 11.3 万字正文）在 4 万预算下只留得住最后 19 个回合 —— 而丢掉的那 21 个回合恰好是"这场到底要解决什么"的开头。⇒ 现行行为对"完整"是反的：它保住尾巴、砍掉来由。所以这件事不能靠"把窗口调大"解决。
②
入口必须长在那一场上，而且点开才能算。菜单在由此侧问下面加一条由此 Dream；菜单标题不带规模 —— Menu 的 content 惰性没有保证，即便惰性也是在每次悬停展开时算，等于把"扫该会话全部 events 的聚合"绑到悬停上。⇒ 规模在点击之后查，一条聚合就够（json_extract(payload,'$.content.text._0') + LENGTH），不解码事件流（真实那场 794 个事件里有 616 个解码完就被丢）。
③
定向那一次绝不推进 lastRunAt。它不是"这个定时任务的一次运行"。而 dreamDigestSince 取的是 min(now-36h, lastRunAt)：36 小时是地板、改不动，被吃掉的恰好是"上次真跑在很久以前"那段补跑窗口 ⇒ 那几天里没被定向跑过的会话永久掉出窗口，且零红灯。同一个块里 logSessionId 照写 —— 这条也是判据"那一行确实执行过"的唯一证据。
④
预算要松两只手。sessionDigest 有单会话与整段两个上限；定向只改前者的话，整段那个 4 万仍在，一场照样被裁。定向把两个都传成 dreamTargetedMaxChars，并在段头把口径换成「整场 · 指定会话」—— 否则段头写着"窗口 36 小时"就是假话，而模型是拿它判时间跨度的。
⑤
段名一个字都不能改。摘录段仍叫【最近会话摘录】：dreamPrompt 的指令正文指着它（"见本消息末尾的【最近会话摘录】段"），改名的效果是告诉模型"没有摘录段"，它会直接收场 —— 而且不报错。定向的范围说明走追加（dreamTargetedScopeNote），落库的常量一个字不动。
⑥
顺带补上"重复"这块。定向让重复提炼从罕见变常态（人点一次 + 当晚定时那轮又吃一遍）⇒ 收口时按根 + 目标路径 + 标题在待审队列里去重，并把跳过数单列进日志。不单列的话，"这条我上次提过"看起来就像"模型这次没提"。
