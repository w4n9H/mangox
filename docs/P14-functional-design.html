00结论先行VERDICT

一句话

这四条都做得成，但其中三条的价值不在「加功能」，而在把已有的东西接到 macOS 的惯例位上 —— 设置窗改独立、⌘, 绑上、菜单栏补齐。第四条（工作区自动刷新）不能照抄现有刷新路径：FileNode.id 是随机 UUID，重扫必然折叠用户展开的树，那是在身上添疤，不是收口。

①
外壳三条干净得出乎预料：showSettingsPanel 的 9 处引用里，7 处是「切会话时关掉主区面板」的机械删除；删完设置窗就能和主区任意面板并存（§03）
②

③

01需求说明REQUIREMENT

要做什么 —— 把「一个 macOS 用户会下意识去碰的外壳」补齐，并让工作区在 agent 改完文件后自己跟上。

现在为什么不行 —— 三条现状，都是「用户按肌肉记忆去够，够空」：

  • 设置按 ⌘, 没反应 —— 它不是 macOS 的 Settings 场景，而是画在 ContentView 里的整页覆盖（ContentView.swift:144），只能从侧栏按钮点进去。
  • 菜单栏只有系统默认项 —— mangoxApp.swift 全文没有 .commands（全文 34 行，实测），所以「关于 / 帮助 / 检查更新」这类位置是空的。
  • 工作区要手点刷新、图片看不了 —— agent 改完文件，文件树停在上一次扫描的结果上（WorkspaceView.swift:80 那颗刷新按钮是唯一入口）；点开一张 png 得到的是一句占位文案（WorkspaceView.swift:685）。

谁受益、在哪个场景受益 —— 就是本人和任何 macOS 用户，受益点是「不用学它」：窗口能开两个、⌘, 打得开设置、菜单里找得到帮助。工作区那条受益在「agent 干完活不用我再去点一下」。

明确不做什么（放末尾，各带理由）：

  • 不做全局搜索 —— 这是加一个功能，不是收口；且要新起一个搜索面（会话标题 / 知识条目 / 文件内容三种目标还没定）。⌘F 先接工作区过滤框（见 §03 口径）。
  • 不接自动更新 —— 它硬依赖签名与托管 appcast，属交付面（另一条主线），本版不持有它的结论。
  • 不动 README「已知限制」里标了「有意」的那批 —— 「命中」列恒 —、工具标签小写、Codemode 不挂业务扩展、宽表表头跟滚、换行开关不落库、空态不画光标 —— 它们是设计决定，改掉才是退步。

控件去掉描边之后，我原先把 accentSoft 高亮底留着当状态表达 —— 真机上看到「选中档位」是一块粉底，成了这一行里唯一残留的色块，与参考图的「裸图标 + 文字」直接冲突。⇒ 底色也去掉，选中态只剩文字色（textTertiary → accent）；无底之后 clipShape(Capsule()) 成了 no-op，一并删掉（不留空壳）。

⚠️ 我错在哪：我把「状态要不要表达」当成了我该推理的事（结论：要 ⇒ 保留底色），可参考图里根本没有底色 —— 那是事实，不是待推理的题。像素量测能定「有没有边界、边界多深」，定不了「该不该有底色」，后者是风格判断，只能靠真机看。下次遇到「参考图已经给出答案」的项，照抄事实，不要拿推理去覆盖它。

第二次（同一天）：底色去掉之后文字仍是 accent 品牌红 —— 我又把「状态要靠颜色强调」当成了需要我在红与黑之间权衡的事，于是留了红。实测参考图控件行的颜色直方图：主色 #181818 / #E0E0E0 / #000000，R=G=B，零彩色。⇒ 换 textPrimary（近黑），深浅仍承载状态（默认 textTertiary / 激活 textPrimary）。

⚠️ 同一个坑，一天踩两次：两次都是「参考图已经给了答案，我却拿推理去覆盖」。⇒ 本批立一条判据：控件行的所有元素必须落在灰阶上（R=G=B）—— 出现彩色就是没对齐。参考图是这个风格，不是「我判断该不该用强调色」的问题。

定标与量测的两脚坑（都记在这儿）

图1 输入卡 x 21..1622 = 1602px，代码 Tune.composerMaxWidth = 848pt ⇒ 缩放比 1.889（不是 2）。自证：按此比例把图1 的卡片圆角量成 22px ⇒ 22 ÷ 1.889 = 11.6pt，与代码 radiusLg = 12 吻合。
⚠️ ① 图1 里 y=79 那条线是上方 projectPill 的底边，不是输入卡顶边 —— 拿它拟合圆角会得出 38pt 的假值。
⚠️ ② 水平剖面会把上/下描边误读成填充：「控件有浅灰 pill 底」这个结论就是这么错的；竖直剖面才看清囊内是纯白。判一个区域有没有底色，必须看穿过它的竖直剖面。

为什么这么做，为什么不是别的做法

  • 设置窗为什么不用 Settings 场景 —— SwiftUI 的 Settings 场景要求 store 提升到 App 层，而 ChatStore 现在是 ContentView 的 @StateObject；提升会动窗口模型，且 mangoxApp.swift 不进冒烟 ⇒ 那部分逻辑断言不到。走独立控制器则形态与 mini 台同款、可测。
  • 菜单命令怎么够到 store —— 用 focusedSceneValue / @FocusedValue 通道，而不是全局单例或通知。被否的那个：把 ChatStore 改成单例 —— 会改掉「每窗口一份 store」的现状，且 ContentView 的 @StateObject 语义跟着变，收益不抵风险。
  • 自动刷新为什么不用 FSEvents —— MangoX 自己就知道 agent 何时写文件（WorkspaceView.swift:338 已经在按 edit / write 工具算触达路径）。为「agent 改文件」这个已知事件去监听整个仓库，是多余能力，还要管递归监听与生命周期。
代价与临时妥协

① ⚠️ 设置窗用 @FocusedValue 拿 store ⇒ 多窗口（⌘N 开新窗）时，设置窗只跟随最近聚焦的那个窗口。消掉条件：哪天把 store 提升到 App 层。
② ⚠️ 视觉没有在真机上核对过 —— 本机无头浏览器起不来（GPU 进程崩溃），上面三张原型是排版草案：类名由 lint 守住、配色跟主题变量走，但间距与换行没被眼睛看过。
③ 三张原型的样式积木（.mocks / .mock / .win …）加在 docs/assets/design-doc.css。若本版被否，这批类名要跟文档一起撤掉 —— 否则就是留在样式源里的死代码。

05风险与边界RISK & BOUNDARY

风险现象结法
命令够不到 store无聚焦窗口（或窗口全关）时 @FocusedValue 为 nil ⇒ 命令点了没反应三个菜单项统一 .disabled(store == nil) —— 宁可置灰，不要留死项
设置窗持有旧 storeContentView 重建后，窗口仍挂上一份已失效的 store控制器记 hostingStore，show 时比对引用，换代就重挂 contentView
合并写错张冠李戴同名节点复用了错的 id ⇒ 展开态错位。实测下来真正的缺口不是「不同目录」（mergeLevel 每层只拿本层旧数组比，天然按目录分隔），而是同级同名但类型不同：旧的文件 A 可能把身份借给新的目录 A匹配键 = 同级 + 同名 + 同类型（isFolder 进判据）；冒烟加一条手搓旧树的反例（磁盘上造不出同名文件与同名目录并存）—— 把 isFolder 从判据里删掉，该条精准变红 2 例（已实测）
关窗后 flag 不同步红灯关窗但 showSettingsPanel 仍为 true ⇒ 侧栏高亮不灭订阅该窗口的 willCloseNotification 置 false（MiniWindowController:41 同款）
菜单项本地化冻结窗口标题走 L()，若不订阅 LanguageModel 会冻在首次取值控制器订阅 LanguageModel.shared.$current 重设标题（这正是「冻结取词」那条坑）

边界

  • 本版改什么：应用外壳（设置窗形态 / 菜单 / 快捷键）与工作区（刷新时机 / 图片预览）。
  • 本版不改什么：pi 协议与 spawn 参数一个字节不动；注入链路、审批桥、数据库 schema 不碰；README 标「有意」的那批不动。
  • 本版不往 README / CHANGELOG 写本版内容 —— 它们是发版面：README 的版本徽章、词表条数（614 → 623）、冒烟条数（909 → 951）与那两条已过时的「已知限制」（文件树不自动刷新 / 图片预览）都得跟着版本号一起改，不宜提前把未发布的行为写进 README。留给下一次走发版链路时一次改完。
  • 不持有谁的结论：交付面（签名 / 公证 / 自动更新）是另一条主线，本版只用到「LSApplicationCategoryType 与版权串」两个与它无关的 plist 字段。
