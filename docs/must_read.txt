must_read.txt —— MangoX 对齐文档的写法约定
================================================================================
写任何 P{N} 对齐文档之前先读这一份；写完按 §F 自检清单逐条打钩。
本文件只管「对齐文档」（P3 及以后的 P{N}-functional-design.*），不管 README / CHANGELOG
/ 代码注释 / daily log —— 那些各有各的写法。

生效范围：P13 起。P3~P12 的 .md 保留原样（历史），新文档一律 .html。


================================================================================
§A  为什么要有这份约定
================================================================================
md 是**线性**载体：被迫从头读到尾，判据、证据、方案、待办全混在同一条流里。
而对齐时真正要看的是「**哪些面定了 / 哪些没定 / 卡在哪**」—— 那是一张二维状态矩阵。

⇒ 判据：对齐文档的本质是 **状态矩阵 + 证据链**，不是叙事。
⇒ 载体必须是能**扫**的（色块 / 条形 / 折叠），而不是能**读**的。
⇒ 所以：结构固定（§B）、状态用颜色承载（§D）、证据必须可复查（§C）。


================================================================================
§B  骨架：六个必需块，编号与顺序固定
================================================================================
   00 结论先行      VERDICT        一屏看完"什么定了"
   01 需求说明      REQUIREMENT    为什么做这件事
   02 需求调研      RESEARCH       凭什么相信（证据链）
   03 路径与方案    APPROACH       怎么做，以及为什么不是别的做法
   04 待办与跟进    TODO           还没做的、怎么验、卡在哪
   05 风险与边界    RISK           会怎么坏，以及和谁的分界

- 六块都有内容才叫对齐文档；某块确实为空，就写"本版无"并给一句理由，**不许删标题**。
- 每块的**编号不许改**（脚本/人靠编号定位）。块内小节可用 h3 自由组织。
- 页面顶部固定给：状态（调研中 / 设计阶段 / 已开工 / 已完成）、前身、单一来源、日期。


================================================================================
§C  每块填什么
================================================================================
--------------------------------------------------------------------------------
00 结论先行  VERDICT
--------------------------------------------------------------------------------
必须回答
  · 一句话判定（结论本身，不是"本文讨论了…"）
  · 不超过三条 TL;DR：读完必须记住的事
  · 状态矩阵：每个"面"一行 —— [面] + [判定] + [依据强度]
     依据强度只有三档：强 = 实测 / 源码；中 = 官方文档；弱 = 推测

一票否决
  · 结论埋在正文里、要读完才知道
  · 出现"整体可行，细节待定"这类不含信息的句子

常见假通过
  · 把"待定"和"已定"混在同一张矩阵里不加区分 —— 待定的必须显式标 ⚠️


--------------------------------------------------------------------------------
01 需求说明  REQUIREMENT
--------------------------------------------------------------------------------
必须回答
  · 要做什么 —— 一句话，**不带方案**
  · 现在为什么不行 —— 没有它，现状是什么样、哪里痛
  · 谁受益、在哪个场景受益
  · 明确不做什么（含理由；放本块末尾）

一票否决
  · 只说"要 X"，说不出"现在为什么不行"

常见假通过
  · 把方案写进需求（"用 codemode 实现 X"）—— 需求不该预设实现路径
  · 把"老板提过"当理由 —— 要写清提它的**动机**


--------------------------------------------------------------------------------
02 需求调研  RESEARCH   ← 本约定里最重的一块
--------------------------------------------------------------------------------
必须回答
  · 上游 / 外部契约是什么（原文出处 + 关键原文片段）
  · 我们这边的现状（文件:行号）
  · 关键实测（**可复现命令** + 观测面 + 结果数字）
  · 每条结论的可信度分级（§C[00] 那三档）

一票否决
  · 任何一条结论没有出处 —— 要么给 `文件:行号`，要么给可复现命令

常见假通过（都踩过）
  · 拿"注释说会这样"当实测 —— **注释可能是错的**，本项目已有先例
      （P12 §七 那句"codemode 绕过审批桥"就是被源码交叉推翻的）
  · 拿"官方文档这么写"当生效 —— 要分开「文档说支持」和「我们这条路真跑通」
      （`--tools +codemode` 官方配方在我们 `-ne` 的前提下是空操作）
  · 判据只能变绿、不能变红 —— **判据必须能造反例**，否则它只是自证
  · 观测面选错导致"测了但测不出来"（如用 stderr 判工具是否注册，而 pi 对未知工具名不吭声）
  · 数字按记忆写 —— **一律现算**，脚本里用断言把数字钉住


--------------------------------------------------------------------------------
03 路径与方案  APPROACH
--------------------------------------------------------------------------------
必须回答
  · 目标形态 —— 矩阵 / 对照表（每档、每种情形分别落到什么）
  · 改动面 —— `文件:行号`，一行一处，写清"现状 → 改成什么"
  · 为什么这么做，**以及为什么不是另一种做法**（被否掉的那个要给判据）
  · 代价与妥协 —— 有临时妥协必须显式标出来（补丁是长在身上的疤）

一票否决
  · 只给"要改哪"，不给"为什么不是 B"

常见假通过
  · 方案里的判断没有指回 02 的某条证据（等于凭感觉选型）
  · 顺手发现的次生问题被吞掉 —— 要么写进 04，要么写"本版不动 + 理由"


--------------------------------------------------------------------------------
04 待办与跟进  TODO
--------------------------------------------------------------------------------
必须回答
  · 前置门 —— 不过就不做的门。每条给：判据 + 做法 + 状态
  · 验收项 —— 每条**可执行**、有期望值（可机检的写命令）
  · 状态只有三种：**未做 / 进行中 / 已实测**（外加一个：被谁阻塞）
  · 依赖与跟进人（有就写）

一票否决
  · 出现"待验证"却不写怎么验证
  · 前置门写着"未做"，正文却按"已具备"往下推理

常见假通过
  · 把"源码 / 注释看过了"当成"已实测" —— **读注释不算**
  · 验收项写成"功能正常""没问题"这种不可执行的句子
  · 把"未做"留空 —— 空白会被默认读成"已完成"


--------------------------------------------------------------------------------
05 风险与边界  RISK & BOUNDARY
--------------------------------------------------------------------------------
必须回答
  · 风险：现象 + 现状 + **结法**（不是"注意一下"）
  · 与其它版本 / 模块的边界：本版改什么、不改什么、**不持有谁的结论**
  · 上游暴露面：我们依赖了哪些上游默认值 / 未文档化行为

一票否决
  · 只列风险不给结法

常见假通过
  · 把风险写成"我们会小心"
  · 不写"上游一改默认值我们会怎么变形"（能力面静默漂移是这类项目最常见的事故）

§D  格式纪律（一票否决级）
================================================================================
1. 载体：`docs/P{N}-functional-design.html`（P13 起）。样式**只能**来自
   `docs/assets/design-doc.css`，由脚本同步：
       python3 scripts/docs/design_doc_css.py --apply    # 改完样式同步
       python3 scripts/docs/design_doc_css.py --check    # 交付前必须绿
   文档里**不许手写 CSS**；`@style:begin/end` 块内是生成的，手改会在下次同步被覆盖。
   为什么要内联而不是 `<link>`：预览面板只服务单个文件（同级路径返回 **403**），
   外链样式在面板里会**静默失效** ⇒ 单一来源由脚本保证，不由链接保证。
   **唯一例外**：承载「数据」的内联 style，例如条形图的宽度 `style="width:76.7%"` ——
   那是数据不是样式。除此以外，一个 `style=` 属性都不许有。

2. 状态用**颜色**承载，不用形容词：
       🟢 c-ok 已定 / 做完了    🔴 c-bad 定死了不行    🟡 c-warn 待实测 / 未做
       🔵 c-info 数字事实        🟣 c-acc 需要强调      ⚪ c-mute 待做（无风险）
   **禁用词**：应该 / 大概 / 基本 / 差不多 / 问题不大。

3. 折叠"**查得到就行**"的（契约清单、集成面清单、字段表）；
   展开"**要拍板**"的（结论 / 实测 / 方案 / 待办 / 风险）。

4. 实测结论必须带可复现命令；源码结论必须带 `文件:行号`。

5. **单一来源**：同一件事只写在一个地方，别处只留指针（"见 §X"）。

6. 数字一律现算。凡是从别处抄来的数字，交付前重数一遍。

7. 临时妥协必须标出来，并写清"什么条件下该被消掉"。

§E  命名与位置
================================================================================
  docs/P{N}-functional-design.html     对齐文档（P13 起 .html，P3~P12 为 .md）
  docs/assets/design-doc.css           唯一样式源
  docs/must_read.txt                   本文件
  scripts/docs/design_doc_css.py       样式同步 / 校验
  scripts/diag/*.py                    判据件（文档里"实测"一行的可复现入口）

§F  交付前自检清单
================================================================================
  [ ] 六个块都在，编号 00~05 顺序没乱；顶部有状态 / 前身 / 单一来源 / 日期
  [ ] 00 有 1 句判定 + ≤3 条 TL;DR + 状态矩阵；"待定"都显式标了
  [ ] 01 说得出现状为什么不行；没有预设实现路径；写了不做什么
  [ ] 02 每条结论都有出处；至少有 1 条**能变红的判据**；数字现算过
  [ ] 03 给了改动面 `文件:行号` + "为什么不是 B"；次生问题有去处
  [ ] 04 每条"未做"都写了怎么做；没有把"看过源码"当成实测
  [ ] 05 每个风险都有结法；写了上游暴露面；写了与其它版本的边界
  [ ] 全文没有 §D[2] 的禁用词
  [ ] 除承载数据的内联 style 外，没有别的 `style=` 属性；没有 `<link>` 外部样式
  [ ] python3 scripts/docs/design_doc_css.py --check 通过
  [ ] 实测件（`scripts/diag/*.py`）当前能跑通，且文档里引用的命令与之一致
