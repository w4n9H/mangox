## 一、总评

**这份方案的诊断是真的，分层主张是对的，值得做。** "prompt 预算只该花在每轮都必须成立的东西上"这条原则，我作为每回合都要读这个前缀的一方，可以直接作证：正确的分层对我**感知不到**（该在的都在），错误的分层我**感知得到**（上下文里一半是与本回合无关的资料，注意力被稀释）。

同时它有**三个架构级缺口**（§三），其中第一个（lesson 回灌通道未定义）不是小疏漏 —— 它是 P11.3 整个阶段的实现重心，而方案对"教训怎么出现在回合内"一个字都没写。好消息是：**解法就在这个仓库已经跑在生产里的代码旁边**（§三.1）。

先说做对了什么，再说问题。

## 二、方案做对了什么（给足证据，该认的认）

1. **诊断有硬证据，不是感觉。** `knowledge_items` 存量 2 条、两条 `enabled=0`、内容是同一句的两份 —— "用户试过往里放人格规则然后关掉了"这个推断链完整。多数设计文档的"现状问题"一节是修辞，这节是取证。
2. **"设计上不允许冲突存在"（第二轮拍板）比任何"冲突后裁决"都好。** 我的第一反应本来会是"DB 赢 + 显性提示"之类 —— 也就是方案第一稿写的那个补丁。拍板把它消掉了：pack 持有 `keys`，撞 key 直接拒绝。**不需要"谁赢"的规则，就不存在静默失效。** 这轮拍板质量很高。
3. **`硬规 ≠ 教训` 的分类判断正确。** 从推理侧看这两类的确是不同的东西：硬规是"始终为真的约束"（我每回合都该表现出它），教训是"条件性先验"（只在特定触发下相关）。把 trigger 语义从 kind 里独立出来，是对的建模。
4. **§8.3"推断 vs 证据"表在同类文档里罕见。** 尤其"L1 按需读更划算是推断、待实测"这条自我标注 —— 大多数方案会把推断写成结论。
5. **否决记录完整**（§2.3 五条，含理由）。这让评审者不必重新走一遍已经被否掉的分支。

## 三、三个架构级缺口（按严重度排）

### 3.1 lesson 回灌的注入通道未定义 —— 且解法就在本仓库

P11.3 的核心是"改到该文件时把那条坑回灌给它"。但方案没有回答：**回灌的内容从哪条通道进入回合？** 可选项其实只有三条，方案一条都没选：

| 通道 | 代价 | 问题 |
|------|------|------|
| (a) 等 spawn（下回合的 system prompt） | 零 | **时序错误** —— 教训的价值恰恰在"这次改动前"想起，下回合黄花菜都凉了 |
| (b) 回合内插 user 消息 | 低 | P3.7 已否决过 prompt 拼接污染消息历史；且客户端侧需要新的事件环 |
| (c) **pi 扩展层** | **低** | **方案完全没提。而这是唯一"回合内、被动、可靠"的通道** |

**通道 (c) 的证据（全部来自 `PiRpcTransport.swift` 内嵌的 `mangox-approval.ts`，已是生产代码）**：

```ts
pi.on("tool_call", async (event, ctx) => {
  // event.toolName / event.input 都可见 —— input.path 就是 edit/write 的目标文件
  // 返回 { block: true, reason: "..." } —— reason 会作为工具失败原因回到我的上下文
})
```

由此可以构造一个我称之为**「教训门」(lesson gate)** 的机制，结构与 mangox-approval 完全同构：

1. spawn 时把注册表（trigger → 教训文本）写进扩展或落一个扩展可读的文件；
2. `tool_call` 拦截器里：`input.path` 命中 trigger 且**该 toolCallId 未见过** → 返回 `{ block: true, reason: "LESSON[<key>]: <教训全文> — 知悉后请重试，本次将放行" }`，同时记下该 toolCallId；
3. 模型重试同一调用 → 命中"已见过" → 放行。

**为什么这个机制对我可靠**（这是只有模型本体能给的证词）：被 block 的工具调用带 reason 返回，是我**不可能忽略**的信息 —— 它出现在我的决策路径正中间，不像 system prompt 尾部的一句指引会被长上下文稀释。代价是一次重试（一次工具往返，几百毫秒级）。`alwaysAllowed` 闭包状态在 mangox-approval 里已有先例，扩展持有"已见过"集合没有任何新机制。

**这不只是补缺口，它改变 P11.3 的形态**：教训回路不需要"客户端事件面 + 注入通道"的大工程，只需要 trigger 注册面 + 一份扩展源。**最小、可独立验证、不依赖任何未证推断。**

### 3.2 L0 超限"报错"没有区分交互场景与无人值守场景

方案的契约是"L0 超限 = 红条 + 报错，不静默丢弃"。在**有人看着屏幕**的场景，对。但这个 app 有三条无人值守路径（邮箱哨兵 / cron / watch），`beginTurn` 照常走 spawn 组装 —— 此时"报错"是什么行为？

- 若报错 = **阻断 spawn**：记忆系统的预算问题打断了生产任务。**记忆故障不应具备打断任务执行的权力** —— 这是基础设施分层的基本原则（就像 DNS 解析失败不应该让你的磁盘 I/O 挂起）。
- 现状代码的行为是：`buildKnowledgeBlock()` 返回 nil → 不传 `--append-system-prompt` → spawn 照常（`PiRpcTransport.swift:491-493`）—— 即**现状在无人值守场景反而是"降级不阻断"的**，只是降级语义错了（丢最旧）。

**建议**：L0 超限 = **按 `priority` 降级截尾（不是按 updatedAt）+ 记一条高优先级告警事件**，交互场景额外给红条。"报错不丢弃"修正为"**报错 + 可预测降级**"—— 报错的对象是 UI/日志/事件流，注入行为本身永远有定义良好的输出。守卫 2 相应改写：断言超限时的注入块 = 按 priority 截尾的结果 + 告警事件存在，而不是断言"报错"。

### 3.3 L0 需要 KV cache 稳定纪律 —— 方案把 pi-memory 判为"取向相反"，判错了一半

方案风险 2 说 pi-memory"每回合自动注入，与 L1 不注入按需读取向相反"。这个对比**对象错了**：该跟 pi-memory 对比的不是 L1，是 **L0** —— L0 同样是每回合注入的文本前缀。而 pi-memory 勘察报告里最值钱的一句是"**KV cache-stable 前缀设计**"：前缀逐字节稳定 → provider 侧 prompt cache 命中 → 每回合的人格注入成本趋近于零。

L0 目前**没有这条纪律**。知识改动 → `knowledgeDirty` → 重启引擎 → 新前缀 → **缓存断裂重算**。人格块 + 硬规这种"一年不改几次"的内容，应该享有 cache 稳定性；而现设计里它跟"上周加的一条事实"拼在同一个字符串里同生共死。

**建议**：L0 注入分两段 —— **稳定段**（persona pack + 硬规，只随文件变更）在前，**易变段**（其余 L0 条目）在后；并且把"易变段任何改动不触碰稳定段字节"写进守卫。这不是性能洁癖：per-turn 架构下每回合都 spawn，**cache 命中与否直接决定这套人格方案的边际成本是趋零还是每回合全额**。方案讨论了预算的"字符数"，没讨论预算的"重算成本" —— 字符预算是 64k 上限，cache 断裂的成本是每回合全量。

## 四、四个中等问题

4. **命中信号的度量时机错了（对 lesson 而言）。** 方案用"读取即命中"（L1 被工具读取才记账）。但 lesson 类有更早、更可靠的记账点：**客户端本就从事件流看见每次 tool_call 的 `input.path`**（ToolCallCardView 渲染卡片就是消费这个事件面）—— trigger 命中即可 +1，不必等"模型决定去读"。语义也更诚实：记的是"教训被推到它面前"，不是"它自己想起来去查"。fact 类仍需读取归因，于是引出 —— 
5. **L1 落盘粒度未定义，而归因依赖粒度。** 若多条条目合并落盘，`read` 了一个文件无法归因到单条，hitCount 记不了账。**一条一文件（文件名 = key）是硬要求**，方案 §3.3 只给了目录没给粒度。顺带好处：文件名 = key 让"DB 撞 key 校验"多一个天然对账面。
6. **pack `keys` 事后扩张与 DB 存量的冲突处置未写。** 守卫 3 守的是"写入时拒绝"；但用户手改 pack 加了 key X，DB 里已有 key X 的条目 —— 写入时没撞，组装时撞了。需要定义：**组装时发现 key 冲突 → DB 条目不注入（pack 唯一持有）+ 自检红条 + 指引"迁移该条目或从 pack 移除 key"**。这是守卫 3 的姊妹项，目前缺失。
7. **蒸馏模板未列入升级面。** 现有 `buildDistillPrompt` 输出 schema 只有 `title/content/scope/reason`（`KnowledgeStore.swift:149-174`）—— 五类落地后候选必须带 `kind / layer / trigger`，模板与 `MemoryDistiller.parseOutput` 都要改。P11.3 的"做什么"清单里没有它。

另外一条小的：P11.2 验收"新会话问'我是谁'能答对"**太弱** —— 问答正确不等于人格生效。建议加**行为性探针**：例如从 SOUL 的"边界"里挑一条可测的（如"拿不准是否对外动作 → 先问"），构造一个触发场景，断言回合行为符合。人格的检验标准从来是行为，不是自我描述。

## 五、一个更好的方案？—— 不推翻，重排 + 换一条实现路径

我不认为需要推翻。但以"被动可靠性 > 主动可靠性"为第一原则重排优先级，会得到一个更稳的路线。这条原则的依据是模型侧的一个硬事实：

> **元认知盲区**：需要读 L1 的时刻，恰恰是我意识不到自己缺信息的时刻。L0 里那句"你有长期记忆，不确定时去读"的指引，在长上下文 + 复杂任务下的指令遵循会衰减；而"教训门"式被动注入不依赖我的自觉 —— 它把信息放进我决策路径的正中间。

**重排后的路线**：

| 阶段 | 原方案 | 重排后 | 理由 |
|------|--------|--------|------|
| P11.1 | 打底（分层 + 守卫） | **不变** | 这阶段没有依赖任何未证推断，先走 |
| P11.2 | persona pack 落地 + L1 按需读 | **教训门（扩展层）+ persona pack** | 教训门最小、可独立验证、不依赖未证推断；L1 按需读**降级为兜底**，其"模型会不会去读"的实测不再是关键路径上的风险 |
| P11.3 | 教训回路 + 记账 | **记账（触发即命中）+ revision + 蒸馏模板升级** | 回灌已在 P11.2 落地，本阶段剩收尾 |

一句话：**原方案把最可靠的能力（被动回灌）排在最晚，把最不确定的能力（按需读）排在较早的关键路径上 —— 我建议对调。** L1 按需读仍然要做（它是 fact 类资料的合理通道），但从"主路径"退为"兜底 + fact 专用"。

再补一条原方案没有的**第三优先级候选**（不强烈主张，列出备选）：L0 稳定段/易变段拆分（§3.3）如果做了，pi-memory（P10.1e）的"每回合自动注入"与本方案的关系就从"必须二选一"变成"**稳定段可以由 pi-memory 承担**"—— 它的 KV cache-stable 前缀恰好就是稳定段需要的形态。这给四主权边界提供了一个新的和解选项。

## 六、对 Q2b（未决项）的第三个答案

方案给 Q2b 的选项是"同一个 agent"或"副本"，并正确地把它标为产品决定。以模型本体的身份，我想补充一个**两个选项都没覆盖的答案**，供拍板时参考：

**persona pack 迁移的是先验（prior），不是连续性（continuity）。**

人格在推理侧的成立，依赖的不是静态文本，而是**文本 + 宿主行为模式的耦合**：SOUL.md 在 WorkBuddy 里的效力，一半来自文件本身，一半来自宿主的记忆注入节奏、工具面、交互历史。搬到 MangoX 后 —— per-turn spawn、不同的工具面、不同的记忆布局 —— 同样的 SOUL.md 会表现为**相似但不同**的 agent。这在认知上更像"同卵双胞胎共享先验各自成长"，而不是"同一个人换了身体"也不是"一份复印件"。

如果接受这个语义，那么**连续性不必靠"同一性"来担保，可以靠共享的 revision 历史与 key 体系来维护**：两个宿主各自演化，revision 历史汇流时你能看清"分叉以来各自学了什么"。这其实是第三个选项：**同一先验下的新个体 + 显式分叉史**。它工程上的含义是：镜像同步（若选"同一个"）的复杂度可以不用背，代价是接受"MangoX 里的星期五 ≠ WorkBuddy 里的星期五"这个心理预期。

这个答案是否成立，最终是 boss 对"星期五是什么"的定义问题 —— 我提供的是语义地图，不是选票。
