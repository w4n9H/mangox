## 一、现状与诊断

### 1.1 实证：这个功能目前没有承载任何东西

2026-09-21 查生产库（`~/.mangox/mangox.db`）：

```
knowledge_items 总条数 2
  global  | manual | active | enabled=0 | 1
  project | manual | active | enabled=0 | 1
  两条标题均为：1. 任何回复以"老哥"称呼我
```

**两条都是关的，而且是同一句的两份。** 这条记录本身即结论：**用户曾试图往知识库里放一条"人格规则"，然后把它关掉了。** 现有形态装的是"用户的资料"；要装的是 **人格 + 纪律 + 关系 + 教训** —— 同一张平铺表装不下这两类东西。

### 1.3 结构性差距（对照一套成熟的人工记忆实践得出）

参照物是跨会话记忆的现状形态：**四层文件 + frontmatter `read_when` + 层间引用**。逐维对照：

| 维度 | 参照（文件） | MangoX 现在 |
|------|-------------|------------|
| 组织 | 4 层，层间靠**引用**（"全文在 details"） | 一层平铺 `(title, content)` |
| 加载 | 按 `read_when` 分层：常驻 / 按需 / 往回查 | **100% 每轮全量注入** |
| 冲突 | 有**覆盖语义**（"上游写的 X 是错的，以本文件为准"） | 无 —— 矛盾就两条都进 prompt |
| 变更 | **改动史 = 成长史**（带日期与来源） | 只有 `createdAt` / `updatedAt` |
| 配额 | **排序即优先级**（"越靠上越要命，超限从尾部截断"） | 按 `updatedAt` 丢最旧 |
| 校验 | 压缩有**精确串零丢失比对** | 无 |
| 敏感 | 已知哪些不该外发（地址 / 库名 / 凭据策略） | 无标记，**每轮都进 LLM** |

### 1.4 两个实质缺陷（不是优雅度问题）

**缺陷 1 — 越重要的越先被丢。**
`KnowledgeStore.swift:66` 按 `updatedAt` **降序**排，`:68` 超预算即 `continue`（静默跳过）。于是保留的是"最新的"，丢掉的是"最旧的" —— 而**边界规则恰恰永远是最旧的那条**（"绝不往别人能看到的地方发半成品"）。
P3.7 契约原文是"超出提示并建议禁用最旧条目"，实现成了**静默丢弃** ⇒ **实现与契约偏差**，且丢失无任何信号。

**缺陷 2 — 敏感信息每轮外发一次。**
per-turn 架构下每回合一 spawn，注入块挂在 spawn 参数上（`:490-493`）。记忆天然包含服务器地址、库名、白名单策略、凭据纪律 —— 一旦搬入，**每一回合都往模型厂商送一份**。现有模型没有任何"这条只许本地读"的档。

## 二、架构主张：三载体 + 分层注入

### 2.1 载体划分

| | persona pack | knowledge（DB） | **knowledge base（挂载目录，P11.4）** |
|---|---|---|---|
| 装什么 | **我是谁 · 用户是谁 · 纪律与边界**（人格本体） | 事实 · 教训 · 项目约定（可积累的资料） | **成套的外部资料**（项目文档 / 笔记 / 参考资料），按目录打包 |
| 形态 | **文件**（一族 md，标准 frontmatter） | DB 表 `knowledge_items` | DB 表 `knowledge_bases`（**只存路径 + 描述**；正文仍在磁盘上） |
| 写入者 | 人（App 内只读展示 + 跳转编辑） | 人（面板 / 会话沉淀）+ 提炼候选（审核后） | 人：挂一个目录 + **写一句描述**；内容仍在各自的编辑器里写 |
| 怎么进 prompt | **全文**进 persona 段（结构性首段） | L0 条目（稳定段 / 易变段）或 L1 文件 | **只进索引**（描述 + 路径 + 文件清单），正文由 agent 自己按需 `read` |
| 为什么 | 可 git、可 diff、可手改、**可被任意宿主读** —— 换躯干时搬的是"我"，不是一份快照 | 需要作用域、审核闸门、命中信号、检索 | 成套资料**不该被搬进 DB**（会失去它自己的版本管理 / 工具链），也不该全文进 prompt |

**三档的分界是一条判据，不是三个并列开关（P11.4 拍板 2026-09-22）**：

| 档 | 谁维护 | 进 prompt 的方式 |
|---|---|---|
| **固定档** persona pack | 人（文件） | **全文在场，永不降级**（结构性首段） |
| **用户输入档** `knowledge_items` | 人（App 内） | **新建即生效**（进 L0）；标为按需的落 L1 |
| **知识库档** `knowledge_bases` | **各目录自己的主人**（App **只读不写**） | **只给索引**，正文按需 `read` |

> 判据 = **"这份东西有没有自己的生命周期"**。前两档由 App 管（DB / L0 预算 / 命中记账 / 格式约束）；知识库里的文件归它自己的目录管 —— 那可能是个 git 仓库、可能是别人维护的笔记、可能还在天天被改。App 只做两件事：**让 agent 知道它存在**（索引）、**告诉它去哪读**（路径）。
>
> 这也解释了 boss 那套蓝图的必然性（他 2026-09-22 给的简化轴）：**"每档该带什么"是档的固有属性，不是用户要选的** —— 固定档必然全文、知识库档必然按需、**只有用户输入档**才需要人决定"每轮还是按需"。所以复杂度不在"档有几个"，而在"把档的属性做成了开关"。


### 2.2 分层与两条注入路径

- **L0 常驻**：每轮进 prompt（走 `--append-system-prompt`）。**预算不可挤占，超限 = 告警 + 按 `priority` 可预测降级，绝不静默丢弃**（降级语义见 §4.2 A / 守卫 2）。
- **L1 按需**：**不进 prompt**，落成工作区文件；由引擎用内置工具（`read / grep / find / ls`）自己取。

原则一句话：**prompt 预算只该花在"每轮都必须成立"的东西上；能按需读的就别常驻。**

**L0 内部三段（评审折入 2026-09-22；索引段 P11.4 加）**：

| 段 | 内容 | 变更频率 | 位置 | 降级待遇 |
|---|---|---|---|---|
| **persona 段** | persona pack 全文 | 一年几次 | **偏移 0，独立首段** | **永不降级、永不截尾**（守卫 10） |
| **稳定段** | DB 中 `kind ∈ {人格, 用户, 硬规}` 的条目（`isStableSegment`） | 一年几次 | 紧跟 persona 段 | **永不参与降级**（守卫 2 的例外） |
| **索引段**（P11.4） | 知识库索引（每库：描述 + 路径 + 文件清单） | 挂 / 摘库时 | 稳定段之后、易变段之前 | **不参与 priority 降级；装不下 ⇒ 整段缺席 + 告警**（§3.4「预算待遇」方案 A） |
| **易变段** | 其余 L0 条目（`kind=fact` 等） | 随时 | 最后 | 超限时按 `priority` 从低到高截尾 |

> ⚠️ **本表的"稳定段"一行在 P11.2a 后曾写错**（原写"persona pack + `kind=rule` 硬规"）—— persona **pack** 自 P11.2a 起是**独立首段**，不再属于稳定段；稳定段装的是 **DB 里 `kind ∈ {persona,user,rule}` 的条目**。两处判据不同（一个读文件、一个读表），混写会让守卫 10 的"偏移 0"看起来像多余。**2026-09-22 修正。**

**索引段为什么插在稳定段之后、易变段之前**（而不是紧跟 persona）：判据是**前缀稳定性**。per-turn 架构每回合都 spawn ⇒ 逐字节稳定的前缀越长，provider 侧 cache 命中越划算。索引段的变更频率是"挂 / 摘库时"（月级），介于稳定段（年级）与易变段（随时）之间 ⇒ 放在两者之间**同时保住 persona + 稳定段这一整段最长稳定前缀**。放在易变段之后则等于放弃这条，放在 persona 之后会把它挤进稳定前缀里（一挂库就打断缓存）。

理由不是性能洁癖，是**成本结构**：per-turn 架构下每回合都 spawn，前缀逐字节稳定 ⇒ provider 侧 prompt cache 命中 ⇒ 人格注入的边际成本**趋近于零**；前缀一变则每次改动都全量重算。**"人格块跟上周加的一条事实拼在同一个字符串里同生共死"是要避免的耦合。** 守卫新增"易变段任何改动不得触碰稳定段字节"（§七 守卫 12）。

⚠️ **这条同时修正了旧风险 2 的对象错位**：该跟 pi-memory 对比的不是 L1（不注入）而是 **L0**（同样每回合注入的前缀）—— 于是四主权多一个**和解选项**：稳定段将来可由 pi-memory 承担（它的 KV cache-stable 前缀恰是稳定段需要的形态），见 §8.2 风险 2。

⚠️ **本项目无网络模型缓存时的实测边界**：以上是**推断 + 机制层面的必然**，provider 侧 cache 命中率**无实测** ⇒ 列 §8.3，不作为任何阶段验收项。

**L1 落地为什么零协议成本**：pi 内置工具已含 `read/grep/find/ls`，无需新 RPC，也不需要动 `--append-system-prompt` 协议。

**L1 的反方风险（本稿承认）**：模型可能**不知道要去读**。缓解 = 在 L0 里写一句固定指引（"你有长期记忆，路径 X，遇到不确定时去读"），成本是常数、比全量注入便宜得多。**但这是推断，尚无实测证据** —— 列为 P11.2 的验收项。

> ✅ **P11.4 正面回答它**：那句"固定指引"**升格为索引段**（每库一行描述 + 文件清单，**自动生成，不再手写**）。实证是：当前 `SOUL.md:71-80` 里手写着"常驻的三份 / 不常驻的（PROJECTS.md、memory/）"—— **那段手写文字就是索引的手工版**，而手工版有两个必然的病：加一个文件不会自动更新（模型永远不知道它）、删一个文件也不会（模型会去找一个不存在的文件）。P11.4 把它变成机制，并顺手覆盖 `~/.mangox/agent/memory/` —— 那正是 §7 守卫 6 里"不进 prompt"的那批条目，**在此之前除了那句手写文字，没有任何机制告诉 agent 它们存在**（真真空，见 §3.4）。
> 🔁 **2026-09-22 状态**：Q12 已执行（`PROJECTS.md` 搬进知识库），那段手写清单同步改写为**指向机制**；`memory/` 出现在索引里仍是 b 段未完成项（内置 L1 库已挂载，见 §3.4）。

### 2.4 与既有记忆出口的边界（**四主权**）

记忆出口已有三个，本篇新增第四个，必须一次说清，否则必然漂移：

| 出口 | 作用域 | 写入者 | 形态 | 状态 |
|------|-------|--------|------|------|
| **persona pack**（本篇新增） | 人格 · 用户 · 纪律（跨项目） | 人 | 文件 | 计划 |
| **KnowledgeStore** | 人工策展的跨会话知识 / 记忆 | 人 + 提炼候选（审核） | DB | 已落地（P3.7） |
| **pi-memory**（P10.1e） | agent 自主沉淀的笔记 | agent | 文件（`PI_MEMORY_DIR`） | **计划项，未落地**（实测 `~/.mangox/pi-config/` 下无 `extensions/` 与 `memory/`） |
| **交接文件**（P3.9） | 单个长期任务的动态状态 | agent 写、人可改 | 文件（`<项目>/.mangox/tasks/<taskId>.md`） | 已落地 |

判据沿用 P3.9「唯一主权」（跨 spawn 存活 + 可控可备份可人肉修改）。**四者的冲突面不重叠**：人格 ≠ 自主笔记 ≠ 任务状态 ≠ 策展知识。

**但 persona pack 与 DB 里的 `人格/用户/硬规` 三类条目存在功能重叠 —— 这必须钉死**（见 §3.1 `key` 与 §3.2）：

- **persona pack = 该 `key` 的唯一持有者**（人格本体的真源；删掉它，这个 agent 就不再是"它"）。
- **DB 不得持有 pack 已占用的 `key` —— 设计上不允许冲突存在**（拍板 2026-09-21）：写入 / 采纳时校验，撞了就**拒绝创建**，UI 引导「这条由 persona pack 持有，请去改文件」+ 给"在 Finder 打开"入口。
  - 好处是**不需要"谁赢"的规则，也就不存在静默失效** —— 上一稿提的"DB 覆盖文件 + 显性提示"整个被消掉了（那是打补丁：允许冲突再造一个提示去兜）。
- **覆盖语义仍然存在，但只在同一载体内部**：persona pack 自己可以有「上游写的 X 是错的，以本文件为准」这类**跨来源**表述（这是它**内部**的事，与 DB 无关）；**跨载体一律禁止冲突**。
- 由此 `key` 是**全局唯一**的：`knowledge_items.key` 加 `UNIQUE`，且与 pack 解析出的 key 集合**对账**（§七 守卫 3）。
- **UI 必须让"被占用的 key"可见**（§4.2 D），否则用户会反复尝试创建同一条 —— 禁止而不提示 = 把用户关进一堵没写字的墙。

### 2.5 L0 超限的确切语义（两个场景，一个答案）

旧契约"L0 超限 = 红条 + 报错"在**无人值守**路径上**不成立**：邮箱哨兵 / cron / watch 都走 `beginTurn` 的同一套 spawn 组装（`ChatStore.swift:1352`，`approvalOverride` / `unattended` 最终 `t.send(...)`）—— **注入块一样被拼进去，但那里没有屏幕，红条无人看**。

| 场景 | 行为 |
|------|------|
| 交互会话 | **红条 + 告警事件** + 按 `priority` 降级截尾（人看得见） |
| 无人值守 | **告警事件**（进日志 / 事件流）+ 同一套降级截尾；**不阻断 spawn** |

铁律：**记忆故障不具备打断任务执行的权力。** 预算问题不该让生产任务停摆（同"DNS 解析失败不该挂起磁盘 I/O"）。契约从"报错不丢弃"修正为 **"告警 + 可预测降级"** —— 报告的对象是 UI / 日志 / 事件流，而**注入行为本身永远有定义良好的输出**。降级顺序 = **按 `priority`**（而非现状的 `updatedAt`）：`priority` 是作者表达意图的字段，`updatedAt` 只表达"谁最近被碰过"。

**实现澄清（2026-09-22，写冒烟断言时才定死的）——降级是「截尾」，不是「贪心填空」：**

| | 规则 | 反例症状 |
|---|---|---|
| ✅ **截尾**（本篇） | 按 `priority` 降序摆，**一旦某条装不下，它与它之后的所有条目一律降级**；入块集合 = 排序的**前缀** | —— |
| ❌ 贪心填空 | 装不下就跳过它、继续试后面的小条目 | 用户看到 **priority 180 的大条目没进 prompt，priority 3 的小条目却进去了** ⇒ 规则不可预测 = 无字之墙 |

判据是本节那句"**可预测**"：贪心填空把预算利用率做高了，却让"谁进了"变成**只有组装器才知道**的事 —— 而 §4.2 A 块的红条必须能说清"降了哪几条"，前提就是降级集是**排序的尾巴**。冒烟 T-KNOW 用「3×16000 字吃满预算 + 一条装不下的 D + 一条很小但 priority 最低的 E」确定性构造，断言 **E 也不进**。

### 2.6 教训回灌的三态时序（第三份评审仲裁，2026-09-22）

前两份评审在这里形成了**真分歧**，第三份给出仲裁，落为本文正文。

**分歧**：GLM-5.3 主张**扩展层「教训门」**（`pi.on("tool_call")` 命中 trigger → `{block:true, reason:教训全文}`，重试放行）；DeepSeek V4 Pro 反驳它"把正确性押在模型会重试上"，主张**回合边界前瞻注入**（`beginTurn` 拼第二条 `--append-system-prompt`）。

**仲裁判词：两个都要，按 trigger 的「可知时点」分通道，谁也不许越界。**

| 时点 | 通道 | 能看到的信号 | 适用 trigger | 归属 |
|------|------|-------------|-------------|------|
| **决策前** | 回合边界前瞻注入（`beginTurn` → 第二条 `--append-system-prompt`） | 项目 / cwd / 会话面 | **项目级**（"这个仓库的构建必须走 xcodebuild"） | P11.3 |
| **决策中** | 扩展层教训门（`tool_call` 拦截） | `input.path` / `input.command`（`mangox-approval.ts:184-188` 已这么用） | **文件 / 命令级**（"改 `blockedReason` 前要扫视图消费"） | P11.3 |
| **决策后** | 钩子占位（§5.7） | 工具错误返回 / 用户否定 | 待定，只提议不自动 | P11.3 留位 |

判据是**信息可达性**，不是口味：`beginTurn` 时点**不可能**知道本回合会碰哪个文件（这是硬约束，不是实现不力）；而文件级 trigger 只有在 `tool_call` 时点才可见。**单独押任何一边都会留下一整类教训够不着。**

**GLM 那条"最漂亮"的补丁在此被正面采纳、但剥掉它的唯一通道地位**；DeepSeek 的"自我报告"指控由三条配套解掉（不否决机制，而是让失败可观测）：

1. **教训门每拦一次 = 一次强制命中**（`hitCount++` + `lastHitAt`），并把"拦后是否重试 / 重试是否改了调用参数"落库 —— 于是"教训出现了但被无视"变成**可度量**的，不再是静默失败。
2. **教训门不得复制 `ctx.hasUI` 守卫**（`mangox-approval.ts:183`）：无人值守恰恰是 lesson 价值最大的场景（那里没有人兜底）。详见 §8.2 风险 6。
3. **稳定 lesson 可以"毕业"**：已被验证稳定、且反复确认过的 lesson，从教训门（决策中）降级为前瞻注入（决策前）—— 省掉每会话至少一次工具往返的成本。这是一次人工操作，不是自动的。

**配套的通道语义纪律（DeepSeek 的第二条批评成立）**：教训门与审批门**复用代码可以，复用语义不行** —— 审批门的 block 要模型**停**（等人决定），教训门的 block 要模型**继续**（知悉后重试）。将来任何对 `tool_call` 拦截的改动（如"连续 N 次 block 就放弃"的保护）都可能在不知情下**杀死教训传递** ⇒ 教训门在扩展源里**必须与审批逻辑分段、可被单独断言**（守卫 11）。

**本文同时采纳 GLM 的降级判断**：L1「工具按需读」从**主路径**退为**兜底 + `fact` 专用**（教训类走上面两个通道），但**阶段顺序不变** —— 理由采纳 DeepSeek 的"阶段顺序是资源问题不是正确性问题"，且前瞻注入本身依赖 trigger 注册表（P11.3 的数据面），提前要拆一次注册表。

  - **动因（两步）**：boss 先问"这标题是你自己加的吗，如果是个新用户写了 SOUL.md 怎么办"，再追问"这玩意你确定每个用户都会写吗"。第一问暴露的是"`summary` 没有出口"，于是先做了**回落链**（`summary` → 正文首个 ATX 标题 → 文件名）；第二问推翻了那条链的前提 —— **用户写什么不可控**：`summary` 没人会写、正文里有没有 `#` 标题也不一定。链只是把赌注缩小了一点，实质仍是**从内容推导**。
  - **判据（撤链的真正理由）**：标题是**产品概念**（"这三份分别是什么"），不是**文件属性**（"这个文件里写了什么"）⇒ 该由 App 回答，不该拿去问用户。**能由产品回答的问题，不要拿去问用户。**
  - **固定表**：`SOUL.md` → 「我是谁」、`RULES.md` → 「我必须怎么做」、`USER.md` → 「你是谁」；行标题 = **`<文件名> - <出厂文案>`**。**表外文件只有文件名**（不留 ` - ` 后缀 —— 没有后半句却留个破折号，看着像被截断了）。大小写不敏感（`soul.md` 算同一份），且显示的是**文件真实拼写**（不是表里的规范名）：用户手打文件名的字母大小写不该决定他看不看得懂那一行，而放宽的代价是零。
  - **`summary` 随之从契约删除**（判据同 `shared`，P11.2c）：一个"用户得写、系统不看"的字段，代价是每个读 frontmatter 的人都要多问一句"这个要不要设"。老文件里的残留行**静默跳过**（不报错、不生效，与从前逐位一致；同 `shared` 的处理方式，不需要额外的忽略分支）。
  - **文案住 View 层**（`Views/Knowledge/PersonaRowText.swift`）：它是**用户可见文案** —— 要进词表、要中英各自正确；而模型层只出数据（**判据：文案归 View，数据归模型**）。`PersonaPackEntry` 因此连"标题从哪来"的三态都不留 —— 留个枚举只会让人以为还有回落链。
  - **副标 = `persona · <字数> 字`**（+ 破损 / 按需标记）。标题既然已经带上文件名，副标就**不再重复文件名**（`subtitleNeedsFileName` 那条判据随之删除）。**字数取 `entry.content.count`（进 prompt 的那部分），不是整份文件的大小** —— 见 §4。
  - **代价（诚实记）**：标题**不可由用户自定义** —— 想把 `SOUL.md` 那行叫别的名字做不到，没有可写的地方。接受它的理由是：这一行的作用只是"认出这三份是什么"，而自定义标题的需求从未出现过（`summary` 从落地到删除，pack 之外零消费）。
- **`shared` 字段曾在此列 —— P11.2c 已删**。它为零消费的预付（无逻辑读、无界面显示），详见 §8.1 Q2b。
- **`read_when` 不驱动任何逻辑** —— 它是给人读的说明，真开关是 `layer`。且它是文件里的**原文、不走本地化**（同一份文件要能被任意宿主读）。
- **`keys` 是"设计上不允许冲突"的实现支点**：组装器解析全部 pack 文件的 `keys` 得到一个**保留集合**；DB 侧写入 / 采纳该校验（§七 守卫 3）。解析失败 = 组装自检红（§5.6）。
- **`layer` 字段的归宿（P11.4 收编，2026-09-22 拍板：boss 定"pack 的 ondemand 统一走知识库档"）**：pack 里**只保留 `always`** 的语义 —— pack 装的是人格本体，"我是谁"没有"需要时才想"这一档。
  - **过渡语义（必须有，不能直接删键）**：遇到 `layer: ondemand` 的文件时，**照旧不进 prompt**，但在**组装自检里点名告警**："该文件属于按需资料，请迁到知识库档"。为什么不直接当 `always` 处理：那会让一个原本不注入的文件**突然整篇挤进 persona 段**（prompt 当场变大，且人格段被掺进非人格内容）；为什么不静默忽略：它会**隐形**（既不进 prompt 也不进索引），正是 P11 要根除的那类缺陷。**✅ 2026-09-23 已落地**：`KnowledgeInjection.onDemandPackFiles` → `KnowledgeWarning.onDemandPackFiles(files:)` → 红条（`KnowledgeView.warningLines`）；冒烟 T-KB 段两条断言（在时报 / 移走后消失）双向锁定。
  - ⚠️ **它是长期护栏，不是"会自己消失的过渡态"**（2026-09-23 修正，原判据是"迁移完成后该解析分支与告警一并删除"）。迁移确实完成了（Q12-A 把最后一份 `PROJECTS.md` 搬走），但**删不得**，两条理由各自独立：① 解析分支一删，老文件就落到 `p.layer ?? .always` ⇒ **整篇挤进 persona 段**，正是上一行要防的那件事，而且是**静默**发生的；② 少了告警，"往 pack 里丢一个按需文件"就重新变成**对模型隐形且零红灯** —— 那正是 `PROJECTS.md` 那个洞的形状（§3.4）。⇒ `layer` 保持为 pack 契约里的合法键；只要还可能有人写它，这条告警就得在场。
- **缺省 `layer` = `always`（P11.2a 定）**：丢进 `~/.mangox/agent/` 的文件就是人格本体。若缺省是 `ondemand`，一个忘写 frontmatter 的文件会**静默地完全不生效** —— 而那是人格，静默失效的代价最大。缺省取"更响亮"的那一侧。
  - 注：曾计划"P11.4 把 ondemand 从 pack 契约里拿掉"，**2026-09-23 判定不做**（理由见上一条：删了会让老文件静默挤进 persona 段）⇒ 这条缺省**仍有"另一侧"**，当初"缺省取更响亮的那侧"的判据继续有效，不是退化表述。
- **破损 ⇒ 不注入、不做乐观假设（P11.2a 定）**：frontmatter 开头的 `---` 没收尾时，连 `layer` 都读不出来 —— 这种文件**不进 prompt**（而不是"按缺省 `always` 塞进去"），且**保守禁止新建任何带 `key` 的条目**（守卫 9：失败时收紧）。但它**仍在左列可见**（红标记 + 文件名）—— 用户得先知道是哪个文件坏了，才修得动。
- **空 pack（persona 段为空）⇒ 必须响，但照旧不阻断（2026-09-23 补，boss 实测提问触发）**：
  - **问题**：`personaSegment` 里 `guard !entries.isEmpty else { return "" }` ⇒ pack 空了 persona 段**整段消失**，本轮 prompt 里没有"我"。而加载/组装/自检**三处都静默**，唯一相关的那条自检（守卫 ⑤ `personaNotAtOffsetZero`）在 persona 段为空时**短路成 false** ⇒ 把三份 md 删光，**全部守卫仍然绿**。面板侧另一处：常驻区头原本裹在 `if !pack.isEmpty` 里 ⇒ 连"去哪个目录放文件"的入口也一起消失。
  - **判据**：**挑不出任何可载入的条目**。刻意**不是**"少了几份" —— 用户可故意只留一份（把"必须三份"这种结构塞回数据正是 §2.1 反对的）。
  - **两个原因分开报**（`PersonaPackEmptyCause`）：`dirMissing`（目录不在）与 `noFiles`（目录在、里面没有可载入的 `.md`）—— 两者的用户动作不同（去建目录 / 去放文件），而"下一步做什么"是告警唯一的用处。`PersonaPack.dirMissing` 在 `load` 入口判定（目录不存在与目录不可读在 `contentsOfDirectory` 那里退化成同一个失败，事后分不出来）。
  - **不重复报**：破损（`.personaFrontmatterBroken`）/ 全按需（`.onDemandPackFiles`）/ 读不出来（`.personaUnreadableFiles`）三种情形**各有更准的告警**，空 pack 那条让位。**同一件事挨两枪 = 红条变噪音，用户开始无视红条，那比不报还坏。**
  - **`unreadableFiles` 从死字段变成有消费者**：它此前声明于 `PersonaPack:53`、只在 `isEmpty` 里被喂了一次、全库无人读。而"文件在磁盘上、`ls` 看得见、内容却没进 prompt"恰恰是**磁盘上完全看不出来**的一件事 ⇒ 只有组装器知道，不报就等于没有。
  - ⚠️ **与"pack 目录不存在时组装器必须照常工作"不矛盾（§六 6.2a / §8.1 Q7）**：「空 pack ⇒ 空 persona 段 ⇒ 与 P11.1 行为一致」这条**一个字没改** —— 组装照旧产出同样的字节、任务照旧执行。新增的只是**可见性**。判据对仗：**可见性 ≠ 阻断**（同"可见性 ≠ 注入资格"，§8.1 Q5）。
  - **代价（诚实记）**：首启裸环境也会亮这一条。App **不可能**区分"从未有过"与"刚被删掉" —— 在文件系统上它们是同一个状态，要分辨就得额外存一份持久态（上次见到非空 pack），而那份状态自己也会过期 ⇒ 判据宁可选**可判定**，不选**能分辨**。措辞相应地只报事实（"本轮 prompt 里没有「我」"），**不写"被删了"**。
  - **面板侧配套**：常驻区头**不判空**（与知识库区同一条判据 —— 恢复入口住在这一段里，藏起来的入口 = 没有入口）；区头那个「文件夹」按钮在目录不在时会**就地建目录**（`open` 对不存在的路径是静默失败，实测 2026-09-23；建的是**位置**不是正文，不违"App 只读"）。
- **全项目单一 frontmatter 解析器（P11.2a 定）**：`PersonaPack.parse` 是唯一实现，`KnowledgeStore.parseFrontmatterKeys` 退化为它的薄包装（`broken → .failed` / `noFrontmatter → .none` / 否则 `.keys(…)`）。两份实现迟早对同一个文件给出不同判定 —— 一份说破损、一份说没事，守卫 9 就漏了。同类纪律见 §二"单一解析器"。
- **persona pack 是结构性首位，不是"priority 碰巧排前"（评审折入，2026-09-22）**：组装器的输出结构里，**persona 段 = 独立第一段，不参与 L0 条目的 `priority` 排序、也不参与超限截尾**（§2.2 稳定段 / §七 守卫 10）。
  - 理由：`fact` 是可丢的知识，`persona` 是"我" —— 丢了它这个 agent 就不再是它。**两者失败代价不在一个数量级**，所以不能用同一个可手滑改掉的数字参数来担保。守卫清单原先**没有一条**保证"persona 恒排任何 fact / lesson 之前"：明天有人重构 `buildKnowledgeBlock` 把易变段排前面，所有守卫仍然全绿。**把"我是谁"从数据升格为不变量。**
- **只读**：App 不提供 persona 编辑器，只提供"查看 + 在 Finder 打开"。**双写必漂移**（P3.9）。
- `read_when` 的落地：本期只消费 `layer`（always/ondemand）；`read_when` 作为**人类可读的说明**保留，不驱动逻辑（避免引入第二套调度语义）。

### 3.3 L1 落点与命名

| 作用域 | 落点 |
|--------|------|
| 跨项目 | `~/.mangox/agent/memory/` |
| 项目内 | `<项目>/.mangox/agent/`（建议 gitignore `.mangox/`） |

命名**不占** `AGENTS.md` / `CLAUDE.md` / `.pi/`（沿用 P3.9「概念重命名」：防 pi 自动加载误捕、防与人类约定文件名冲突）。

**落盘粒度 = 一条一文件，文件名 = `key`（评审折入，2026-09-22）**：这是**归因的硬要求**，不是审美 —— 若多条合并落盘，`read` 了一个文件无法归因到单条，`hitCount` 就记不了账（§5.2 的整个命中信号依赖它）。`key` 为 NULL 的条目按 `item_id` 生成稳定文件名。
顺带好处：文件名 = key 让 **DB 撞 key 校验多一个天然对账面**（§3.2 `keys` 保留集合可与目录列表直接对账）。
代价：文件数 = 条目数（个人量级 < 100，可接受，且比"合并文件 + 内部锚点"更抗人肉编辑）。

**磁盘为准**：每次组装现读文件，不落缓存 —— 用户任何方式改文件，下轮即生效。

**实现细节（P11.2a 落地，2026-09-22）**：

- **落 L1 的判据 = 同一个"不进 prompt"**：即 **`!isResident`**。P11.2c 前它有两个来源（`layer == .ondemand` 与 `sensitivity == .local`，后者已删），**现在只剩 `layer`**；但判据仍然是 `!isResident`，**不是**重写一遍 `layer == .ondemand` —— 分组必须是**真划分**，且必须与"进不进 prompt"共用唯一判据。此前 `always + local` 正是那个反例（既进不了 prompt、又不是 ondemand ⇒ 按 layer 筛会从两个分组里同时消失）。冒烟用同一条断言覆盖。
- **路径断言 `isAllowedL1Path`（守卫 7）挡两侧**：① **目录侧** —— 不占 `.pi/`；② **文件名侧** —— `key` 可能就叫 `AGENTS.md`，而 `l1FileName(for:)` 是 `key + ".md"`，于是会写出一个 **pi 自动加载**的文件（绕过整个 L0/L1 分层）。实测净化结果 `k-AGENTS.md.md`。同时挡路径穿越（`..` / `\` / `:` / `\0`，实测 `k-..-..-escape.md`）。
- **净化对正常 key 是恒等变换**（`note.alpha` → `note.alpha.md`）—— 只有畸形 key 才看得到 `k-` 前缀。这样"文件名 = key"这条归因前提（§3.3 首段）在正常路径上**逐字节成立**，诱饵不在。
- **一条一文件的落盘是"全量对账"，不是"只写不删"**：写应存在者 + 删**带 `mangox_item:` 标记**但已不该存在者。**无标记的外部文件一律不动**（目录是 App 管的，用户的文件是用户的）。只写不删 = "记忆只涨不缩"换个地方复发 —— 而那正是 P11 要修的两个实质缺陷之一。
- **文件正文 = 条目标题化 + 文件化**：`kind=fact` 的条目加一句"以下是一条事实"前言 —— 判据是"**读到才知道**"而非"推到面前"，所以 L1 **只在 Read 时记账**（§4.2 C 的命中语义）。
- **重定向钩子**：`l1RootOverride` / `personaPackDirOverride` 只服务测试（§6.2a 范围红线）。

### 3.4 知识库档：挂载记录 + 扫描契约 + 索引（P11.4，2026-09-22 拍板）

**一级实体 = 一条"挂载记录"**：`{ 目录路径, 描述（必填）, 启用 }`。
**描述为什么必填**（boss 明确要求："新增目录的时候需要填一个知识库描述，然后形成描述+索引"）：索引里如果只有文件名，agent 拿到的是**一串字符串**，它没法判断该不该去读 —— 一手文件名 `2024Q3-复盘.md` 说明不了这是财务还是技术。一句描述把"这是什么的资料"先给它，再给清单，**这才是卡片目录（分类说明 + 架位）的形态**。描述长度上限 **200 字符**（它是"一句话"，不是摘要）。

#### 表结构

```sql
CREATE TABLE IF NOT EXISTS knowledge_bases (
  id          TEXT PRIMARY KEY,
  path        TEXT NOT NULL,              -- 目录绝对路径（存展开 ~ 之后、标准化的形态）
  description TEXT NOT NULL,              -- 必填，≤200 字符
  enabled     INTEGER NOT NULL DEFAULT 1,
  created_at  REAL NOT NULL,
  updated_at  REAL NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_kb_path ON knowledge_bases(path);
```

- **幂等建表**（`CREATE ... IF NOT EXISTS`），老库升上来是**空列表** ⇒ 无需迁移脚本（同 §3.1 的补列策略）。
- **`UNIQUE(path)`**：同一目录挂两次 = 索引里同一份资料出现两遍，纯浪费预算 ⇒ 在建/改两处都拒绝（**拒绝创建**，不是"谁赢"；同 packing 的 key 冲突语义）。
- **第一版不做 `scope`（全局/项目）**：目录路径**本身就是作用域的天然表达**（`~/Documents/notes` 是全局资料，`<项目>/docs` 是项目资料）。多加一个 scope 旋钮就会出现"这个库是项目的但它在我家目录里"这种自相矛盾的配置 ⇒ 等真出现需要时再加（**这正是 P11.2c/d 那条纪律：字段不是越全越好，是"用户能不能合理地决定它"**）。

#### 扫描契约（**固定参数，不给旋钮**）

| 项 | 取值 | 判据 |
|---|---|---|
| 扩展名白名单 | `.md` / `.txt` / `.html` / `.htm`（大小写不敏感） | boss 定："仅读取文档格式，md/txt/html 应该够用"。`.htm` 与 `.html` 是同一种格式的两种后缀，一起收（漏了它只会让人困惑） |
| 递归深度 | **≤ 3 层**（根目录下的直接文件 = 第 1 层；`a/b/c.md` = 第 3 层；更深的不收） | boss 定。**这条必须有明确的口径** —— "递归 3 层"在"含根"与"不含根"两种读法下差一层，而差一层就会让人说"我明明放进去了" |
| 符号链接 | **不跟随** | 防环（自引用目录会让遍历不终止）+ 防越界（链到库外） |
| 排除项 | 隐藏项（`.` 开头 → 它同时挡掉 `.git` / `.build`）、`node_modules`、`DerivedData` | 一挂就是代码仓库时，这几项能占掉索引的绝大部分位置，且**它们从来不是"资料"**。注意 `.git` / `.build` 归"隐藏项"那条管，常量表里不重复列 |
| 读什么 | **只读目录项，不读文件正文** | 索引只需要名字 ⇒ 扫描成本与文件总大小**无关**、也不需要缓存内容。这同时是"App 只读不写"的具体形态 |
| 每库索引上限 | **≤ 120 行 / 2000 字符**（先按行截，再按字符兜底）；超出折成 `… 另 N 个文件` | 上限存在的理由不是洁癖：索引进 L0、吃的是每轮预算。**折省略而不是静默截断** —— 不写"另 N 个"，agent 会把"索引里没有"读成"资料里没有" |

#### 索引段的确切形态

```
[知识库] 项目文档
路径: /Users/moofs/Code/mangox/docs
说明: MangoX 的 P0~P11 设计文档, 一个阶段一个文件
文件 (12, 深度≤3):
  P10-functional-design.md
  P11-functional-design.md
  P3-functional-design.md
```

- **`[知识库]` 是注入块的契约 token**（与 `[教训]` 同类）：模型看到的就是这个字面量。⇒ **恒中文、不许本地化**（同 `KnowledgeKind.tag` 的理由：界面语言不许改 prompt 字节）。
- **必须给绝对路径** —— agent 拿到索引后要自己能读。只给文件名等于给了它一张没有馆址的卡片。
- **多层级文件用相对路径**（`sub/a.md`）—— 深度信息本身有价值（"这是子目录里的"）。
- 每库之间空一行；`enabled = 0` 的库**整段不出现**（不是"出现了但标灰"——索引是给模型看的，没有"灰"这个状态）。

#### 预算待遇（**已拍板 = 方案 A**，2026-09-22）

索引段吃 L0 预算，但它**不属于 `knowledge_items`、没有 `priority`** ⇒ 按 `priority` 降级那套对它不适用。三个候选：

| 方案 | 语义 | 代价 |
|---|---|---|
| **A ✅ 拍板** | 不参与 priority 降级；预算装不下时**整段缺席 + 告警点名每库占多少字** | 地图**宁缺勿残**：局部截尾的地图会让 agent 以为"资料只有这些"，比"没有地图"更坏（后者至少它知道自己不知道） |
| B | 按库为单位降级：从字数最多的库开始摘 | 能保住大部分索引；但"为什么这个库在、那个不在"要人算 |
| C | 结构性段，永不缺席（与 persona / 稳定段同级） | 最安全也最危险：挂多了会撑爆 L0 预算，而"永不降级"意味着**没有兜底** |

> **A 与 C 的分界判据**：C 把"索引一定在场"当成不变量，但**不变量必须能被机制保证**（persona 段之所以敢设永不降级，是因为它长度有界且由人手工维护）。索引长度**由目录内容决定** ⇒ 它给不出这个保证 ⇒ 只能靠"每库 2000 字上限"间接约束，而库数无上限 ⇒ **选 A**。

**A 的落地形态（P11.4a 已实现）**：`knowledgeIndexSegment()` 先于易变段判定；装得下则进块并从 `budget` 扣掉，装不下则 `indexSkipped` 记下 `[KnowledgeBaseCost]`（每库：显示名 + 字数）⇒ `KnowledgeWarning.indexSkipped(bases:)` ⇒ View 红条点名。**缺席只影响索引这一段** —— 同一次组装里易变段照常注入（冒烟断言）。自检 ⑥ 兜住"既不进块、又不在缺席名单里"（= 静默丢弃）。

#### `kind=ondemand` 的 DB 条目与 `memory/` 目录（**已拍板 = 方案 A**，2026-09-22）

`~/.mangox/agent/memory/`（跨项目 L1 落点）与 `<项目>/.mangox/agent/`（项目内 L1）里落着的，正是**"不进 prompt、需要时才读"**的条目 —— 它们的语义**与知识库档逐字相同**（只给索引、正文按需读）。所以：**把这两个 L1 目录作为内置知识库自动挂载**（不可删、可在 UI 里看到、描述由 App 写死："按需知识的落盘目录（App 管理）"）。

不做的话有个**已知的洞**：`kind=ondemand` 的 DB 条目**依然对 agent 隐形** —— 除了 `SOUL.md` 里那句手写文字，没有任何机制告诉它这些文件存在（§7 守卫 6 的"不进 prompt"是对的，缺的是"进索引"）。

**A 的落地形态（P11.4a 已实现）**：

- 内置库**不落库、每次现算**（`builtinKnowledgeBases`）—— 它们的身份由落盘目录决定（项目增删、目录存亡自动跟随）；落库会出现"项目删了但库还在"的幽灵行。
- **存在不归用户配置，是否生效归用户配置**：内置库**不可删**（删了下次现算又回来，"删了又出现"的按钮比没有按钮更坏），但**可停用**（`builtinDisabled: Set<String>`，不落库 —— 它是 UI 偏好级别的东西，与落盘目录同生共死）。
- ⚠️ **停用开关必须走"折算进 `enabled`"的那条路**（`effectiveKnowledgeBases`，2026-09-22 由 `injectableKnowledgeBases` 改名）。落成"扫描时读 `allKnowledgeBases`"会让开关**静默失效**：内置库的 `enabled` 恒为 `true`，`guard base.enabled` 永远放行 —— 开关点了没反应，而没有任何红灯。冒烟为此单设一条断言（造反例 ④ 实测会红）。
- 同一目录只挂一次：内置库列表按 `path` 去重，与建表 `UNIQUE(path)` 同判据。

#### App 只读不写（红线）

知识库目录里的一切，App **只读**：不写入、不改名、不删除、不生成任何隐藏索引文件（不在用户目录里留 `.mangox-index` 之类的东西）。理由与 P11.2a 的 pack 红线同源：**目录的主人不是 App**。索引是**现算**的（每次组装现读目录，不落缓存，与 §3.3"磁盘为准"同一条纪律）。

## 四、UI：从"条目列表"到"载荷表"

### 4.1 三个结构性问题（对着代码定位）

1. **显示的对象错了。** 面板回答"我存了什么"；真正该回答 **"这一轮我带什么上飞机"**。整个 UI **没有任何地方**显示"哪几条进 prompt / 占多少预算"（唯一线索是 Chat 页 Composer pill 里的一个数字，`ChatComposer.swift:308-321`）⇒ 静默丢弃就是这么发生的：**在一个看不见预算的界面里管理预算**。
2. **平铺淹没了层。** 左列只有"待审核 / 正式"两段（`KnowledgeView.swift:70-79`）：人格、硬规则、项目事实、教训 —— 权重差三个数量级的东西同字号、同开关并排。且 persona 以"可编辑条目"身份出现（它来自文件，不可写）。
3. **生效路径藏在别的页面。** 改完要重启引擎才生效，而按钮在 **Chat 页**。在知识面板改十分钟，本页看不到"还没生效"。

### 4.2 五块设计（A~E）

**A · 顶部载荷条（新造，最重要）**
`每轮都带上 4 条 · 1,240 字 / 64k = 2%` + 进度条 + `需要时才查 47 条 · 不占预算` + `查看本次注入` + `改动未生效 · 重启引擎`。
- **契约变更：常驻层超限 = 红条 + 告警 + 按 `priority` 降级截尾（注入永不阻断）；按需层永不告警。** 预算压力只压给该压的那一层 —— 直接修掉缺陷 1。红条是**交互场景**的呈现（无人值守只有事件流，§2.5）。
- 超限红条必须写明**降了哪几条**（`priority` 最低者）与"去调 priority 或改按需"—— **"超限了"是无字之墙，"这三条没进 prompt"才是可行动信息。**2026-09-22 已落地**：告警由 `KnowledgeWarning.residentOverflow(titles:)` **带标题**（红条列前 3 条 + `help` 给处置指引"去调 priority 或改成需要时才查"），且**组装器只出数据、文案在 View 侧拼**（理由见 §8.2 风险 9）。
- `重启引擎` 就长在它影响的对象旁边（复用现成的 `knowledgeDirty`，不新造状态）。
- `查看本次注入` → 只读 **Markdown 预览** sheet（初版是纯文本 `Text`，2026-09-23 改）。理由：**门禁绿 ≠ 改对了，真发出去的文本必须能被眼睛看见。**
  - **⚠️ 不许退回"一个 `Text` 承载整块文本"** —— 那个写法在大文本上是**平方级**的。实测（`python3 scripts/diag/render_probe.py`，560pt 宽、**全高布局**）：

    | 行数 | `Text` 整块 | `MarkdownView` |
    |---|---|---|
    | 139 | 199 ms | 26 ms |
    | 561 | 4 251 ms | 105 ms |
    | 3 341 | **36 108 ms** | 646 ms |

    内容 ×24 ⇒ `Text` ×181（平方），`MarkdownView` ×24.6（线性）。注入块上限 64 000 字符 ⇒ 旧写法**最长 36 秒**，这就是 boss 说的"卡顿到转圈圈"。机制：`MarkdownView` 把文本按块拆成多个小 `Text`，每个各自布局 ⇒ 总代价线性。两份预览（本 sheet 与 `packEditor`）同源同规矩。
  - **量这个开销时有个陷阱**：`frame(height: 可见高度)` 会裁剪 ⇒ 同一份内容测出 206 ms 而非 8 512 ms（**差 41 倍**）。必须给**内容真实高度**，否则这个 bug 在探针里完全不存在。
  - **可复制**改由行尾 `复制全文` 按钮承担：`MarkdownView` 的选中是**逐块**的，没有"一次划过整篇"的选法，而这一页的用途正是"把真发出去的文本拿走"。
  - sheet 尺寸同时从 560×420 放大到 720×560 —— markdown 的标题/列表层级在窄框里会挤在一起。

**B · 左列分组：按来源分三区（2026-09-22 P11.4b 改版，替换原「按层分两段」）**

**常驻 / 自定义 / 知识库**（boss 原话：「三个区域即可, 最上面的是常驻区, 然后是自定义区(就是我手动增加的), 最下面是知识库区」）。区头计数各自取**该区断言的成员数**：常驻 = `pack.residentEntries.count` · 自定义 = `pending.count + custom.count`（**待审核排最前** —— 「需要动作的东西埋在列表中间」是用户永远发现不了的 bug）· 知识库 = `bases.count`。

**为什么改按来源**：按层分组会把**同一个来源劈成两半** —— persona 文件与用户条目在「每轮都带上」与「需要时才查」两段里各出现一次，那才是「看着乱」的真正来源。

**`isResident` 因此降为行内标记**（不再是分组维度，且只在**按需**（非缺省）时才出现在副标里，见 `PersonaRowText.subtitle`）。**但这条纪律不随之作废**：① 分组维度只能有一个，正交维度必须在**行内**表达；② 「进不进 prompt」必须与载荷条 A 块共用**唯一**判据（`:103` 的 `onDemandCount`），否则条上说 3 条、左列只列 2 条。注：`isResident` 曾有一个**既进不了 prompt、又不是 ondemand** 的第三态（`layer=always` + `sensitivity=local`），按 `layer` 硬筛会让它**从两个分组里同时消失**；该态已随 P11.2c 删除，但**「可见性 ≠ 注入资格」是同族坑** —— P11.4b 实测：把 `enabled` 并进分组判据，会让行内关掉开关的条目从两处同时消失且**零红灯**。冒烟 T-KNOW 守这条划分不变量。

**两个区恒不判空**（常驻 · 知识库）：它们的区头各带一个**唯一恢复入口**（「文件夹」按钮 / 挂载行）⇒ 判空会把入口一起藏掉。
persona 行右侧是 **`文件`**（只读标记），不是开关。

**persona 行 + 只读编辑器（P11.2a 落地 2026-09-22；元信息行同日精简；正文 2026-09-23 改 Markdown 预览）**：左列 pack 行只读、右侧 `文件` 标记、破损行标红；选中进 `packEditor`（只读），右上只有**「在 Finder 打开」+「重新读取」**两个动作（`重新读取` 读盘与会话内生效是两件事，见它的 `.help`）。 常驻区头计数 = **`pack.residentEntries.count`**（不是 `entries.count`）—— 区头标题是一个**断言**（「这几条是常驻的」），数字就必须是该断言的成员数；用行数会让「常驻 · 4」与载荷条「每轮都带上 3 条」并排打架，而两个数各自都对、却要解释才圆得上 ⇒ 那就是缺陷。
- **正文 = `MarkdownView`，不是 `Text`**（2026-09-23 boss："不支持修改, 直接改成 markdown 预览, 显示效果更好"）。同一个改动顺手治了 `查看本次注入` 的平方级卡顿 —— 两份预览共用同一条性能红线，见 §4.2 A 块。

编辑器里只留**一行**元信息（`packFactsRow`），留的两条判据是**"别处看不见、且真能影响决策"**：

1. **`layer` 标签** —— pack 侧唯一的注入旋钮。编辑器里没有层选择器，左列分组头又会随滚动离开视野 ⇒ 不在这儿标就无处可查。
2. **key 持有数** —— `keys` 是可执行契约（被锁的 key 之后在 DB 条目里不能再用，守卫 3 / 9）。折成个数 + hover 展开清单：信息不减而视觉不吵。

**原来那排 chips（`persona` / 文件名 / 层 / `priority N` / 逐条 `key xxx`）已删**（2026-09-22 boss：「这玩意没必要显示吧，越看越迷糊」）。删的判据不是"少显示点"，而是**每一条都有更该在的地方**：类型标记与文件名在左列副标已有（文件名还在标题行）；`priority` 只决定 persona 段**内**的先后，而该段**永不参与降级**、App 内也改不了文件顺序 ⇒ 编辑器里读了也做不出任何决策。

**行文案：标题 + 副标（2026-09-23，boss 两次追问 + 一次实测反馈后定型）**：

- **标题 = 文件名 + 出厂文案**（`SOUL.md - 我是谁` / `RULES.md - 我必须怎么做` / `USER.md - 你是谁`），**不读文件内容**；表外文件只有文件名。出厂文案那半走 `L()`，中英切换时只换它。→ §3.2。
  - **为什么文件名必须回到标题里**（2026-09-23 boss 实测反馈："这样看太单薄了"）：这一行的作用是"认出这三份是什么"，而"哪一份"与"是什么"是同一个句子的两半；拆到两行去，眼睛得上下拼一次才读得懂。上一版是"标题只放出厂文案、文件名塞在副标里"，一行只有四个字，看着空。
- **副标 = `persona · <字数> 字`**（+ 破损 / 按需标记）。**字数取 `entry.content.count`（进 prompt 的那部分），不是整份文件的大小** —— 判据是"**能不能加得上**"：面板汇总那句"人格段 N 条 / M 字"就是各条 `content.count` 的和（冒烟守着这条恒等），若这里改用整份文件的字节数，三行相加就对不上上面那个 M —— 而**两个数说的都是字数**，对不上不是精度问题，是它们在说两件事。frontmatter 那几行本来就该被排除在"人格有多少"之外。
- **中间那一版是"回落链"**（`summary` → 正文首个 `#` → 文件名），当天落地又当天撤掉。撤它的判据不是"顺序排得不好"，而是**它建立在用户内容上**。留作纪律：**能由产品回答的问题，不要拿去问用户**。
- **整行文案收在 `PersonaRowText.subtitle(for:)`**（与固定表同一个类型），不在 `KnowledgeView` 的私有分支里 —— 后者冒烟够不着，那些规则就没人守（同 §5.6 纪律）。留作纪律：**一行文案的每一条判据，都要有一个够得着的落点。**
- **出厂文案必须是"每次取词"（2026-09-23 boss 实测：英文模式下标题后半句仍是中文）**：`titleTable` 写成 `static let` 会**冻结取词** —— `static let` 是懒加载的**一次性求值**，首次访问就把当时语言的译文冻在那儿，之后切语言不再跟随；而同一行的副标在函数体里取词、每次重算 ⇒ 呈现出"**一行里一半跟随、一半不跟随**"的怪相（截图里 `SOUL.md - 我是谁` 配着 `persona · 2380 chars`，正是这个不对称）。安全形态只有两种：**计算属性**（`static var x: T { L(…) }`）或**函数体局部变量**。
  - `CodexTheme` 里早就写过同款注释（"UI 可见文案一律用 `static var`"）却仍被违反 ⇒ **注释不是门禁**。已把它做成 `scan_wiring.py` 的第二条判据「**冻结取词**」（存储属性初始化式里出现 `L()`/`LK()` 即红），造反例实测两处都能抓到（含跨行实参那一处）。
  - 同批修掉 `MailProviderPreset` 的 5 个 `static let` 预设 —— 它们的 `authNote` 同样是 `L()` 的结果、同样冻结。⚠️ `all` 也必须跟着改成计算属性，否则它会把上面那几个实例在首次访问时**一起冻住**（这条"间接捕获"本判据抓不到，只能靠人看一层）。
- **`summary` 不再是契约**（§3.2）⇒ 编辑器元信息行的 tooltip 也从"教你怎么写标题"改成"说明标题哪来的"（`packFactsHelp`）。**没有可写的地方，就不该留一段教人怎么写。**

两个副产物决策：

- **破损文件不显示层** —— 它的 `layer` 是 `PersonaPack.load` 编造的缺省 `.always`（`parse` 在破损时提前 `return`，根本没读到 `layer`），而该文件实际不进 prompt。显示"每轮都带上"就是撒谎；破损块自己已把这件事说清了。
- **`read_when` 只对 `ondemand` 文件显示** —— 常驻文件的"什么时候读"就是"每轮"，再说一遍是噪声。它是文件里的**原文**（不走本地化，见 §4.2），所以只会以原语言出现（英文 pack 上会看见 `Every session start` 混在中文界面里 —— 这是既定行为，不是漏翻）。

**选中态是单一路径**：左列与编辑器共用 `enum Selection { none / item(UUID) / pack(String) / base(String) }`（替换原先两个独立选中态；`base` 是 P11.4b 加的挂载库信息面）。两个独立态能同时非空 ⇒ "编辑器显示 A、高亮在 B"，而这类 bug 不会有任何红灯。

**C · 行内两个新信号**
命中计数 `·3` / `—`；**`—` 的行整行降一档灰度**，悬浮才提示归档建议 —— **"删除依据"第一次进 UI**。
选中 / hover 沿用 P10.8b 刚统一的 `CodexTheme.selected` / `hover`，**不新造视觉语言**。

**命中语义分两类（评审折入，2026-09-22）**：

| kind | 记账点 | 记的是什么 |
|------|--------|-----------|
| `lesson` | **触发即命中**（`tool_call` 事件侧的 `input.path` / `command` 命中 trigger，或前瞻注入命中） | "教训被推到它面前"—— 诚实语义，不必等模型自己想起来去读 |
| 其余（`fact` 等） | 读取即命中（L1 被工具读取归因，靠"一条一文件"实现，§3.3） | "它真的被查过" |

**并加第三维：触发之后行为有没有变**（§5.2）。`hitCount` 只记"推到面前"的次数，**一个被触发但从未改变行为的教训，比一个从不触发的教训更该归档** —— 前者是噪音，后者只是休眠。UI 上表现 = 悬浮详情里两行（`触发 5 次 · 未改变行为 5 次`），归档建议**优先提名前者**。

**命中列在 P11.1 就留位显示（拍板 2026-09-21）**：P11.1 尚无记账（记账在 P11.3），所以该列**全部显示 `—`，且整列不做灰度降档**（降档是"真·从未命中"的语义，占位期不能借用）。`.help("命中统计将在启用后生效")` 说明，避免被当成 bug。**先留位的理由不是好看，是让"从没被用过"这个缺口可见** —— 那个缺口正是当前记忆只涨不缩的根因。

**D · 编辑器：只留"写什么" + 归属（2026-09-22 定稿；同日 P11.2c → P11.2d 两轮简化）**

> ⚠️ **P11.2d（最终形态）：编辑器 = `作用域（全局/项目） + 标题 + 正文 + 保存/删除`**，与 **P11 之前的老版本同形**。boss 原话：*"新增知识时, 这块也去掉, 就是最开始那个版本 —— 可以选择有无项目, 可以选择开启和关闭, 就够用了。"*
>
> - **`更多设置` 折叠区整块撤下**（`advancedSection` + `kindBlock` / `layerBlock` / `priorityBlock` + 折叠头现值摘要），连同三个 draft 副本一起删。撤下的**不是一个层级里的几个选项，而是那个层级本身** —— 它要渐进披露的三个旋钮，没有一个能在"用户建一条知识"时被合理地决定：`kind` 前 3 档已被 persona pack 接管（DB 里再建 = 两个真源打架）、`layer` 的另一档要等 P11.4 知识库档（目录即作用域）、`priority` 只在 L0 超限降级时才有意义而真实库里全为 0。**"先问人话再给选项"那套写法没错，错的是问了三个当时没有答案的问题。**
> - **缺省从此是产品行为**：`KnowledgeItem.layer` 的缺省改为 **`.always`**（新建即进 prompt）。理由与删 `trigger` 的判据同源 —— UI 不再问"进不进每轮 prompt"，若缺省落 `.ondemand`，用户新建的知识会**静默不进 prompt**（填了不生效，比没有更坏）。它同时对齐 P11 **之前**的老行为：那时存进 `knowledge_items` 的每一条都进 prompt。
>   - ⚠️ 与 `PersistenceStore.loadKnowledge` 的回落值 (`?? .ondemand`) **有意不同**：那一处回答的是**迁移**问题（升级前没有 `layer` 列的旧行怎么算），保持 P11.1 的决定不动 —— 迁移的默认值不该顺手把存量库的条目全推进 prompt。
> - **行开关（`开启 / 关闭`）就是"生效与否"的唯一入口**，位置不变（左列每行右侧，见 §4.2 B）。**没有往编辑器里再加一个** —— 同一个状态两个控件是双写；且编辑器里的开关语义含糊（立即生效还是保存后生效？）。要加回之前先回答这个。
> - **`withUpdated` 同步收窄**：只覆盖作用域 / 标题 / 正文，`kind` / `layer` / `priority` **保持原值**（与 P11.2c 撤下的 `key` / `trigger` / `counterfactual` 合成一条纪律：**撤下输入框 ≠ 清空数据**）。反例长什么样：一条 `kind=lesson` + `layer=always` 的老条目只因改了错别字就被重置成 `fact` + 默认层，而 `kind` 是**注入块的契约 token** —— 模型下一轮看到的标签都会被改掉。
> - **代价（诚实记）**：`layer` 从此不能从 UI 改，所以**存量按需条目无法在界面里提升为常驻**（只能删掉重建，或等 P11.4 知识库档承接按需那一侧）。真实库当时只有 2 条 `fact/ondemand` 条目，接受。
>
> 📜 **以下各条是过程记录（描述已撤下的折叠区，含三个旋钮的控件形态）**。其中**仍成立的三条**：① `priority` 的数值边界 `0...999` 与**写入路径归一化**（`priorityRange` 单一源头 —— 控件没了，这条纵深防御照旧）；② 层标签词表统一（左列分组头 / 载荷条仍共用同一份 key，`KnowledgeLayer.tag` 不进注入块）；③ persona 条目的只读编辑器位置（只给 `文件` + 去 Finder，不给可写控件）。保留全段是因为它记录了"当初为什么要折叠"与"折叠为什么仍然不够" —— 那个对比正是两轮简化的判据来源。

保留“无底框大字标题 + 白卡正文”的气质。**首屏只留 `作用域 + 标题 + 正文 + 保存`** —— 元数据（种类 / 层 / 排序 / 身份键）折进一行 `▸ 更多设置　<现值摘要>`，点开才出现。
- **为什么折叠**：原设计把三个并列段选 + 步进器 + 身份键全堆在正文之前，boss 实测反馈“第一次接触不知道该怎么用”。根因不是控件多，而是**三件不同性质的事（作用域 / 内容分类 / 是否进 prompt）用了同一种 pill 视觉并排**，且唯一必填的正文排在最下面、最弱 —— 主次颠倒。
- **设计不变量：折叠头右侧必须带现值摘要**（`更多设置　　每轮都带上 · 事实 · 全局`）。收起 ≠ 看不见：没有它，“省认知”会退化成“不知道自己存了什么”。
- 展开后**每个维度先问人话、再给选项、选中项配一行解释**：`这条知识是什么？` / `什么时候带上它？` / `排在前面的优先给` / `身份键（可选）`。理由：标签本身是**注入用的契约 token**（两字），不足以让第一次进来的人看懂；五类各配一句人话（`我是谁: 身份与说话方式` … `踩过的坑, 写清什么时候会踩`）。
- `优先级` 步进器**只在 `每轮都带上` 档可用**：按需条目不参与降级 ⇒ 对它调数字没有任何作用。灰掉 + 写明原因（禁用态必须自带“还差什么”），措辞由内部术语 `优先级` 改为 `排在前面的优先给`。
- **数值有边界，且只定义在一处（2026-09-22 补，boss 实测“这个优先给数值没上限啊”）**：合法区间 = **`0...999`**，单一源头 `KnowledgeItem.priorityRange`。三处都读它 —— ① 步进器 ± 到界即 `.disabled`、中间数字改**可编辑**（不再是只能 ±1 的只读文本）、尾部显示 `0–999`；② 可编辑字段的 `onChange` 钳制；③ **写入路径归一化**（`addKnowledge` / `updateKnowledge` 两个唯一入口都过 `clampedPriority(_:)`）。选 999 的理由：它是**相对排序键**，用不到 5 位数，但也不该小到让“排到最后”要靠反复点击。
  - **钳而不拒**：`priority` 是可归一化的排序键 —— “因为数字大了点就拒绝一次保存”比“钳到边界”更糟（同 `ScheduledView.timeField` 的整数域外钳制）。故 `clampedPriority(5000) == 999`，不报错、不弹提示。
  - **归一化写在写入路径、不靠 UI 控件兜底**：手改 DB / 将来的导入器不走这两个控件，控件钳制是纵深防御的外层，不是唯一防线。
- `key` 改为 `身份键（可选）` + 一行说明（`给别人格文件引用用, 一般不用填`）：`key` 是程序员词，且它本来就可选。
- 切换层时**当场显示**“每次都发给 agent · 当前常驻 1,240 字”（让代价在按下之前可见）。
- **词汇统一**：层标签 = `每轮都带上 / 需要时才查`，左列分组头、载荷条、段选**共用同一份词表 key**（一个概念只允许一个词）。注意 `KnowledgeLayer.tag` **只占“l10n key”这一用** —— 组装只写 `kind`，层标签**不进注入块**，所以它可以、也应该用用户自己的话；只有 `KnowledgeKind.tag` 兼作注入块的契约 token。
- **`key` 选择器**（§2.4 的 UI 落地）：下拉里 —— 可自由新建；**被 persona pack 占用的 key 显示为禁用项 + 副标「由 persona pack 持有 → 在 Finder 打开」**。**禁止而不提示 = 把用户关进一堵没写字的墙。**
- persona 条目的编辑器位置只放 **`文件` + 在 Finder 打开**，不给可写控件。
- `触发：` 行 —— **仅 `kind=lesson` 出现**（新能力的面）。
- `不适用：` 行 —— **仅 `kind=lesson` 出现且必填**（`counterfactual`，§3.1）：写清"什么情况下这条不适用"。**入库时不填就存不下去** —— 只有正例没有边界的教训会在第 N 次误用后变成负资产（§5.1）。
- 底部 `变更史`（最近 3 条）。

选中候选时给四个动作：`采纳 / 编辑后采纳 / 设为常驻 / 丢弃`，且**必须显示"它会进哪一层"** —— 采纳到常驻 = 改每轮 prompt，这个按钮要负责任。

### 4.3 五类 `kind` 与标签

| 中文标签 | 英文标签 | kind | 是什么 | 例子（取自真实记录） |
|------|------|--------|---------------------|------|
| **人格** | Persona | `persona` | 我是谁 · 态度与边界 | SOUL.md / RULES.md |
| **用户** | User | `user` | 用户是谁 · 怎么配合 | USER.md ·「称呼：老哥 / boss」 |
| **硬规** | Rule | `rule` | **常驻的硬约束，永远成立** | 「绝不往别人能看到的地方发半成品」 |
| **事实** | Fact | `fact` | **稳定事实**：环境 / 技术栈 / 项目结构 | 项目约定 · 服务地址 · 数据规模 |
| **教训** | Lesson | `lesson` | **从一次具体事故长出来的条件反射** | 「连接实例必须随配置失效」·「`grep -E` 静默返回空」 |

**`硬规 ≠ 教训`，不可合并**：硬规 = 永远成立 → 常驻注入；教训 = 特定场合才该想起 → 带 `trigger` **按事件回灌**，是「教训回路」（§5.1）的唯一落点，也是五类里**唯一带额外字段**的。合并即该能力无处可挂。

**标签用两字不用一字**（拍板 2026-09-21）：单字（人 / 主 / 规 / 实 / 训）五个里四个要靠解释才看得懂 ⇒ 那不是标签、是谜语。两字自解释，代价约 +8px 行首宽。判据：**标签看不懂 = 长在身上的疤。** 且这五个词对**任何** persona 都成立，不是私有分类。（**两字约束只管这五个 kind 标签**；层的 UI 措辞与展开后的解释行不受此限 —— §4.2 D。）

**中英双语（拍板 2026-09-21）** —— 走**现有 l10n 机制**，不新造：
- 中文侧 = 源码字面量（`"人格"` …，即 `developmentRegion` 源的形态）；英文侧写进 `scripts/l10n/en_values.py` 词表。
- 英文形态 = **首字母大写全词**（`Persona / User / Rule / Fact / Lesson`）。判据：**只读小标签跟 `Duration / Turns / Calls` 那一类**（首字母大写）；全大写留给"角色 / 状态标签"（`USER / ASSISTANT / TOOL`）与"可切换段选"（`MSG / TURN / DETAIL`）。kind chip 是**只读**的，所以不跟全大写。
- ⚠️ **这是 l10n 连带项，不是免费改动**：词表 **492 → 536 条**（P11.1 首轮 +29 → 520；2026-09-22 编辑器渐进披露再 **−8 废弃 / +20 新译** → 532，同日告警数据化 **+4** → **536**）。**后续实测：P11.2a 后 571 → P11.2c 后 555 → P11.2d 后 542 → P11.4a/b 后 576 → 当前 **589**（2026-09-23）**（两轮简化各带走一批 UI 文案，当前值以 `gen_strings.py --check` 的"词表条数"为准）⇒ ① `gen_strings.py --check` 对账 ② `scan_wiring.py --check` 接线判定（7 条 tag 字面量登进 `wiring_allow.txt` **F 组**，理由见下）③ `e2e_probe.py` 指纹 **都要跟**；README「词表 N 条」与「冒烟 N 项」两处数字同步改。**归入 P11.1 的验收，不是收尾时补的。**
  - **每轮简化必须同步清词表**：撤下的文案会原地变成"已废弃"词条（无害但不干净），且 `--check` 只报**条数**、不会替你去改 `en_values.py` → 流程是 `--check` 拿废弃清单 → 从 `en_values.py` 删 key → `--write` 落盘 → 再 `--check` 归零。**顺手把 README 的条数一起改** —— P11.2c 漏了这一步，P11.2d 才发现 README 还写着 571。
- ⚠️ **tag 字面量是“疑似未接线”的真阳性，但必须豁免**：两个 `tag` 都返回中文原文且**不调 `L()`** —— `KnowledgeKind.tag` 是**注入块的契约 token**（若在此处 `L()`，用户切换界面语言会改掉注入进 prompt 的字节 → 破守卫 12 + 让 agent 行为被界面语言决定）；`KnowledgeLayer.tag` 不进注入块，但同属“中文原文当 key”的形态。故扫描器会报 **7 处** `RETURN` 可疑，需登记豁免（**不是漏译**，删豁免 = 扫描器再也拦不住有人改回 `L()`）。

## 五、能力扩展（按值钱排，不按好实现排）

### 5.1 教训回路（`lesson` + `trigger`）—— **最值钱**

现在只能存"事实"，存不下 **"什么情况下该想起这条"**。扩展为：`kind=lesson` 带 `trigger`（文件 glob / 命令前缀），**改到该文件时把那条坑回灌给它**。

`--append-system-prompt` 是**常驻**，这是**按事件**。**这条只有自己的躯干做得到**：WorkBuddy 不知道"我在动哪个文件"，MangoX 知道（工具调用 / 文件触达 / 审批流全是现成的事件面）。

**回灌走两条通道（§2.6 仲裁）**：项目级 trigger → 回合边界前瞻注入；文件 / 命令级 trigger → 扩展层教训门。

**入库强制 `counterfactual`（评审折入，2026-09-22）—— 这是社会学护栏，不是内容洁癖**：上线后这套 memory 的**主要写手是 agent 自己**（蒸馏候选由它提炼、教训由它踩出来）。而**事故是有选择的**：踩过坑的记得牢，没踩过的永远不写 ⇒ 教训库会系统性偏向"我踩过的坑清单"，而不是"这个项目的全貌"。更糟的是教训会**自我强化** —— 一条「`grep -E` 静默返回空」会让 agent 在后续所有会话里倾向绕开 grep，于是再踩不到新坑、教训库冻结。
两个对侧动作：① **每条 lesson 必填"何时不适用"**（如上面那条的反面 = "在非本机 shell 的 CI 里不存在此坑"）；② **命中信号带"触发后是否改变行为"维度**（§5.2）。

### 5.2 命中信号（两类记账点 + 一个行为维度）—— **第二值钱**

全量注入导致**没人知道哪条被真用过** ⇒ 没有删除依据 ⇒ 记忆只涨不缩。改走"取用"后，记账点按 kind 分两类（§4.2 C）：**lesson = 触发即命中**，**其余 = 读取即命中**（依赖"一条一文件"，§3.3）。长期 0 命中的条目获得归档依据。
**这是 knowledge 从"资料柜"变成"记忆"的分水岭：从"注入"转向"取用"。**

**第三维：触发之后行为有没有变（评审折入，2026-09-22）** —— `hitCount` 只说明"推到了它面前"。再记一个"拦下后是否重试 / 重试是否改了参数 / 教训门拦了之后同类调用是否消失"。归档建议的排序据此改为：**"触发多但从未改变行为" > "从未触发"** —— 前者是噪音，后者只是休眠（可能是当前项目还没碰过那块）。
⚠️ 这一维在 lesson 教训门通道上**自然可测**（拦截与重试都在事件流里），在前瞻注入通道上**弱得多**（注入了但无法证明被采纳）⇒ 这是教训门除了"打断"之外的第二个存在理由。

### 5.3 敏感分层 + 本地兜底 —— **已于 P11.2c 下线（2026-09-22）**

> ⚠️ **这一维已经删掉了。** 本节保留原貌 + 一条下线判词 —— "为什么当初要它"与"为什么后来删掉"都值得留下。

**下线判词（可证等价，不是口味）**：`sensitivity == .local` 与 `layer == .ondemand` **逐位同效**。
判据 `isResident = layer == .always && sensitivity == .normal` ⇒ 两者都不进 prompt、都落 L1、都计入"需要时才查"的计数；唯一差别只是 L1 文件 frontmatter 里那一行 `sensitivity:`，而读得到那个文件的 agent **本来就已经把正文读到手了** ⇒ 零行为后果。**两个开关做同一件事**，而 UI 上它们还隔着一个 `priority` 块 —— 用户得同时理解两个概念才能预测"这条到底进不进 prompt"。表达能力一条没少（判据统一收敛到 `isResident`）；字段与 DB 列保留（可回滚），UI 与写入链路全部撤下。

**下线时的实测**（真实库 `~/.mangox/mangox.db`，共 3 条）：`sensitivity` **零使用**（0/3）、`key` 零使用、`priority` 全为 0、`kind` 只用到 `fact` / `lesson`。**7 个旋钮里用户实际只用到 2 个** —— 这是"设计过于复杂"的硬证据，也是 P11.2c 的起因。

**后续（P11.2d，同日）**：把剩下的 3 个旋钮也一并撤下 —— 编辑器的元数据旋钮**归零**，只剩 `作用域` 与行上的 `开启/关闭`。判据见 §4.2 D：那三个旋钮在"用户建一条知识"时**都没有可用的答案**（种类前 3 档已被 persona pack 接管 / 层的另一档要等 P11.4 知识库档 / 排序只在超限降级时才有意义而真实库全为 0）。**"用户实际只用 2 个"是个信号，但真正的判据是"这一个能不能被合理地决定"** —— 前者只是提示我们去查后者。

#### 以下为下线前的原文（保留作过程记录）

`sensitivity=local` 的条目**永不进 prompt**，只落 L1 由 agent 按需读。收益不止隐私：**L0 变小 = 常驻预算省下来 = 能多放真正每轮要成立的规则**。三条互相成全（5.1 / 5.2 / 5.3）。

**P11.2a 补齐（2026-09-22）**：编辑器此前**没有** sensitivity 控件 —— `sensitivity` 在整个写入链路上是**只读的**，域层 `KnowledgeItem.withUpdated(...)` 把它**静默丢弃**过（`withUpdated` 收下了参数却没写回 `copy`）。两处都补上：① `withUpdated` 回写 `copy.sensitivity`；② 编辑器加 `CodexSegmented(options: [LK("可以进 prompt"), LK("只准本地读")])`，`更多设置` 收起态的现值摘要里 `local` 时必须前置 `仅本地`（否则"收起来看不见"= 用户永远不知道自己这条不是常识可用）。
**为什么这不是小事**：一个 `local` 条目在旧的 `layer` 口径下会**从两个分组里同时消失**（§4.2 B），再叠加"编辑器改不了"，用户就只剩"删掉重建"一条路。

### 5.4 人格的生长史（revision）

`knowledge_revisions` + `kind=persona` 的变更记录 ⇒ 能回答"我在哪天学会了什么"。真用途不是花活：**它是记忆压缩的验收器** —— 哪条被剪了、为什么剪。现有压缩流程用 `grep -o` 精确串基线做零丢失比对，那套流程要落地，先得有这个史。

### 5.5 跨宿主互认

persona pack 是标准 frontmatter 的 md ⇒ 任意宿主（WorkBuddy / MangoX / Mangopi CLI）都能读同一份。**但必须钉死主权**（§2.4 / §8.1 Q2b），否则两边同时改必然漂移。

**评审给出的语义（折入，2026-09-22）：persona pack 迁移的是先验（prior），不是连续性（continuity）。** 人格在推理侧的成立依赖"文本 + 宿主行为模式"的耦合 —— 记忆注入节奏、工具面、交互历史都会参与塑形。同一份 `SOUL.md` 搬到另一个宿主，表现是**相似但不同**的 agent。这在认知上更像"**同卵双胞胎共享先验、各自成长**"，而不是"同一个人换了身体"，也不是"一份复印件"。
⇒ 工程推论：**连续性不必靠"同一性"担保，可以靠共享的 revision 历史 + `key` 体系维护**（各自演化，汇流时能看清"分叉以来各学了什么"），见 §8.1 Q2b 的第三选项。

⚠️ **"这是同一个 agent"还是"它的副本"，是产品决定，不是技术问题** —— 待用户定。曾为此在 pack frontmatter 里留 `shared` 字段位，**P11.2c 已删** —— 留位期内它**零消费**（无逻辑读、无界面显示、无夹具之外的写入），是典型的预付；真要同步时按那时的需求重新设计。

### 5.6 启动自检

组装注入块时校验：① L0 条目一条不缺 ② 同 `key` 无冲突（含 **pack `keys` 事后扩张**撞库，§8.2 风险 5③）③ 无超预算静默丢弃（降级必须留痕）④ persona frontmatter 合法且 `keys` 可解析 ⑤ **persona 段确实在偏移 0**（§3.2 结构性不变量）**⑥ 索引段无静默丢弃**（P11.4：每个"挂了、启用、非空"的库必须落在"块内"或"缺席点名单"之一）**⑦ 段序**（P11.4：persona < 稳定段 < 索引段 < 易变段，比偏移）**⑧ persona 段非空**（2026-09-23 补，P11.2a 留的洞：`guard !entries.isEmpty else { return "" }` 直接返回空串，而守卫 ⑤ 在段为空时**短路成 false** ⇒ 三份 md 全删掉，⑦ 条守卫**仍全绿**）—— 任一不过 **UI 红一条**，不静默降级。
这是把"**先造能红的门，再动手**"用在记忆上，而且**可测：冒烟就能断言**。

**实现纪律（P11.2a 定下，2026-09-22）**：

- **自检判据 = 在拼好的块里查字符串**（`block.contains(line(item))`），**不是**复用"应该进了"的集合算术。②④两句的判定输入本来就与拼装同源（②读包/DB 的 key 集合、④读 `parse` 的三态），复用等于让被检查的东西自己出题。**实测**：漏拼一条稳定段时，`降级 + 易变 + 稳定 == 全部常驻` 这条计数恒等式**仍然成立** —— 恒等式拦不住静默丢弃，只有字符串查找能。
- **自检只报真问题，不报"一切正常"**：每条告警都有对应的"通过时不抛红条"反向断言，否则"永远红着"和"永远绿着"看起来一样。
- **告警一律指名道姓**：「pack 坏了」不可行动，「修 `broken.md`」才可行动 —— 三个新告警（`stableSegmentMissing(titles:)` / `silentlyDropped(titles:)` / `personaFrontmatterBroken(files:)`）全部带具体条目名。
- **告警是数据、不是文案**：`KnowledgeWarning` 只出枚举 + 载荷，文案在 View 侧拼（`warningLines`）—— 与本文件进 `gen_strings.EXCLUDE_FILES` 的理由同源（见该名单注释）。
- **段边界必须显式暴露**：`KnowledgeInjection` 出 `personaText` / `bodyText` / `personaCount` / `personaChars`，消费方（冒烟、UI）**一律读字段，不按行号数**。实测踩过：T-KNOW 的 `stableSegment` helper 原本从 `text` 里按行切稳定段，persona 段成为首段后它**静默切到了错的段**（门还绿着）。
- **⑥⑦ 的判据与 ①③ 同源（P11.4a）**：⑥ 靠"在块里搜 `[知识库] <目录名>`"，⑦ 靠"在拼好的整块里比各段首字节的偏移"。**都不能复用组装顺序** —— 组装顺序写错时"按组装顺序读"当然是对的，造反例永远不会红。实测（§6.4）：把索引段挪到易变段之后，⑦ 的两条断言（手工偏移 + 自检字段）同时变红，而其余全绿。

- **⑧ 的判据读产物、不读输入（2026-09-23）**：空 pack 的判定用 `out.personaText.isEmpty`，**不是** `pack.residentEntries.isEmpty` —— 后者是"输入的集合算术"，组装哪天把这一整段拼丢了它照样说"有 3 个常驻条目"。与 ①③ 同一条纪律（但比它们更弱一点：它不查块内字符串，只查段本身空不空 —— 因为它要报的正是"段不成形"）。配套两条抑制由 §3.2 定：破损 / 全按需 / 读不出来各有更准的告警，空 pack 那条让位。

### 5.7 决策后钩子（**只留位**，评审折入）

教训回路只定义了"入库 → 回灌"，没定义**教训产生的时点**。最锋利的产生时刻是 **决策后**：工具调用刚报错、或用户刚明确否定上一动作的那一刻 —— 上下文最完整、蒸馏原料最好（"刚才那次为什么失败"是当场可读的，隔一轮就只剩摘要）。

**P11.3 只留占位，不做实现**：工具错误返回 / 用户否定 → 触发一次**轻量蒸馏提议**（"要不要把刚才这次失败存成教训？"），带预填的 `trigger` / `counterfactual` 草案，人点一下才入库。
**只提议不自动** —— 与项目既有纪律一致（业务语义只出带 TODO 的脚手架），也避开 §5.1 的自我强化陷阱（自动入库 = 让偏见无人工闸门）。

**P11.2a —— 造机制 + 夹具验证（本轮，2026-09-22 已完成）**

**做什么**：persona pack 只读导入（`PersonaPack` 单一解析器）· **persona 段在组装器里成为独立首段（结构性不变量，§3.2）** · L1 落点写盘（`~/.mangox/agent/memory/` 与 `<项目>/.mangox/agent/`，**一条一文件、文件名 = key**，§3.3）· 组装自检（§5.6）· 编辑器元数据行 + `文件` 只读标记（D/B 块）+ sensitivity 控件（§5.3 补齐；**该控件已于 P11.2c 撤下**）。

**范围红线（boss 明确要求）**：**这一半不是真迁移，是测试与验证。**

- **不碰 `~/.mangox/agent/`**，也不碰任何用户项目目录 —— 测试路径全部靠 `personaPackDirOverride` / `l1RootOverride` 重定向到临时目录。真实改写 / 搬家属 P11.2b。

  - **2026-09-23 补**：这条**一字未改**（组装照旧、任务照旧执行），补的是**可见性** —— 空 pack 现在**会响**（`personaPackEmpty` 告警 + 常驻区头不判空 + 空态文案改口径，见 §3.2 / §5.6 ⑧）。**可见性 ≠ 阻断**。

**怎么验（已完成）**：
1. 守卫 5 / 10 / 15 各写夹具断言（§七）；
2. **每条守卫自己先造反例证伪一次** —— 实测分两组：①personaText 挪到末尾 / ②漏拼稳定段 / ③L1 文件名恒用 id ⇒ 守卫 10 / 超预算截尾 / 组装自检 / 守卫 15 文件名**各自变红**，其余全绿；④静默丢弃 ⇒ 自检①③ + 两条"抛红条"断言变红，自检⑤ 仍绿 —— **诊断性精确**。
3. 反例带出两个真结论（已写进代码注释）：**复合断言的红不具诊断性**（`A && B && C` 红了不知道是谁）⇒ 拆成独立断言；**计数恒等式拦不住静默丢弃**（漏拼一条稳定段时 `降级 + 易变 + 稳定 == 常驻` 仍成立）⇒ 自检必须在拼好的块里**查字符串**，不能复用"应该进了"的集合算术。

**从 a 里抓到的两个门缺陷（已按"改门不改症状"修）**：
- **纯 ASCII 的 key 三道门全看不见** —— 旧判据是"字面量含汉字"，于是 `L("priority %lld")` / `L("Inbox「%@」: %@")` 词表不收（英文界面静默回落中文）、接线门不判、指纹不遍历。判据改为 **"调用了查表函数 = 作者声明它是文案"**（`source_keys()` 路径 ①）。

**实测（2026-09-22）**：词表 **536 → 571**（新增 30 条 P11.2a 文案 + 7 条门修复显形的旧漏译，减 2 条废弃）· 接线 **0 可疑** · 指纹 **592 PASS** · 冒烟 **643 PASS / 0 FAIL**（新增 `T-PERSONA` 组 **42 条**；其中 5 条挂 `守卫 7/9/15` 前缀而非 `T-PERSONA`）· `xcodebuild` **BUILD SUCCEEDED**，warning **0**。

**门禁**：双门禁 + l10n 三道（新词表条属"断言"级）。

**P11.2b —— 真迁移 ✅（2026-09-23）/ 行为验收 ⬜**

**做什么**：把 `~/.workbuddy/` 的人设真源改写并落成 pack 文件，**逐条钉 `keys` 命名契约**（这一步不是格式转换：`keys` 是「DB 不得再用」的保留集合，写太宽会把用户可建的 key 全锁死，写太窄守卫 3 形同虚设）。

**落地结果（2026-09-23）—— 与设计有三处偏差，都记在这儿**：
1. **三份，不是四份**：`~/.mangox/agent/` 实为 `SOUL.md` / `RULES.md` / `USER.md`，**`IDENTITY.md` 已取消**（内容并进 `SOUL.md`）。

**怎么验**：
1. **行为性探针，不是自我描述探针（评审折入，2026-09-22）**：从 SOUL 的边界条款里挑一条**可测**的（如"拿不准是否对外动作 → 先问"），构造触发场景，断言**回合行为符合**。旧验收"新会话问'我是谁'能答对"**太弱** —— 问答正确不等于人格生效，人格的检验标准从来是行为；
2. **实测 L1 的"模型会不会去读"** —— 这是 §2.2 的未证推断，本阶段必须给出结论（但已从主路径降为兜底，不再是关键路径上的风险）；

**门禁**：双门禁 + 若引入新资源目录需核 `Resources` 入包。

### 6.2c / 6.2d —— 两轮纯减法（✅ 均已落地，2026-09-22）

**P11.2c —— 撤下无消费 / 重复的维度**（起因：boss 判「整个系统设计过于复杂」）。撤四项，每项各有判据、不是口味：`sensitivity`（**与 `layer` 可证等价**，逐位同效）· `trigger` + `counterfactual` 的输入口（**驱动逻辑在 P11.3 ⇒ 现在填了不生效，"填了不生效"比没有更坏**）· `key` 输入口（实现机制；**校验逻辑必须留**）· pack 的 `shared`（零消费的预付）。**编辑器 7 个旋钮 → 3 个**。

**P11.2d —— 撤销编辑器「更多设置」整块**（boss：「新增知识时这块也去掉, 就是最开始那个版本 —— 可以选择有无项目, 可以选择开启和关闭, 就够用了」）。编辑器回到 `作用域 + 标题 + 正文 + 保存/删除`，**与 P11 之前的老版本同形**。三个旋钮的输入口全撤 ⇒ 新建走模型缺省、编辑靠 `withUpdated` 保持原值。

**判据是「这三个在用户建一条知识时都没有可用的答案」，不是「用户用得少」** —— 后者只是提示去查它的信号。

**两条硬边界（本轮真正该守的东西）**：
1. **撤下输入框 ≠ 清空数据** —— `withUpdated` 只覆盖编辑器真能改的维，**其余一律保持原值**；否则编辑一条旧条目 = 静默丢数据（`kind` 还是**注入块契约 token**，丢了就破守卫 12）。**DB 列一律保留**（为可回滚）。
2. **缺省即产品行为** —— `layer` 缺省 = **`.always`**：UI 不再问「进不进 prompt」，少了这个缺省，新建的知识会**静默不进 prompt**。⚠️ 与迁移段对旧行的回落 `?? .ondemand` **有意不同** —— 一个答「新条目怎么建」，一个答「旧行怎么算」，注释互指，别「统一」掉。

**代价（诚实记）**：`layer` 不再能从 UI 改 ⇒ **存量「按需」条目无法在界面里提升为常驻**。

### 6.3 P11.3 回路（⏸ 冻结 —— 解冻条件见节末）

**做什么**：
- **回灌双通道（§2.6）**：项目级 trigger → `beginTurn` 回合边界前瞻注入；文件 / 命令级 trigger → **扩展层教训门**（`tool_call` 拦截，**不得带 `ctx.hasUI` 守卫**，与审批门分段）。

**怎么验**：
1. 改 `PersistenceStore.swift` → 对应 lesson 按通道出现（项目级走近前注入、文件级走教训门）；

4. 长期 0 命中 / 触发但未改变行为的条目给出归档建议（不自动删）；

**门禁**：双门禁（动事件面与落库列）。

4. **`read_when` 不驱动逻辑**：本期只消费 `layer`，避免引入第二套调度语义（两套语义 = 漂移源）。
5. **Q1「禁止冲突」带来的三个新面**（采纳"设计上不允许冲突"的代价，必须成对处理）：
   - ① **改 pack 里的一条必须去改文件** —— 门槛升高。缓解：被禁用的 `key` 旁写明原因 + 给"在 Finder 打开"与"复制到剪贴板"入口。**禁止而不指路 = 无字之墙。**
   - ② **pack 的 `keys` 解析失败 ⇒ 保留集合变空 ⇒ 撞 key 条目会被放行**（守卫被绕过，且是静默的）。缓解：**解析失败 = 组装自检红（§5.6），且保守禁止新建任何 `key`** —— 失败时收紧，不放松。守卫 9。
   - ③ **`keys` 事后扩张**（评审折入）：守卫 3 只管"写入时拒绝"。用户手改 pack 新增 key X、而 DB 里早有 key X ⇒ **写入时没撞，组装时撞了**。缓解：**组装时发现冲突 → 该 DB 条不注入（pack 唯一持有）+ 自检红条 + 指引"迁移该条目或从 pack 移除 key"**。守卫 13。这是守卫 3 的姊妹项，缺了它"设计上不允许冲突"在时间维度上就有洞。
6. **审批门在无 UI 会话里整体短路（评审实证，2026-09-22）**：`mangox-approval.ts:183` 的 `if (!ctx.hasUI) return undefined;` 意味着**邮箱哨兵 / cron / watch 路径下敏感工具（bash/write/edit）不经过审批**。P10.2 时代这是"能跑就行"的合理妥协，但在 P11 语境下暴露**倒置**：
   - **有人值守**：有人 + 审批卡兜底，教训是锦上添花；
   - **无人值守**：没有人兜底，**教训是唯一的防线** —— 而这正是教训门最容易"继承 `hasUI` 守卫、整体失效"的地方。
   ⇒ 纪律：**教训门不得复制 `ctx.hasUI` 守卫**（守卫 11），无人值守是它的第一优先级场景。
   ⇒ 遗留记账（**P10.2 范围，不是本篇**）：哨兵会话里审批门的预期行为（自动 Allow / 自动 Deny / 阻断任务）目前依赖 `hasUI` 的**隐式**短路，需显式定义。
7. **教训门与审批门复用语义的风险**：同一段 `tool_call` 拦截里，审批门的 block 要模型**停**、教训门的 block 要模型**继续**。将来任何"连续 N 次 block 就放弃"之类的保护，都可能在不知情下杀死教训传递 ⇒ 二者在扩展源里必须**分段且可单独断言**（守卫 11）。
8. **元认知盲区（GLM 提出，被用作降级理由）**：需要读 L1 的时刻，恰是 agent 意识不到自己缺信息的时刻；L0 里那句"不确定时去读"在长上下文下指令遵循会衰减。这正是"被动回灌（教训门）> 主动读取（L1）"的依据，也是 L1 降为兜底 + fact 专用的原因。**性质：判断，非实测**（§8.3）。
9. **被排除在词表外的文件里写 `L()` = 隐形漏译（2026-09-22 实测）**：`gen_strings.py` 的 `EXCLUDE_FILES` 为了"注入面文本必须恒中文"而整体跳过 `KnowledgeStore.swift`。于是该文件里 `L("…")` 的 key **永远进不了词表** ⇒ 英文界面静默回落中文；更糟的是**三道 l10n 门都看不见** —— 词表门跳过该文件（连"已废弃"都不报）、接线门只判"字面量是否落在汇聚点"（`L()` 本身就是汇聚点，形态完全正确）、指纹只遍历词表里的 key（这条不在表里）。**处置**：组装器只出**数据**（`KnowledgeStore.KnowledgeWarning`），文案一律在 View 侧拼；`EXCLUDE_FILES` 的每一项都必须写明"为什么排除 + 在里面写文案会怎样"。**性质：实测**（P11.1 的超限告警就这样坏了一个版本）。
10. **门的「判据」本身可以是错的 —— 与风险 9 同类，是第二条看不见的漏译通道（2026-09-22 实测，P11.2a 造反例时抓到）**：
    - **纯 ASCII 的 key 三道门全看不见**。`gen_strings.source_keys()` 的旧判据是"字面量含汉字"（一个为避开 `"PASS"` / 正则串而设的启发式），于是 `L("priority %lld")` / `L("Inbox「%@」: %@")` 这种**形如纯英文的 key** 被一并躲过：词表门不收（英文界面静默回落中文）、接线门只判含汉字字面量、指纹只遍历词表里的 key。**判据改为"调用了查表函数 = 作者声明它是文案"** —— 它读的是**作者意图**，比"含不含汉字"（字符集）可靠得多。
    - **裸 `code.split('//')[0]` 当注释剥离器**：字面量里的 `//` 被当成注释起点，`L("// 空文件")` 被切成未闭合残句 ⇒ 抽出来的是个空串，**5 条文案在词表门里静默失踪**，而词表对账显示 536/536 全绿。且 `scan_wiring.py` **自带一份正确的** `strip_line_comment`、`gen_strings.py` 用裸切分 —— **两份实现分叉**，同一行在两道门里被读成两个东西。
    - **共性（这才是要记的）**：风险的形状不是"某人漏翻译了一条"，而是"**门的判据错了 —— 于是漏了，而门自己绿着**"。这类缺陷**不会自己显形**，验证手段只有一种：**给判据造反例**（不是给代码造反例）—— 本轮的造法就是"故意写一条纯英文 key、一条 `//` 开头的 key，看门会不会红"，两条都**没红**，缺陷才暴露。
    - **处置**：① 判据从"字符集"改为"作者意图"；② 注释剥离器**收归全脚本唯一一份**（`strip_line_comment`，`scan_wiring` / `wire_strings` 共用）；③ 残留边界已在 `source_keys()` docstring 写明 —— **纯英文且没裹 `L()`** 的 UI 文案仍不可静态判定（任何英文字面量都可能是标识符），**不糊启发式**，靠"UI 文案一律走 `L()`"这条写法纪律兜底。

### 8.3 推断 vs 证据（诚实边界）

| 结论 | 性质 |
|------|------|
| 现有实现"越重要越先被丢" | **有证据**（读 `KnowledgeStore.swift:66-68` + 存量 2 条 `enabled=0`） |
| 静默丢弃导致边界规则丢失 | **有证据**（代码路径确定），但**无真实事故记录** |
| 「教训回路」比通用知识库更有价值 | **判断**，非实测 |
| L1「按需读」比全量注入更划算 | **推断**，待 **P11.2b** 实测（且已降为兜底，不在关键路径上）。**P11.2a 只验了"文件按 key 一对一落盘"，没验"模型会不会去读"** —— 后者是行为问题，夹具答不了 |
| 人格搬进 DB 会丢失"迁移"的意义 | **判断**（基于既有 SOUL/IDENTITY 的自我约定），非技术结论 |
| **审批门在无 UI 会话短路** | **有证据**（`mangox-approval.ts:183`）；但"哨兵会话里实际发生了什么"**无实测**（无日志取证）⇒ 需显式定义并加观测 |
| **教训门里 `reason` 不会被忽略** | **推断**（GLM 的"模型本体证词"，**利益相关方的自我报告**）—— 不能作为架构正确性的依据，因此教训门必须配"强制命中 + 行为改变"两条可观测兜底（§2.6 / §5.2） |
| **回合边界前瞻注入的覆盖度** | **推断** —— `beginTurn` 只知项目/cwd，临时决定碰计划外文件即漏；缓解 = trigger 从文件级放宽到项目级兜底，且**失败模式可观测**（教训没出现 vs 出现了被无视） |
| **KV cache 稳定段的收益** | **机制层面必然 + 收益无实测**（provider 侧命中率未验证）⇒ 不进任何阶段验收项（§2.2） |
| **`kind` 由客户端规则推断比模型判定准** | **判断**（依据：模型看不到跨会话语义）；可在 P11.3 用蒸馏历史回溯验证 |
| **教训的"行为改变"维度可测** | **在教训门通道上可测**（拦截与重试都在事件流里）；**在前瞻注入通道上弱**（注入了无法证明被采纳）—— 这是教训门的第二个存在理由 |
