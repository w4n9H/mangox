## 一、载体与注入模型

### 1.1 三个载体：按"有没有自己的生命周期"分档

| | **固定档** persona pack | **用户输入档** `knowledge_items` | **知识库档** `knowledge_bases` |
|---|---|---|---|
| 装什么 | 我是谁 · 用户是谁 · 纪律与边界（人格本体） | 事实 · 教训 · 项目约定 | 成套外部资料（项目文档 / 笔记 / 参考） |
| 形态 | 文件（一族 md，标准 frontmatter） | DB 表 | DB 表**只存「路径 + 描述」**，正文在磁盘 |
| 写入者 | 人（App **只读**展示 + 跳转编辑） | 人（面板 / 会话沉淀 → 审核） | 人挂目录 + 一句描述；内容归目录自己的主人 |
| 进 prompt | **全文**，结构性首段 | 进 L0，或落 L1 按需 | **只进索引**（描述 + 路径 + 文件清单），正文由 agent 按需 `read` |

判据 = **这份东西有没有自己的生命周期**。前两档由 App 管（DB / 预算 / 记账 / 格式约束）；知识库里的文件归它自己的目录管（可能是个 git 仓库、可能还在天天被改）⇒ App 只做两件事：**让 agent 知道它存在**（索引）、**告诉它去哪读**（绝对路径）。

这也解释了分档的必然性：**"每档该带什么"是档的固有属性，不是用户要选的** —— 固定档必然全文、知识库档必然按需，**只有用户输入档**才需要人决定"每轮还是按需"。复杂度不在"档有几个"，而在"把档的属性做成了开关"。

### 1.2 分层：L0 常驻 / L1 按需

- **L0 常驻**：每轮进 prompt（走 `--append-system-prompt`）。**预算不可挤占；超限 = 告警 + 按 `priority` 可预测降级，绝不静默丢弃**。
- **L1 按需**：**不进 prompt**，落成工作区文件，由引擎用内置工具（`read / grep / find / ls`）自己取。零协议成本 —— 不需要新 RPC，也不需要动 `--append-system-prompt`。

原则：**prompt 预算只花在"每轮都必须成立"的东西上；能按需读的就别常驻。**

**预算构成**：总量 `Tune.knowledgeTotalCharLimit = 64000` 字符；**先扣 persona 段与稳定段**（它们永不降级），余下才是易变段的额度；**单条正文上限 `Tune.knowledgeItemCharLimit = 16000`** —— 超出按字符**截断**（不是丢弃）。

**L0 内部四段：**

| 段 | 内容 | 变更频率 | 位置 | 降级待遇 |
|---|---|---|---|---|
| **persona 段** | persona pack 全文 | 一年几次 | **偏移 0，独立首段** | **永不降级、永不截尾**（守卫 10） |
| **稳定段** | DB 中 `kind ∈ {persona, user, rule}` 的条目 | 一年几次 | 紧跟 persona 段 | **永不参与降级**（守卫 2 的例外） |
| **索引段** | 知识库索引（每库：描述 + 路径 + 文件清单） | 挂 / 摘库时 | 稳定段之后、易变段之前 | **不参与 priority 降级；装不下 ⇒ 整段缺席 + 告警** |
| **易变段** | 其余 L0 条目（`kind=fact` 等） | 随时 | 最后 | 超限时按 `priority` 从低到高截尾 |

**段序的理由 = 前缀稳定性**：per-turn 架构每回合都 spawn，前缀逐字节稳定 ⇒ provider 侧 prompt cache 命中 ⇒ 人格注入的边际成本趋近于零；前缀一变则每次改动全量重算。索引段的变更频率介于稳定段（年级）与易变段（随时）之间 ⇒ 放在两者之间，同时保住"persona + 稳定段"这条最长稳定前缀。守卫 12：**易变段任何改动不得触碰稳定段字节**。

> ⚠️ 这是**机制层面的必然 + 收益无实测**（provider 侧命中率未验证）⇒ **不作为任何验收项**。

### 1.3 L0 超限的确切语义

旧契约"超限 = 报错"在**无人值守**路径上不成立：邮箱哨兵 / cron / watch 走同一套 spawn 组装（`ChatStore.swift:1352`），**注入块一样被拼进去，但那里没有屏幕**。

| 场景 | 行为 |
|---|---|
| 交互会话 | **红条 + 告警事件** + 按 `priority` 降级截尾（人看得见） |
| 无人值守 | **告警事件**（进日志 / 事件流）+ 同一套降级截尾；**不阻断 spawn** |

铁律：**记忆故障不具备打断任务执行的权力。** 报告对象是 UI / 日志 / 事件流，而注入行为本身**永远有定义良好的输出**。

**降级是「截尾」，不是「贪心填空」：**

| | 规则 | 反例症状 |
|---|---|---|
| ✅ **截尾** | 按 `priority` 降序摆，**一旦某条装不下，它与它之后的所有条目一律降级**；入块集合 = 排序的**前缀** | —— |
| ❌ 贪心填空 | 装不下就跳过它、继续试后面的小条目 | **priority 180 的大条目没进 prompt，priority 3 的小条目却进去了** ⇒ 规则不可预测 |

判据是"**可预测**"：§3.1 的红条必须能说清"降了哪几条"，前提就是降级集是**排序的尾巴**（冒烟用「3×16000 字吃满预算 + 一条装不下的 D + 一条很小但 priority 最低的 E」确定性构造，断言 **E 也不进**）。

### 1.4 四主权与 `key` 唯一定位

| 出口 | 作用域 | 写入者 | 形态 | 状态 |
|---|---|---|---|---|
| **persona pack** | 人格 · 用户 · 纪律（跨项目） | 人 | 文件 | 已落地 |
| **KnowledgeStore** | 人工策展的跨会话知识 / 记忆 | 人 + 提炼候选（审核） | DB | 已落地（P3.7） |
| **pi-memory**（P10.1e） | agent 自主沉淀的笔记 | agent | 文件（`PI_MEMORY_DIR`） | **未落地** |
| **交接文件**（P3.9） | 单个长期任务的动态状态 | agent 写、人可改 | 文件（`<项目>/.mangox/tasks/<taskId>.md`） | 已落地 |

四者冲突面不重叠：**人格 ≠ 自主笔记 ≠ 任务状态 ≠ 策展知识**。但 **persona pack 与 DB 里的 `人格/用户/硬规` 三类条目功能重叠，必须钉死**：

- **persona pack = 该 `key` 的唯一持有者**（人格本体的真源；删掉它，这个 agent 就不再是"它"）。
- **DB 不得持有 pack 已占用的 `key` —— 设计上不允许冲突存在**：写入 / 采纳时校验，撞了就**拒绝创建**，UI 引导「这条由 persona pack 持有，请去改文件」+ 给"在 Finder 打开"入口。
  - 好处是**不需要"谁赢"的规则，也就不存在静默失效**。
- **覆盖语义只在同一载体内部存在**（pack 内部可以有"上游写的 X 是错的，以本文件为准"这类表述）；**跨载体一律禁止冲突**。
- 由此 `key` **全局唯一**：`knowledge_items.key` 加 `UNIQUE`，且与 pack 解析出的 key 集合**对账**（守卫 3）。
- **UI 必须让"被占用的 key"可见**，否则用户会反复尝试创建同一条 —— **禁止而不提示 = 把用户关进一堵没写字的墙。**

## 二、数据模型

### 2.1 `knowledge_items`

| 列 | 类型 | 语义 | 缺省 |
|----|------|------|------|
| `kind` | text | `persona` / `user` / `rule` / `fact` / `lesson`（§3.6） | `fact` |
| `layer` | text | `always`（L0 常驻）/ `ondemand`（L1 按需） | `ondemand`（迁移）/ **`.always`（新建）** |
| `priority` | int | **L0 内排序与超限降级的唯一依据**；越大越靠前；合法区间 **`0...999`**（单一定义在 `KnowledgeItem.priorityRange`，越界走 `clampedPriority(_:)` **钳而不拒**） | 0 |
| `key` | text NULL | **全局唯一**的条目身份键；pack 已占用的 key **禁止出现在 DB**（§1.4）；NULL = 不参与配对 | NULL |
| `trigger` | text NULL | **仅 `kind=lesson`**：文件 glob / 命令前缀，驱动按事件回灌 | NULL |
| `counterfactual` | text NULL | **仅 `kind=lesson`**：**"什么情况下这条不适用"**（入库强制填）—— 只有正例没有边界的教训库，会在第 N 次误用后变成负资产 | NULL |
| `sensitivity` | text | **已停用**：列留在 schema 里、代码不再读写（`sensitivity == .local` 与 `layer == .ondemand` 可证等价） | `normal` |
| `hitCount` / `lastHitAt` | int / real | 命中信号（记账在 P11.3，现在恒 `—`）。**lesson = 触发即命中**；其余 = 读取即命中 | 0 / NULL |

**两条不能合并的硬规则：**

1. **`layer` 的缺省是产品行为** —— `KnowledgeItem.layer` 缺省 = **`.always`**：UI 不再问"进不进 prompt"，缺省落 `.ondemand` 会让新建的知识**静默不进 prompt**。
   - ⚠️ 与 `PersistenceStore.loadKnowledge` 的迁移回落值 **`?? .ondemand` 有意不同**：那里回答的是"升级前没有 `layer` 列的旧行怎么算"，**迁移的默认值不该顺手把存量库的条目全推进 prompt**。两处注释互指，**别"统一"掉**。
2. **列只增不删** —— 唯一零引用列 `sensitivity` 也**不删**：项目已发版（11 个 tag）⇒ 旧版本代码里有 `SELECT sensitivity`，DROP 之后**旧 App 打开新库即崩**，而只有「新库 + 旧 App」这一组合会炸、**最容易被漏测**。`trigger` / `counterfactual` / `hitCount` / `lastHitAt` 引用少**不是因为没人要，而是因为消费点还没写**（记账在 P11.3）。
   - 判据：**"零引用"是硬事实，"有引用 ≠ 有消费者"**。体检脚本 `scripts/diag/db_column_audit.py`（**只排嫌疑、不定论** —— 单文件内读取的列会看起来像零引用，例如 fork 用 `fork_source_file` 重建会话）。

**迁移**：纯增列 + 缺省值 ⇒ 存量条目自动落为 `fact / ondemand`，**无需数据迁移脚本**。

**不新增表**：`revision`（变更史）用 `knowledge_items` 旁的轻表 `knowledge_revisions(item_id, at, actor, reason, before, after)` —— 只写不读，UI 取最近 3 条。

### 2.2 persona pack 文件约定

- **目录**：`~/.mangox/agent/`（跨宿主镜像位仍未定，§七风险）。
- **文件**：`SOUL.md` / `RULES.md` / `USER.md`，**三份全部常驻**。`IDENTITY.md` 已取消（内容并进 `SOUL.md`）。
- **`PROJECTS.md` 已移出 pack**：它原是唯一一份 `layer: ondemand` 的文件，现搬到 `~/.mangox/kb/projects/` 挂成知识库。⇒ 当前 pack 内无"按需"文件，**`layer: ondemand` 成为保留语义、暂无载体**（仍可写，写了仍只展示不注入）。
- **App 只读**：不提供 persona 编辑器，只提供"查看 + 在 Finder 打开"。**双写必漂移。**

**标准 frontmatter（全部字段皆可省）：**

```yaml
---
read_when:
  - Every session start
  - 不确定该用什么态度时
priority: 10        # 越大越靠前；L0 稳定段内的排序依据
layer: always        # always | ondemand
keys:                # 本文件持有的条目 key —— DB 不得再用（§1.4）
  - agent.name
  - user.call_name
---
```

- **`read_when` 不驱动任何逻辑** —— 它是给人读的说明，真开关是 `layer`。且它是文件里的**原文、不走本地化**（同一份文件要能被任意宿主读）。
- **`keys` 是"设计上不允许冲突"的实现支点**：组装器解析全部 pack 文件的 `keys` 得到**保留集合**，DB 侧写入 / 采纳校验它（守卫 3）。**解析失败 = 组装自检红**（守卫 9：失败时收紧，不放松）。

**行标题 = 文件名 + App 出厂固定文案，不读文件内容**：

| 文件 | 行标题 |
|---|---|
| `SOUL.md` | `SOUL.md - 我是谁` |
| `RULES.md` | `RULES.md - 我必须怎么做` |
| `USER.md` | `USER.md - 你是谁` |
| 表外文件 | 只有文件名（**不留 ` - ` 后缀** —— 没有后半句却留个破折号，看着像被截断了） |

- **判据**：标题是**产品概念**（"这三份分别是什么"），不是**文件属性**（"这个文件里写了什么"）⇒ 该由 App 回答，不该拿去问用户。**能由产品回答的问题，不要拿去问用户。**
- 大小写不敏感（`soul.md` 算同一份），显示**文件真实拼写**。出厂文案那半走 `L()`，中英切换时只换它；**必须是"每次取词"**（计算属性或函数体局部变量，`static let` 会**冻结取词** ⇒ 出现"同一行里一半跟随语言、一半不跟随"）。
- **副标 = `persona · <字数> 字`**（+ 破损 / 按需标记）。**字数取 `entry.content.count`（进 prompt 的那部分），不是整份文件的大小** —— 载荷条汇总那句"人格段 N 条 / M 字"就是各条 `content.count` 的和，用整份文件字节数三行相加就对不上。
- **代价（诚实记）**：标题**不可由用户自定义**，没有可写的地方。
- **文案住 View 层**（`Views/Knowledge/PersonaRowText.swift`）：它是用户可见文案 —— 要进词表、要中英各自正确；模型层只出数据（**判据：文案归 View，数据归模型**）。

**`layer` 与破损的边界语义：**

- **缺省 `layer` = `always`**：丢进 `~/.mangox/agent/` 的文件就是人格本体。若缺省是 `ondemand`，一个忘写 frontmatter 的文件会**静默地完全不生效** —— 而那是人格，静默失效的代价最大。**缺省取"更响亮"的那一侧。**
- **`layer: ondemand` = 长期护栏，不是过渡态**：遇到它**照旧不进 prompt**，但在组装自检里**点名告警**"该文件属于按需资料，请迁到知识库档"。
  - 为什么不直接当 `always`：那会让一个原本不注入的文件**突然整篇挤进 persona 段**（prompt 当场变大，人格段被掺进非人格内容）。
  - 为什么不静默忽略：它会**隐形**（既不进 prompt 也不进索引），正是 P11 要根除的那类缺陷。
- **破损 ⇒ 不注入、不做乐观假设**：frontmatter 开头的 `---` 没收尾时连 `layer` 都读不出来 ⇒ 这种文件**不进 prompt**（而不是"按缺省 `always` 塞进去"），且**保守禁止新建任何带 `key` 的条目**（守卫 9）。但它**仍在左列可见**（红标记 + 文件名）—— 用户得先知道哪个文件坏了，才修得动。
- **空 pack（persona 段为空）⇒ 必须响，但照旧不阻断**：
  - **判据**：**挑不出任何可载入的条目**。刻意**不是**"少了几份" —— 用户可故意只留一份。
  - **两个原因分开报**：`dirMissing`（目录不在）与 `noFiles`（目录在、里面没有可载入的 `.md`）—— 两者的用户动作不同（去建目录 / 去放文件），而"下一步做什么"是告警唯一的用处。
  - **不重复报**：破损 / 全按需 / 读不出来的三种情形**各有更准的告警**，空 pack 那条让位。**同一件事挨两枪 = 红条变噪音，用户开始无视红条，那比不报还坏。**
  - **措辞只报事实**（"本轮 prompt 里没有「我」"），**不写"被删了"** —— 文件系统上"从未有过"与"刚被删掉"是同一个状态，要分辨就得额外存一份会过期的持久态。判据宁可选**可判定**，不选**能分辨**。
  - **面板侧配套**：常驻区头**不判空**（恢复入口住在这一段里，藏起来的入口 = 没有入口）；区头「文件夹」按钮在目录不在时**就地建目录**（建的是**位置**不是正文，不违"App 只读"）。
- **persona 段是结构性首位，不是"priority 碰巧排前"**：组装器的输出结构里，**persona 段 = 独立第一段**，不参与 L0 条目的 `priority` 排序、也不参与超限截尾。理由：`fact` 是可丢的知识，`persona` 是"我"，**两者失败代价不在一个数量级** ⇒ 不能用同一个可手滑改掉的数字参数来担保。**把"我是谁"从数据升格为不变量。**
- **全项目单一 frontmatter 解析器**：`PersonaPack.parse` 是唯一实现，`KnowledgeStore.parseFrontmatterKeys` 退化为它的薄包装。两份实现迟早对同一个文件给出不同判定 —— 一份说破损、一份说没事，守卫 9 就漏了。

### 2.3 L1 落点与命名

| 作用域 | 落点 |
|--------|------|
| 跨项目 | `~/.mangox/agent/memory/` |
| 项目内 | `<项目>/.mangox/agent/`（建议 gitignore `.mangox/`） |

命名**不占** `AGENTS.md` / `CLAUDE.md` / `.pi/`（防 pi 自动加载误捕、防与人类约定文件名冲突）。

- **落盘粒度 = 一条一文件，文件名 = `key`**（`key` 为 NULL 的按 `item_id` 生成稳定文件名）。这是**归因的硬要求**，不是审美 —— 若多条合并落盘，`read` 了一个文件无法归因到单条，`hitCount` 就记不了账。顺带让 DB 撞 key 校验多一个天然对账面。
- **落 L1 的判据 = 同一个"不进 prompt"**（即 `!isResident`）：分组必须是**真划分**，且必须与"进不进 prompt"**共用唯一判据**。
- **路径断言 `isAllowedL1Path`（守卫 7）挡两侧**：① **目录侧** —— 不占 `.pi/`；② **文件名侧** —— `key` 可能就叫 `AGENTS.md`，而 `l1FileName(for:)` 是 `key + ".md"`，于是会写出一个 **pi 自动加载**的文件（绕过整个 L0/L1 分层）。实测净化结果 `k-AGENTS.md.md`；同时挡路径穿越（`..` / `\` / `:` / `\0`）。
  - **净化对正常 key 是恒等变换**（`note.alpha` → `note.alpha.md`）：只有畸形 key 才看得到 `k-` 前缀，诱饵不在。
- **落盘是"全量对账"，不是"只写不删"**：写应存在者 + 删**带 `mangox_item:` 标记**但已不该存在者。**无标记的外部文件一律不动**。只写不删 = "记忆只涨不缩"换个地方复发。
- **磁盘为准**：每次组装现读文件，不落缓存 —— 用户任何方式改文件，下轮即生效。
- **重定向钩子**（`l1RootOverride` / `personaPackDirOverride`）只服务测试。

### 2.4 知识库档

**一级实体 = 一条"挂载记录"**：`{ 目录路径, 描述（必填）, 启用 }`。

**描述为什么必填**：索引里只有文件名的话，agent 拿到的是一**串字符串**，它没法判断该不该去读 —— 一手文件名 `2024Q3-复盘.md` 说明不了这是财务还是技术。一句描述把"这是什么的资料"先给它，再给清单，**这才是卡片目录（分类说明 + 架位）的形态**。上限 **200 字符**（它是"一句话"，不是摘要）。

```sql
CREATE TABLE IF NOT EXISTS knowledge_bases (
  id          TEXT PRIMARY KEY,
  path        TEXT NOT NULL,              -- 目录绝对路径（存展开 ~ 之后、标准化的形态）
  description TEXT NOT NULL,              -- 必填，≤200 字符
  enabled     INTEGER NOT NULL DEFAULT 1,
  created_at  REAL NOT NULL,
  updated_at  REAL NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS idx_kb_path ON knowledge_bases(path);
```

- **幂等建表**，老库升上来是**空列表** ⇒ 无需迁移脚本。
- **`UNIQUE(path)`**：同一目录挂两次 = 索引里同一份资料出现两遍，纯浪费预算 ⇒ 在建 / 改两处都**拒绝创建**（不是"谁赢"）。
- **不做 `scope`（全局/项目）**：**目录路径本身就是作用域的天然表达**（`~/Documents/notes` 是全局资料，`<项目>/docs` 是项目资料）。多加一个旋钮就会出现"这个库是项目的但它在我家目录里"这种自相矛盾的配置 ⇒ 等真出现需要时再加。**字段不是越全越好，是"用户能不能合理地决定它"。**

**扫描契约（固定参数，不给旋钮）：**

| 项 | 取值 | 判据 |
|---|---|---|
| 扩展名白名单 | `.md` / `.txt` / `.html` / `.htm`（大小写不敏感） | 仅读文档格式；`.htm` 与 `.html` 是同一种格式的两种后缀，一起收 |
| 递归深度 | **≤ 3 层**（根下直接文件 = 第 1 层；`a/b/c.md` = 第 3 层） | **口径必须明确** —— "递归 3 层"在"含根 / 不含根"两种读法下差一层，差一层就会让人说"我明明放进去了" |
| 符号链接 | **不跟随** | 防环（自引用目录会让遍历不终止）+ 防越界（链到库外） |
| 排除项 | 隐藏项（`.` 开头 → 同时挡掉 `.git` / `.build`）、`node_modules`、`DerivedData` | 一挂就是代码仓库时，这几项能占掉索引的绝大部分位置，且**它们从来不是"资料"** |
| 读什么 | **只读目录项，不读文件正文** | 索引只需要名字 ⇒ 扫描成本与文件总大小**无关**，也不需要缓存内容。这也是"App 只读不写"的具体形态 |
| 每库索引上限 | **≤ 120 行 / 2000 字符**（先按行截，再按字符兜底）；超出折成 `… 另 N 个文件`（**显示 + 省略 == 总数**） | 索引进 L0、吃的是每轮预算。**折省略而不是静默截断** —— 不写"另 N 个"，agent 会把"索引里没有"读成"资料里没有" |

**索引段的确切形态：**

```
[知识库] 项目文档
路径: /Users/moofs/Code/mangox/docs
说明: MangoX 的 P0~P11 设计文档, 一个阶段一个文件
文件 (12, 深度≤3):
  P10-functional-design.md
  P11-functional-design.md
  P3-functional-design.md
```

- **`[知识库]` 是注入块的契约 token**（与 `[教训]` 同类）：模型看到的就是这个字面量 ⇒ **恒中文、不许本地化**（界面语言不许改 prompt 字节）。
- **必须给绝对路径** —— 只给文件名等于给了它一张没有馆址的卡片。
- **多层级文件用相对路径**（`sub/a.md`）—— 深度信息本身有价值。
- 每库之间空一行；`enabled = 0` 的库**整段不出现**（索引是给模型看的，没有"灰"这个状态）。

**索引段的预算待遇 = 整段进或整段不进：**

索引段吃 L0 预算，但它**不属于 `knowledge_items`、没有 `priority`** ⇒ 按 `priority` 降级那套对它不适用。**装不下时整段缺席 + 告警点名每库占多少字**。

判据：**地图宁缺勿残** —— 局部截尾的地图会让 agent 以为"资料只有这些"，比"没有地图"更坏（后者至少它知道自己不知道）。

> 与之对照的备选是"结构性段、永不缺席"（与 persona / 稳定段同级）：那最安全也最危险 —— **不变量必须能被机制保证**（persona 段之所以敢设永不降级，是因为它长度有界且由人手工维护），而索引长度**由目录内容决定**、库数无上限 ⇒ 它给不出这个保证。

落地形态（✅ 已实现）：`knowledgeIndexSegment()` 先于易变段判定；装得下则进块并从 `budget` 扣掉，装不下则 `indexSkipped` 记下 `[KnowledgeBaseCost]`（每库：显示名 + 字数）⇒ 红条点名。**缺席只影响索引这一段** —— 同一次组装里易变段照常注入。自检 ⑥ 兜住"既不进块、又不在缺席名单里"（＝静默丢弃）。

**L1 目录自动挂成内置知识库：**

`~/.mangox/agent/memory/`（跨项目 L1 落点）与 `<项目>/.mangox/agent/`（项目内 L1）里落着的，正是**"不进 prompt、需要时才读"**的条目 —— 语义**与知识库档逐字相同**。所以**把这两个目录作为内置库自动挂载**（不可删、可在 UI 里看到、描述由 App 写死："按需知识的落盘目录（App 管理）"）。

不做的话有个**已知的洞**：`kind=ondemand` 的 DB 条目**依然对 agent 隐形**（除了手写文字，没有任何机制告诉它这些文件存在）。

- 内置库**不落库、每次现算**（`builtinKnowledgeBases`）—— 身份由落盘目录决定，落库会出现"项目删了但库还在"的幽灵行。
- **存在不归用户配置，是否生效归用户配置**：**不可删**（删了下次现算又回来，"删了又出现"的按钮比没有按钮更坏），但**可停用**（`builtinDisabled: Set<String>`，不落库）。
- ⚠️ **停用开关必须折算进 `enabled`**（`effectiveKnowledgeBases`）：落成"扫描时读 `allKnowledgeBases`"会让开关**静默失效**（内置库的 `enabled` 恒为 `true`，`guard base.enabled` 永远放行 —— 开关点了没反应，且没有任何红灯）。
- 同一目录只挂一次：内置库列表按 `path` 去重，与 `UNIQUE(path)` 同判据。

**App 只读不写（红线）**：知识库目录里的一切 App **只读** —— 不写入、不改名、不删除、**不生成任何隐藏索引文件**（不在用户目录里留 `.mangox-index` 之类的东西）。判据同 pack：**目录的主人不是 App**。索引**现算**，不落缓存（同 §2.3"磁盘为准"）。

## 三、UI

### 3.1 顶部载荷条

`每轮都带上 4 条 · 1,240 字 / 64k = 2%` + 进度条 + `需要时才查 47 条 · 不占预算` + `查看本次注入` + `改动未生效 · 重启引擎`。

它回答的是 **"这一轮我带什么上飞机"**，而不是"我存了什么"—— 预算必须在看得见的地方管理。

- **契约：常驻层超限 = 红条 + 告警 + 按 `priority` 降级截尾（注入永不阻断）；按需层永不告警。** 预算压力只压给该压的那一层。
- 超限红条必须写明**降了哪几条**（前 3 条标题 + `help` 给处置指引"去调 priority 或改成需要时才查"）—— **"超限了"是无字之墙，"这三条没进 prompt"才是可行动信息。**
- `重启引擎` 就长在它影响的对象旁边（复用现成的 `knowledgeDirty`，不新造状态）。
- `查看本次注入` → 只读 **Markdown 预览** sheet。理由：**门禁绿 ≠ 改对了，真发出去的文本必须能被眼睛看见。**
  - ⚠️ **不许退回"一个 `Text` 承载整块文本"** —— 那个写法在大文本上是**平方级**的。实测（`scripts/diag/render_probe.py`，560pt 宽、**全高布局**）：

    | 行数 | `Text` 整块 | `MarkdownView` |
    |---|---|---|
    | 139 | 199 ms | 26 ms |
    | 561 | 4 251 ms | 105 ms |
    | 3 341 | **36 108 ms** | 646 ms |

    内容 ×24 ⇒ `Text` ×181（平方），`MarkdownView` ×24.6（线性）。注入块上限 64 000 字符 ⇒ 旧写法**最长 36 秒**。机制：`MarkdownView` 把文本按块拆成多个小 `Text`，各自布局 ⇒ 总代价线性。两份预览（本 sheet 与 `packEditor`）同源同规矩。
  - **量这个开销时有个陷阱**：`frame(height: 可见高度)` 会裁剪 ⇒ 同一份内容测出 206 ms 而非 8 512 ms（**差 41 倍**）。必须给**内容真实高度**，否则这个 bug 在探针里完全不存在。
  - **可复制**改由行尾 `复制全文` 按钮承担：`MarkdownView` 的选中是**逐块**的，没有"一次划过整篇"的选法。

### 3.2 左列：按来源分三区

**常驻 / 自定义 / 知识库**。区头计数各自取**该区断言的成员数**：常驻 = `pack.residentEntries.count` · 自定义 = `pending.count + custom.count`（**待审核排最前** —— 「需要动作的东西埋在列表中间」是用户永远发现不了的 bug）· 知识库 = `bases.count`。

**为什么按来源而不是按层**：按层分组会把**同一个来源劈成两半** —— persona 文件与用户条目在「每轮都带上」与「需要时才查」两段里各出现一次，那才是"看着乱"的真正来源。

三条纪律：

1. **`isResident` 降为行内标记**（不再是分组维度，且只在**按需**（非缺省）时才出现在副标里）。**正交状态不能靠"从分组里抹掉"表达，必须在行内表达。**
2. **分组维度只能有一个**，且"进不进 prompt"必须与载荷条**共用唯一判据**，否则条上说 3 条、左列只列 2 条。
3. ⚠️ **面板可见性 ≠ 注入资格**：把 `enabled` 并进分组判据，会让行内关掉开关的条目**从两处同时消失、面板上彻底消失、且零红灯**（**那个开关的实际效果等于删除**）。`KnowledgeStore` 里必须是**两个**成员：`injectableScopedItems`（含 `enabled`）与 `listedScopedItems`（**不含**）。

**两个区恒不判空**（常驻 · 知识库）：它们的区头各带一个**唯一恢复入口**（「文件夹」按钮 / 挂载行）⇒ 判空会把入口一起藏掉。persona 行右侧是 **`文件`**（只读标记），不是开关。

**persona 行 + 只读编辑器**：左列 pack 行只读、右侧 `文件` 标记、破损行标红；选中进 `packEditor`（只读），右上只有**「在 Finder 打开」+「重新读取」**两个动作。**正文 = `MarkdownView`，不是 `Text`**（同 §3.1 的性能红线）。

编辑器里只留**一行**元信息，留的两条判据是**"别处看不见、且真能影响决策"**：

1. **`layer` 标签** —— pack 侧唯一的注入旋钮，左列分组头又会随滚动离开视野。
2. **key 持有数** —— `keys` 是可执行契约（被锁的 key 之后在 DB 条目里不能再用）。折成个数 + hover 展开清单：信息不减而视觉不吵。

**选中态是单一路径**：左列与编辑器共用 `enum Selection { none / item(UUID) / pack(String) / base(String) }`。两个独立选中态能同时非空 ⇒ "编辑器显示 A、高亮在 B"，而这类 bug 不会有任何红灯。

### 3.3 行内两个新信号

命中计数 `·3` / `—`；**`—` 的行整行降一档灰度**，悬浮才提示归档建议 —— **"删除依据"第一次进 UI**。选中 / hover 沿用统一样式，**不新造视觉语言**。

**命中语义分两类：**

| kind | 记账点 | 记的是什么 |
|------|--------|-----------|
| `lesson` | **触发即命中**（`tool_call` 侧 `input.path` / `command` 命中 trigger，或前瞻注入命中） | "教训被推到它面前" —— 不必等模型自己想起来去读 |
| 其余（`fact` 等） | 读取即命中（L1 被工具读取归因，靠"一条一文件"实现） | "它真的被查过" |

**并加第三维：触发之后行为有没有变** —— `hitCount` 只记"推到面前"的次数，**一个被触发但从未改变行为的教训，比一个从不触发的教训更该归档**（前者是噪音，后者只是休眠）。UI 上 = 悬浮详情里两行（`触发 5 次 · 未改变行为 5 次`），归档建议**优先提名前者**。

**命中列现在全部显示 `—`，且整列不做灰度降档**（降档是"真·从未命中"的语义，占位期不能借用），配 `.help("命中统计将在启用后生效")` —— 那是**诚实的占位，不是 bug**。先留位的理由不是好看，是**让"从没被用过"这个缺口可见**。

### 3.4 编辑器：只留"写什么" + 归属

**形态 = `作用域（全局/项目） + 标题 + 正文 + 保存/删除`**，与 P11 之前的老版本同形。

**两条硬边界：**

1. **撤下输入框 ≠ 清空数据** —— `withUpdated` **只覆盖编辑器真能改的维**（作用域 / 标题 / 正文），`kind` / `layer` / `priority` / `key` / `trigger` / `counterfactual` **一律保持原值**。反例：一条 `kind=lesson` + `layer=always` 的老条目只因改了错别字就被重置成 `fact` + 默认层，而 `kind` 是**注入块的契约 token** —— 模型下一轮看到的标签都会被改掉。
2. **缺省即产品行为**（见 §2.1）。

**行开关（`开启 / 关闭`）就是"生效与否"的唯一入口**，位置不变（左列每行右侧）。**没有往编辑器里再加一个** —— 同一个状态两个控件是双写；且编辑器里的开关语义含糊（立即生效还是保存后生效？）。

**`priority` 的纵深防御**：控件已撤，`0...999` 的边界与**写入路径归一化**（`addKnowledge` / `updateKnowledge` 两个唯一入口都过 `clampedPriority(_:)`）照旧 —— 手改 DB / 将来的导入器不走控件，**控件钳制不是唯一防线**。**钳而不拒**："因为数字大了点就拒绝一次保存"比"钳到边界"更糟。

**代价（诚实记）**：`layer` 不能从 UI 改 ⇒ **存量按需条目无法在界面里提升为常驻**（只能删掉重建，或等知识库档承接按需那一侧）。

### 3.5 裁决动作面

选中提炼候选时给四个动作：**`采纳 / 编辑后采纳 / 设为常驻 / 丢弃`**，且**必须显示"它会进哪一层"** —— 采纳到常驻 = 改每轮 prompt，这个按钮要负责任。

（当前实现只有前三个，缺「设为常驻」与那句层级提示 —— 补齐属 P11.3。）

### 3.6 五类 `kind` 与标签

| 中文标签 | 英文标签 | kind | 是什么 | 例子 |
|------|------|--------|---------------------|------|
| **人格** | Persona | `persona` | 我是谁 · 态度与边界 | SOUL.md / RULES.md |
| **用户** | User | `user` | 用户是谁 · 怎么配合 | USER.md ·「称呼：老哥 / boss」 |
| **硬规** | Rule | `rule` | **常驻的硬约束，永远成立** | 「绝不往别人能看到的地方发半成品」 |
| **事实** | Fact | `fact` | **稳定事实**：环境 / 技术栈 / 项目结构 | 项目约定 · 服务地址 · 数据规模 |
| **教训** | Lesson | `lesson` | **从一次具体事故长出来的条件反射** | 「连接实例必须随配置失效」 |

**`硬规 ≠ 教训`，不可合并**：硬规 = 永远成立 → 常驻注入；教训 = 特定场合才该想起 → 带 `trigger` **按事件回灌**，是"教训回路"的唯一落点，也是五类里**唯一带额外字段**的。合并即该能力无处可挂。

- **标签用两字不用一字**：单字（人 / 主 / 规 / 实 / 训）五个里四个要靠解释才看得懂 ⇒ 那不是标签、是谜语。**标签看不懂 = 长在身上的疤。**
- **中英双语走现有 l10n 机制**：中文侧 = 源码字面量；英文侧 = `scripts/l10n/en_values.py` 词表。英文形态 = **首字母大写全词**（`Persona / User / Rule / Fact / Lesson`）—— 只读小标签跟 `Duration / Turns / Calls` 那一类（首字母大写），全大写留给"角色 / 状态标签"与"可切换段选"；kind chip 是**只读**的。
- ⚠️ **这是 l10n 连带项，不是免费改动**：每次简化必须同步清词表（`--check` 拿废弃清单 → 从 `en_values.py` 删 key → `--write` 落盘 → 再 `--check` 归零），**并顺手把 README 的「词表 N 条」一起改**。当前值以 `gen_strings.py --check` 为准（**589**）。
- ⚠️ **`KnowledgeKind.tag` 是注入块的契约 token，豁免不本地化**：若在此处 `L()`，用户切换界面语言会**改掉注入进 prompt 的字节**（破守卫 12）。两个 `tag` 都会让扫描器报 **7 处** `RETURN` 可疑，需登记在 `wiring_allow.txt` **F 组**（**不是漏译**；删豁免 = 扫描器再也拦不住有人改回 `L()`）。

### 3.7 明确不做

1. **不给 persona 做编辑器** —— 只读 + 跳文件（双写必漂移）。
2. **不新增第四个 nav 项** —— 人格不是另一个页面，它是同一张载荷表里最上面那一段。页面语义从"知识库"改为 **"注入与记忆"**。
3. **不做注入块常驻全文渲染** —— 只做计数常驻 + 按需查看。

## 四、组装自检

组装注入块时校验：

1. L0 条目一条不缺
2. 同 `key` 无冲突（含 **pack `keys` 事后扩张**撞库）
3. 无超预算静默丢弃（降级必须留痕）
4. persona frontmatter 合法且 `keys` 可解析
5. **persona 段确实在偏移 0**（结构性不变量）
6. **索引段无静默丢弃**（每个"挂了、启用、非空"的库必须落在"块内"或"缺席点名"之一）
7. **段序**：`persona < 稳定段 < 索引段 < 易变段`（**比偏移**）
8. **persona 段非空**（`guard !entries.isEmpty else { return "" }` 会让段整段消失，而守卫 5 在段为空时**短路成 false** ⇒ 把三份 md 删光，前 7 条**仍全绿**）

任一不过 **UI 红一条**，不静默降级。这是把"**先造能红的门，再动手**"用在记忆上，而且**可测：冒烟就能断言**。

**实现纪律：**

- **自检判据 = 在拼好的块里查字符串**（`block.contains(line(item))`），**不是**复用"应该进了"的集合算术。②④两句的判定输入本来就与拼装同源，复用等于让被检查的东西自己出题。**实测**：漏拼一条稳定段时，`降级 + 易变 + 稳定 == 全部常驻` 这条计数恒等式**仍然成立** —— **恒等式拦不住静默丢弃，只有字符串查找能。**
- **自检只报真问题**：每条告警都有对应的"通过时不抛红条"反向断言，否则"永远红着"和"永远绿着"看起来一样。
- **告警一律指名道姓**：「pack 坏了」不可行动，「修 `broken.md`」才可行动。
- **告警是数据、不是文案**：`KnowledgeWarning` 只出枚举 + 载荷，文案在 View 侧拼 —— 与进 `gen_strings.EXCLUDE_FILES` 的理由同源（**域层拼中文 = 三道 l10n 门都看不见的隐形漏译**）。
- **段边界必须显式暴露**：`KnowledgeInjection` 出 `personaText` / `bodyText` / `personaCount` / `personaChars`，消费方**一律读字段，不按行号数**。
- **⑥⑦ 都不能复用组装顺序** —— 组装顺序写错时"按组装顺序读"当然是对的，造反例永远不会红。⑥ 靠"在块里搜 `[知识库] <目录名>`"，⑦ 靠"比各段首字节的偏移"。
- **⑧ 的判据读产物、不读输入**：用 `out.personaText.isEmpty`，**不是** `pack.residentEntries.isEmpty` —— 后者是"输入的集合算术"，组装哪天把这一整段拼丢了它照样说"有 3 个常驻条目"。

| 18 | **扫描不越界**：深度 ≤3 / 白名单扩展名 / 不跟符号链接 / 排除隐藏与 `node_modules` 等 | 冒烟：每个边界各一个夹具文件，断言"该进的进、不该进的不进" | P11.4a |
| 19 | **知识库只读**：App 不改用户目录任何内容 | 冒烟：扫描前后对目录做**快照比对**（文件集 + mtime），断言完全一致 | P11.4a |
| 20 | **描述必填**：空 / 超长（>200 字符）⇒ 拒绝创建 | 冒烟：空描述 → 断言被拒且库里无记录 | P11.4a |

|---|---|
| `knowledge_items` | **1 条**，且 `enabled = 0` |
| `source='session'` 的条目 | **0** —— 蒸馏 / 保存为记忆**从没产出过任何东西** |

**解冻条件（任一成立才解冻）：**

1. **启用的** `knowledge_items` ≥ **20 条**（"某些条目长期没被读过"要到这个量级才成为真问题）；
2. `source='session'` 的条目 ≥ **5**（蒸馏 / 沉淀真的在产出东西）；
3. 出现**第一个现场抱怨**："这条知识我明明写了，它怎么就是不用" —— 那正是**教训回灌缺失**的证据。

### 6.2 冻结期间的规格（复活时直接照做）

**做什么：**

- **回灌双通道**：项目级 trigger → `beginTurn` 回合边界前瞻注入；文件 / 命令级 trigger → **扩展层教训门**（`tool_call` 拦截，**不得带 `ctx.hasUI` 守卫**，与审批门分段）。
- **记账**：lesson = 触发即命中；其余 = 读取即命中；加"触发后行为是否改变"维度。
- **教训门的两条配套**：拦后重试 / 改参落库；稳定 lesson 可"毕业"降级为前瞻注入（人工操作，不自动）。
- **蒸馏面升级**：`buildDistillPrompt`（`KnowledgeStore.swift:920`）与 `MemoryDistiller.parseOutput` 的输出 schema 从 `title/content/scope/reason` 扩为带 `kind / layer / trigger / counterfactual`；**但 `kind` 不由模型判定** —— 模型只做"抽取值得记的事实 + 一句话理由"，`kind` 由客户端规则推断（有 trigger → lesson；`scope=project` 且涉及环境/结构 → fact；其余默认 fact，人在裁决面改）。**分类是 schema 责任，不是推理责任。**
- `knowledge_revisions` + 编辑器底部变更史 · 归档建议（"触发多但从未改变行为" > "从未触发"）· 裁决面补齐（§3.5）· 决策后钩子留位。
- **pack `keys` 事后扩张的组装期处置**（守卫 13 已实现）。

**怎么验：**

1. 改 `PersistenceStore.swift` → 对应 lesson 按通道出现（项目级走前瞻注入、文件级走教训门）；
2. 给 `fact` 配 trigger → 不触发（守卫 8）；
3. L1 被读 → `hitCount` 增加；lesson 触发 → `hitCount` 增加且记"是否改变行为"；
4. 长期 0 命中 / 触发但未改变行为的条目给出归档建议（**不自动删**）；
5. 蒸馏跑一轮 → 断言模型输出**不含 kind 字段**，且客户端推断出的 kind 落地正确。

**三条机制前提（原先文档没写清，实现前必读）：**

1. **前瞻注入走第二条 `--append-system-prompt`**。`--append-system-prompt` **只在 spawn 期生效**（`PiRpcTransport.swift:490` 的注释自述"会话内不可改"）⇒"`beginTurn` 回合边界拼第二条"缺机制。定稿：**分两条参数传**，**稳定段那条字节全程不动**（守卫 12 / KV cache 前缀的命根），前瞻段单列；只有"本轮投影集变了"才 respawn（`--session` 恢复 ⇒ 连续性不丢）。
   - **否掉的方案**：拼进本回合 user prompt。判据不是贵，是**语义降级** —— 系统级纪律变成"用户说的话"，还污染 transcript。
2. **扩展 → App 的静默回传**。现有唯一通道是 `ctx.ui.select(...)`（会弹卡片），而记账要静默 ⇒ 扩展用 node `fs` 写 **JSONL 落盘**、App 惰性消费。**扩展绝不写 DB**（DB 单写者是红线；写进去就是双写、双写必漂移）。
3. **教训门独立成 `mangox-lessons.ts`**，不塞进 `mangox-approval.ts`。判据就在那个文件里：审批门第一行是 `if (!ctx.hasUI) return undefined;`，而**守卫 11 明令教训门不许带这个守卫** —— 同文件同函数迟早互相污染，而"可单独断言"要求在**文件层面**就分开。

**一处规格缺口（复活时必须补）**：守卫 14「lesson 入库 `counterfactual` 必填」× 蒸馏产出**没有** counterfactual ⇒ **采纳面必须补 `trigger` / `counterfactual` 两个字段**（`kind=lesson` 时必填），否则蒸馏出的 lesson **永远卡在 pending** —— 一条"能产出、不能入库"的死路。

## 七、已知风险

1. **L1 读了但没人记账**：命中信号依赖"经过工具读取"这一前提；若模型直接凭 L0 里的指引瞎猜，命中会漏记 ⇒ 归档建议可能误导。缓解：归档建议**只提示、不自动删**；lesson 类改走"触发即命中"，不再依赖模型自觉。
2. **persona pack 与 pi-memory 的边界**：`pi-memory` 是**每回合自动注入**（KV cache-stable 前缀）—— 与它对比的**不是 L1**（不注入、按需读），而是 **L0**。P10.1e 落地时必须明确分工，**不能两者同时自动注入同一批文件**。**和解选项**：L0 拆出稳定段后，"KV cache-stable 前缀"恰好就是稳定段需要的形态 ⇒ 稳定段可交给 pi-memory，本篇只负责易变段与 L1。
3. **生效代价**：`--append-system-prompt` 只在 spawn 期生效 ⇒ L0 改动仍需重启引擎 —— 所以 L0 必须**小而稳**（这正是分层的价值）。
4. **`read_when` 不驱动逻辑**：只消费 `layer`，避免引入第二套调度语义（两套语义 = 漂移源）。
5. **"禁止冲突"带来的三个新面**：
   - ① **改 pack 里的一条必须去改文件** —— 门槛升高。缓解：被禁用的 `key` 旁写明原因 + 给"在 Finder 打开"入口。**禁止而不指路 = 无字之墙。**
   - ② **pack 的 `keys` 解析失败 ⇒ 保留集合变空 ⇒ 撞 key 条目会被放行**（静默）。缓解：**解析失败 = 组装自检红，且保守禁止新建任何 `key`**（守卫 9）。**失败时收紧，不放松。**
   - ③ **`keys` 事后扩张**：守卫 3 只管"写入时拒绝"。用户手改 pack 新增 key X、而 DB 里早有 key X ⇒ **写入时没撞，组装时撞了**。缓解：组装时发现冲突 → **该 DB 条不注入 + 自检红条 + 迁移指引**（守卫 13）。缺了它，"设计上不允许冲突"在时间维度上就有洞。
6. **审批门在无 UI 会话里整体短路**：`mangox-approval.ts:183` 的 `if (!ctx.hasUI) return undefined;` 意味着**邮箱哨兵 / cron / watch 路径下敏感工具（bash/write/edit）不经过审批**。这在 P11 语境下暴露**倒置**：有人值守时教训是锦上添花，**无人值守时没有人兜底、教训是唯一的防线** —— 而这正是教训门最容易"继承 `hasUI` 守卫、整体失效"的地方。⇒ **教训门不得复制 `ctx.hasUI` 守卫**（守卫 11）。
   - 遗留记账（**P10.2 范围，不是本篇**）：哨兵会话里审批门的预期行为（自动 Allow / 自动 Deny / 阻断任务）目前依赖 `hasUI` 的**隐式**短路，需显式定义。
7. **教训门与审批门复用语义的风险**：同一段 `tool_call` 拦截里，审批门的 block 要模型**停**、教训门的 block 要模型**继续**。将来任何"连续 N 次 block 就放弃"之类的保护，都可能在不知情下杀死教训传递 ⇒ 二者在扩展源里必须**分段且可单独断言**（守卫 11）。
8. **元认知盲区**：需要读 L1 的时刻，恰是 agent 意识不到自己缺信息的时刻；L0 里那句"不确定时去读"在长上下文下指令遵循会衰减。这正是"被动回灌 > 主动读取"的依据，也是 L1 降为**兜底 + `fact` 专用**的原因。**性质：判断，非实测。**
9. **被排除在词表外的文件里写 `L()` = 隐形漏译**：`gen_strings.py` 的 `EXCLUDE_FILES` 为"注入面文本必须恒中文"而整体跳过 `KnowledgeStore.swift` / `Models/KnowledgeBase.swift`。于是该文件里 `L("…")` 的 key **永远进不了词表** ⇒ 英文界面静默回落中文；更糟的是**三道 l10n 门都看不见**。**处置**：组装器只出**数据**，文案一律在 View 侧拼；`EXCLUDE_FILES` 的每一项都必须写明"为什么排除 + 在里面写文案会怎样"。
10. **门的「判据」本身可以是错的**（与风险 9 同类，第二条看不见的漏译通道）：旧判据"字面量含汉字"**看不见纯 ASCII 的 key**（`L("priority %lld")` 词表不收、接线门不判）；裸 `code.split('//')[0]` 当注释剥离器会把 `L("// 空文件")` 切成残句。**共性**：缺陷的形状不是"某人漏翻译了一条"，而是"**门自己绿着**"—— 只能靠**给判据造反例**抓到。**处置**：判据从"字符集"改为"**作者意图**"（调用了查表函数 = 作者声明它是文案）；注释剥离器**收归全脚本唯一一份**。
