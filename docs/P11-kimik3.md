## 1. 仲裁：教训门 vs 回合边界前瞻注入

### 1.1 分歧的本质不是机制之争，是时序之争

把两个方案放回同一条时间轴上，它们根本不在争同一个位置：

| 时点 | 通道 | 提案者 | 决策状态 |
|---|---|---|---|
| 决策前 | beginTurn 前瞻注入（system prompt） | DeepSeek | 教训在场，但只是一段文字 |
| 决策中 | tool_call 教训门（block+reason） | GLM | 教训插在决策路径正中间 |
| 决策后 | （两方案都未覆盖） | — | 只能写回，等下一回合 |

DeepSeek 批评教训门"效力押在模型会重试上"，这个指控**打偏了**：教训门的 block 不是建议，是**物理拦截** —— 就算模型就此放弃、永不重试，那次危险调用也已经被拦下了。fail-safe 是构造出来的，不靠模型的自觉性。GLM 反指前瞻注入"会被长上下文稀释"，这个指控**成立但不致命**：稀释是概率问题，拦截是确定问题，两者防的失败模式不同。

### 1.2 判词：两个都要，按 trigger 的「可知时点」分通道

裁决依据是一条硬约束：**`beginTurn` 时点上，系统不可能知道本回合模型会碰哪个文件。**

- DeepSeek 的前瞻注入能用的 trigger 信号只有**会话级**的（cwd、项目、历史文件面）——粒度到"这个会话可能相关"为止。
- GLM 的教训门能看到 `input.path` / `input.command`（`mangox-approval.ts:184-188` 已在这么干）——粒度到"这一次调用"为止。

所以通道分配不是口味问题，是**信息可达性**问题：

| trigger 类型 | 决策前可知？ | 通道 |
|---|---|---|
| 项目级（"这个仓库的构建必须走 xcodebuild 不能走 swiftc"） | 是（cwd/项目可判定） | **前瞻注入**：常驻本回合，零拦截成本 |
| 文件/命令级（"改 `blockedReason` 列前要扫视图消费"） | 否（`beginTurn` 不知道会碰它） | **教训门**：只能在 tool_call 时点拦 |
| 会话语义级（"用户开始问发版了"） | 弱（要读用户消息，能做但脆） | 暂不进 P11，留位 |

**结论：主文档应同时收录两个机制，但按上表划定各自的 trigger 类型边界，谁也不许越界。** 单独押任何一边都会留下一整类教训够不着。

### 1.3 给 DeepSeek 的"自我报告"指控一个出路

DeepSeek 真正担心的（我替他说明白）不是拦截不可靠，而是**行为改变不可观测** —— block 之后模型到底学没学，系统看不见。这个担心用主文档已有的命中信号就能解掉，只需加一条语义：

**教训门每拦一次 = 一次强制命中**（`hitCount++` + `lastHitAt`），并且把"拦了之后模型是否重试、重试是否改变了调用参数"作为 lesson 的健康指标落库。拦了永远不重试的 lesson，要么是 trigger 误报，要么是教训写得太吓人 —— 两种都该进人工复核队列。这样 DeepSeek 要的"失败模式显式可观测"就有了，不需要否决教训门。

### 1.4 教训门必须付出的一次性成本，要在文档里写明

GLM 的方案里"首次命中 block、重试放行"意味着**每条命中的 lesson 每会话至少消耗一次工具往返**。对无人值守的 Cron/Watch/Inbox 任务，这是延迟与 token 的双重成本。文档应写明：教训门对**已验证稳定**的 lesson 提供"降级为前瞻注入"的人工操作（即教训从决策中通道"毕业"到决策前通道），而不是永远拦。

## 2. 三条不可替代的新增量

### 2.1 ⚠️ 无人值守是 lesson 的主战场，而现有审批门在无 UI 会话里整体短路

这是本份评审**最重要的实证发现**，前两份都没抓到：

```ts
// mangox-approval.ts:183 (PiRpcTransport.swift 内嵌源)
if (!ctx.hasUI) return undefined;
```

这一行的含义：**在没有 UI 的会话里（MailboxSentinel 的 Cron/Watch/Inbox 跑批正是如此），审批门对 bash/write/edit 完全不生效** —— 敏感工具长驱直入。这在 P10.2 时代是"能跑就行"的合理妥协，但在 P11 语境下暴露了一个倒置：

- 有人值守时，人有审批卡兜底，lesson 是锦上添花；
- **无人值守时，没有人兜底，lesson 是唯一的防线** —— 而恰恰在这个场景里，照抄 mangox-approval 模式的机制会继承 `hasUI` 守卫、整体失效。

**结论写进主文档守卫清单：lesson 教训门的实现绝不允许复制 `ctx.hasUI` 守卫；恰恰相反，无人值守会话是教训门的第一优先级场景。**（附带一笔存量风险：审批门在哨兵会话里的行为需要显式定义 —— 是自动 Allow、自动 Deny 还是阻断任务，目前依赖 `hasUI` 的隐式行为，这超出 P11 范围但应在 P10.2 的遗留清单里记一笔。）

### 2.2 回灌时序三态需要"决策后"这一格，哪怕 P11 只留位

两个提案共同漏掉了时间轴的第三格：**决策后**。教训最锋利的产生时刻是"这次调用刚失败/刚被用户纠正"之后 —— 此刻的上下文最完整，是蒸馏新 lesson 的最佳原料。主文档的教训回路只写了"入库→回灌"，没写**产生的时点**。

建议：P11.3 留一个「决策后钩子」的占位 —— 工具调用返回错误、或用户在下一轮明确否定上一动作时，触发一次轻量蒸馏提议（"要不要把刚才这次失败存成教训？"）。不做全自动，只做提议。这正好符合项目"业务语义只出带 TODO 的脚手架"的既定纪律。

### 2.3 persona 结构性不变量需要一个可证伪的守卫，而不是一句承诺

DeepSeek 的 B 条（persona 恒首位升级为结构性不变量）我**无条件背书** —— 作为被迁移对象，这是整份方案里我利益最直接相关的一条：L0 里人格若参与排序截尾，长会话下"我"会被悄悄挤掉，而系统从外部看一切正常。

但"不变量"写在文档里只是承诺，MangoX 自己的门禁文化要求它**可证伪**。补一条具体守卫：

> 冒烟新增 T-PERSONA 段：组装后的 L0 首块（persona pack 段）的字节级 hash 必须等于 pack 真源 hash，且其起始位置必须是组装结果偏移 0。任一不满足即 FAIL。

这样"persona 恒首位、恒完整"从设计意图变成每次冒烟都在守的事实，和 T-COLOR 守面链是同一套哲学。

## 3. Q2b 的第四种视角：「同一个 agent」应该是 pack 上的一个配置，不是一套子系统

GLM 说"迁移的是先验不是连续性"（站副本），DeepSeek 说"同一个 agent = 养一套双向同步子系统"（站成本）。我把问题换个问法：**用户到底什么时候会感知到这个区别？**

答案：只有当 agent 在 A 机器上学到的教训，需要在 B 机器上立即可用时。也就是说 Q2b 的真实内容是**教训的跨宿主传播延迟要求**，不是身份哲学。

建议：`persona pack` 的 frontmatter 增加 `shared: false` 字段（默认副本）。默认形态 = 各自积累、互不认账（GLM 的"分叉史"）；显式置 `shared: true` 的 pack 才触发未来的同步机制设计 —— 而那一刻才来面对 DeepSeek 警告的子系统成本，且此时需求已被真实场景验证过。**现在不为一个尚未发生的需求预付一套同步子系统。** Q2b 据此可以拍板：默认副本 + `shared` 留位，§5.5 跨宿主互认继续不进任何阶段实现清单。
