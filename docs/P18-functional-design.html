让 MangoX 能看见并操作 macOS 界面 computer use 这件事,在 macOS 上有一条被验证过的窄路:不是"看截图猜坐标",是读可访问性树(AX)。它比截屏快 40~100 倍、不移动鼠标、而且是可枚举的 —— 枚举出来,就能给用户看"它现在看得见什么",并把授权分成两层：App 面宽、动作面窄（能进的默认全给,进去之后能不能动手按类收紧）。这一版把这条路走通:三个载体(一个 Swift 辅助进程 + 一层薄扩展 + App 侧的权限与接管面)、两个工具、一条先修的审批闸门。

00结论先行VERDICT

一句话

MangoX 要的 computer use 不该是"截屏 + 猜坐标"(那会把每次感知变成一次云端往返、每次点击都变成一次焦点争夺),而该是以可访问性树为主角的一条路:读界面用 AX 树(带编号、带差分),动界面用 AX 的语义动作(按按钮、填字段 —— 不移动鼠标),截屏只在 AX 树读不到东西时才按需出场。落到本仓,它是一个自建扩展 + 一个 Swift 辅助进程,判据全在 Swift 侧(能进冒烟、能造反例)。但动工前必须先修两条 —— ① 现在的"敏感工具白名单"会让任何新工具自动放行,而远程驱动档(autoJudge)甚至对写操作一律放行;② 辅助进程那条 socket 默认同用户任何进程都能连,作用域判据挡不住本地进程 —— 见下 ① 与 §04 门 0。

①
先修闸门:现在的审批白名单是"漏 = 出事"的方向。敏感工具集是 new Set(["bash","write","edit"])(PiRpcTransport.swift:287),不在集里 ⇒ 直接放行(:327)⇒ 任何新工具都自带豁免。更狠的是远程驱动档（autoJudge）:分级只管 bash,write / edit 一律放行(:1931-1934)—— 而那正是邮箱哨兵远程驱动用的档。⇒ 若 computer 是个普通工具,一封远程邮件就能驱动你的界面。这条不修,后面全部不做。
②
感知用 AX 树 + 差分,不用截屏。AX 读一次约 50ms,截屏方案一次往返 2~5 秒 —— 10 步任务 3 秒 vs 35 秒(中 · 行业综述,待本机实测)。更重要的是 AX 树是文本:压缩 80~92% 后每步几百 token,且动作后只回差分。而截屏是像素,每步必须重发,且要送到云端。
③
动作走 AX 的语义接口 ⇒ 不抢你的鼠标。AXPress / AXSetValue 是程序化触发,官方文档原话是 "without synthetic mouse movement"。这一条把 macOS 桌面 agent 最难的那个问题(人和 agent 抢同一个鼠标)消掉 ~80%;剩下的 20% 靠人类接管检测兜底。这是本方案与"截屏派"最本质的差别 —— 不是更快,是更不打扰你。
④
授权分两层:App 面宽、动作面窄 —— 不是"把整台 Mac 锁起来"。AX 是可枚举的:枚举出来,就能在界面上列给用户看"它现在看得见什么",并把动作限制在名单 pid 的指定面上(read / act / none)。密码类 App 能进能读,值恒 ••••,但 act 面恒关。真正不给的只有两种:结构上做不到的(系统授权窗、永久删除)与恒拒判据(存盘确认 / 付款字样 / 删除语义)—— 见 §03 改动七。"发送"不在其中(2026-10-28 拍板):它通常就是任务的目的本身。另外要认清:作用域是"我们自缚",不是系统在兜 —— 用户真要放行整台 Mac 也拦不住;这条线的价值在于"默认宽、可收紧、看得见",而不是"系统替你挡了"。

01需求说明REQUIREMENT

R1
MangoX 现在的能力边界是"能写文件、能跑 shell",不是"能操作界面"。凡是没有 API、没有 CLI、只有图形界面的东西 —— 某个内部系统、某个只有网页版的后台、某个画布型工具 —— 现在的 MangoX 一点办法都没有。
R2
而"用 shell 硬凑"这条路是有天花板的。osascript + System Events 能做一部分,但它拿不到结构化的元素标识(每次都要按标题找),要逐个 App 授"自动化"权限,而且对自绘界面完全无能为力。
R3
受益场景的具体形态:① 每天要从一个只有网页版的系统里取数填进另一个表;② 某个客户端没开放 API,只能点;③ 想让 agent 在"我打开的那个 App"里替我做一段重复操作(填表、导出、贴进去)。这三类的共同点是操作是 GUI 语义上的(点某个按钮、填某个字段),不是像素上的。

不做理由

C · 外部契约（三）· TCC 权限的身份问题

macOS 的 TCC 授权按代码签名认进程。而 MangoX 的 Release 包是 ad-hoc 签名(见 README「下载与本地签名」)⇒ 每次重装 / 换机器,权限可能被清掉要重授。

另有一条:辅助进程若放在 .app bundle 内且随包签名,TCC 的"责任进程"仍是 MangoX ⇒ 辅助进程继承 MangoX 已有的授权,不必单独再授一次。(弱 —— 这条要本机验:把 helper 放进 bundle 后不额外授权,看 AX 读是否直接可用。)

为什么不是"扩展里直接做"

扩展跑在 node 里(mangox-web-search.ts / mangox-dream.ts 都是 TS),而 AX / CGEvent 是原生 macOS API ⇒ 扩展拿不到。要么在扩展里 shell out 到 osascript(拿不到结构化元素、要逐 App 授自动化权限),要么引一个原生辅助进程。后者更贵,但它把"判断"放回了 Swift 侧 —— 而 Swift 侧有本仓最值钱的东西:纯函数 + 冒烟 + 能造反例。

这正是 mangox-dream.ts 已经用过的路数:扩展"故意是哑的",判据全在 Models/NoteProposal.swift 的纯函数里(PiRpcTransport.swift:436-439 原话: "判据全部留在…纯函数里,那里能造反例、能进门禁")。computer 沿用同一条纪律,不给 TS 留任何策略。

辅助进程的生命周期:不随 per-turn 拆。MangoX 每次回合拆一个 pi 进程,但辅助进程按 App 会话常驻(懒启动)。理由三条:① 它持有观察缓冲与元素索引,跨回合复用;② TCC 授权提示只弹一次;③ 人类接管的事件监听只有一个,不会出现两个进程同时抢鼠标。

忘了写的一条：这条 socket 只认自己人

env 把 socket 路径交给 pi(PiRpcTransport.swift:1339-1369 那套 p.environment 写法),而 unix socket 默认同用户任何进程都能连 —— 一个后台脚本、一个别的 App、甚至某个依赖里的一段代码,都能连上来发 ui_act。作用域、遮蔽、不可逆红线全在这一层后面 ⇒ 它们挡的是模型,挡不住本地进程。

三条硬要求:① socket 放 0700 目录、文件 0600(~/.mangox/run/);② accept 之后立刻 getsockopt(LOCAL_PEERCRED) 取 pid,只接受本轮 pi 进程或它的子孙,其余断开并记一笔;③ 路径只经 env 下发、不落盘,且父环境里的同名变量必须显式删 —— 照 webSearchEnvironment(PiRpcTransport.swift:997-1004):只"有就设进去"不够,key == nil 且父环境已有同名变量时必须移除,否则会出现「面板显示没开 / 扩展其实连上了」同时为真、而且不亮任何红灯。

⚠️ 我建议它排在闸门倒置前面:闸门挡的是模型的误用,socket 挡的是别人替你的机器动手。前者是"做错事",后者是"被别人做"。

三条整形规则(全部在辅助进程里做,不污染模型上下文):

规则做什么为什么
剪枝只保留可交互角色(button / textfield / checkbox / menuitem / tab / link / toggle / slider / 有文本的 listitem),丢掉纯布局容器这是"80~92% 压缩"的主要来源;布局节点对模型无用。
去冗余AXDescription 与 AXTitle 或角色名相同时丢弃同样的词不写两遍。
编号 + 差分每次读给一份快照编号;动作后只回变化(新值 / 焦点 / 新增 / 消失)动作后不必重发整棵树 ⇒ 每步几百 token 而不是几千。

模型寻址用编号,不用坐标。坐标只写给人看(审批卡里"点哪儿")。理由:坐标会因窗口移动、滚动、缩放而失效,而编号背后是"那个叫『发送』的按钮" —— 语义稳定。

截屏什么时候才出场

只有三种:① 模型明确要看图;② AX 树读不到东西(画布型 / 自绘 / 游戏 / 某些 Electron);③ 一次动作失败,需要视觉证据。默认永远不截屏 —— 截屏是兜底,不是主路。

改动四 · 作用域：App 面宽、动作面窄（最重要的产品决定）

两层：谁能进（App 面）× 进去能做什么（动作面）

App 面：默认全选,用户可逐个排除 —— 不拿 App 类别去代理"危险"(理由见改动七)。辅助进程只对名单里的 pid 建 AX 根、只对名单窗口里的落点发坐标事件。

动作面：每个 App 给一个面 —— read / act / none。密码管理器 / 钥匙串 / 钱包 / 支付类 = 进得来,但 act 面恒关:读到的密码值在序列化边界恒 •••• ⇒ 读也不泄露;要它填密码,它拿不到值,自然填不进去。能看不能动,比"根本进不来"更准 —— 前者挡的是行为,后者挡的只是名字。

为什么这条比任何别的都重要:AX 的权限本身是全有或全无的(辅助功能 = 读所有界面 + 模拟按键,Apple 不给粒度)。粒度只能我们自己造 —— 而只有 AX 这条路造得出来(因为它是按 pid 寻址的)。用截屏派就造不出这个粒度 —— 那是一个像素流,没有 pid 概念。

这个作用域是"我们自缚",不是系统在兜

授权辅助功能之后,系统层面任何进程都能读整屏 —— Apple 不给粒度。「只准碰飞书」是辅助进程自己遵守的纪律,不是内核强制的边界 ⇒ 界面文案必须直说,否则用户会以为点完「允许飞书」系统就替他挡住了其它一切。诚实说法:「MangoX 已获得辅助功能权限(整台机器)。我们只在下面这些 App 里读和点 —— 这条约束由 MangoX 执行,不是由系统执行。」

连带一句:白名单也挡不住绕过辅助进程的路径(见下面「忘了写的一条」与 §04 门 0) —— 那才是唯一能被外部利用的缝。

口子一(§00 ① 那个):SENSITIVE 是黑名单式交集 ⇒ 新工具不在集里、:327 直接 return undefined ⇒ 任何新工具自带豁免。

已拍板（2026-10-28）：定时任务档给完整权限

⚠️ 但 autoJudge 不跟着开。这不是"权限给多给少"的取舍,是"这句话是谁说的"的取舍 —— 定时任务的指令是你写的,邮件正文可能是任何人写的。这两件事的差别不在权限表里,在输入源上。

改动六 · 人类接管（人和 agent 抢鼠标的兜底）

AX 优先把冲突消掉 ~80%(不移动鼠标),剩下 20% 是坐标兜底与菜单操作。兜底手段是行业里那套屏幕共享式接管:

层做什么
检测辅助进程挂 CGEventTap,监听人类的鼠标位移与按键(自己的事件打标记,不算)。
中止检测到人类输入 ⇒ 立刻中止当前动作,把这一轮标成"人接管了"。
告知给模型回一句"用户接管了,界面可能已变,重读再动" —— 不许模型拿旧快照继续点。
可见MangoX 自己的窗口上常驻一条:"正在控制界面 · 移动鼠标或按 Esc 接管"。

这一层是别的桌面 agent 普遍没做的。对一个"你边用电脑边让它干活"的个人工具,它是可用性的地板,不是加分项。

改动七 · 红线与遮蔽

总原则（2026-10-28 boss 定）：能力面 7 : 3 —— 只留三成不给

这个功能的目的就是当助手。每条都要人点一下,做出来的是个玩具。所以判据不是"这条危险不危险",而是"这条不该由谁触发"。约七成的界面能力直接交给它,只有三成永远不给。

⚠️ "三成"不是一张 App 黑名单。第一版我写的是五类 App 进不了白名单 —— 那是补丁:拿 App 类别去代理"危险",挡的是名字不是行为(坏人不会因为 1Password 不在名单里就罢手),而被挡住的反而是高频正事。所以三成落成两层:结构上做不到的(两个)+ 做之前恒拒的判据(三条),见下两表。

第一层 · 结构性不可达 —— 不是"不许做",是"没有这个动作"。

不可达的东西为什么它坏在"结构"上,而不是坏在"危险"上
系统级授权窗（TCC 弹窗 / 登录窗 / 锁屏）让被授权者批自己的权限 = 自指授权。这不是危险程度问题,任何动作级评估都救不了 ⇒ 辅助进程对这类系统进程不建 AX 根,名单里根本不出现。
永久删除 / 清空 / 格式化helper 只实现"移到废纸篓"(trashItem),"直接删"这条 API 在代码里不存在 ⇒ 模型想干也没有可调的动作。把不可逆动作从能力面删掉,审批面上就不用判它 —— 这是修根因,不是贴补丁。

密码管理器 / 钥匙串 / 钱包 / 支付类不属于这一层 —— 它们归改动四的动作面:进得来、只有 read,值恒 ••••。

第二层 · 恒拒判据 —— 做之前就判,纯函数、可造反例(不受"环境不同"影响)。

看到什么恒做什么为什么这条不能"弹张卡让人点"
存盘确认弹窗（"要保存吗"）恒选"取消",回报"这里有未保存的修改,要你决定"模型永远不该替人决定"不保存" —— 内容的唯一副本就在那个窗口里;反过来"保存"也不该它定(存哪、覆盖不覆盖)。
付款 / 下单 / 确认支付 这类控件恒拒,回报"这一步涉及付款,我不点"钱。哪怕能退款,退款本身也是一次操作。这类判断不需要"理解业务",认字就够。
永久删除语义（⇧⌘⌫ / "立即删除" / "清空废纸篓"）恒拒第一层已经把 API 拿掉了,这条是坐标兜底的兜底 —— 万一落点恰好压在"立即删除"上,还得有判据接住。
不在两层里的,一律放行 —— 包括"发送"

发送(邮件 / 消息 / 表单提交)不算不可逆(2026-10-28 boss 拍板,原来我把它列进去了,是错的)。理由站得住:「发出去」往往就是这个任务的目的本身 —— 日报写好要发、消息拟好要发,每到这一步弹一张"不可撤销"的卡,等于让它永远停在最后一步。

密码类 App 的 read 也在这里 —— 进作用域、只读、值恒 ••••:它看得到"有个密码框",看不到里面的字。

判据换一句:该拦的是"做完之后你还不知道发生了什么"(删掉 / 覆盖 / 关掉未保存的);不该拦的是"做完之后你正要它发生的事"(发送 / 提交 / 点确认)。

遮蔽必须在序列化边界做,不能等 prompt

密码框 / 受保护内容 / 疑似卡号的字段 ⇒ 辅助进程在拼字符串时就把值换成 ••••。理由:一旦进了工具结果,它就进了上下文、进了 DB、可能进了日志。"提示模型别看"是第二道防线,第一道是别让它出去。

改动八 · 工具面与档位

工具作用审批
computer_read读当前作用域内的界面(元素表 + 差分);可选"给张图"作用域内静默

档位:挂载与档位无关(extensionArguments 里 computer 与业务扩展并列,10-29 定案),能不能用由 --tools 决定 —— standard / full 能用,minimal 被 allowlist 裁掉、codemode 只剩一个工具;定时任务想在没人看着的情况下驱动界面,任务级档位要选 full —— 这两件事正交(能不能用看 --tools,裁决看审批轴),别混;沿用 web-search 的双闸门(挂载闸门 = 设置里开着;env 闸门 = 这一轮 spawn 时名单非空)⇒ 名单空的会话连 socket 路径都拿不到。

⚠️ 别把双闸门读成「每个会话各配一份」

名单是全局的:存在 settings 表里,一份,所有 standard / full 档的会话 spawn 时都读同一份 —— 一旦在设置里配好,任何 standard / full 档会话都能用,不需要逐会话开启。唯一带「这一轮」味道的是生效时机:名单在 spawn 那一刻下发给 helper ⇒ 改完勾选要等下一次对话才生效(进程复用时会按名单重启 helper,见 ComputerHost.Scope)。

19
focus：判"系统说焦点可不可设"，不是判"它长得像不像输入框"
为什么要有它：一部分 web / Electron 输入框不吃 setValue（AX 返回 success，值没变）；而"先点进去再发按键"要 CGEvent，属于批 3。先把"能不能聚焦"这一半如实交出去，模型才知道该重试还是该放弃。
判据：ComputerActGuard 第 ⑧ 步新增一支 —— target.canFocus（helper 现问 AXUIElementIsAttributeSettable(AXFocused)）为假即拒，话术点名是系统的答案（"系统说这个控件的焦点不可设"），并给出下一步（改用 setValue；连 AXValue 也不吃 ⇒ 这一类只能靠坐标点击，而它还没做 ⇒ 如实告诉用户）。
⚠️ 必须回读：AXUIElementSetAttributeValue 对某些元素返回成功却什么都没做 ⇒ 执行后读 AXFocused，不成立就回"没当成已聚焦"，不许回"聚焦了"。不回读的后果是模型接着 setValue 写进一个没聚焦的控件，然后以为这个 App 坏了。
状态：已做（未发版） —— CaseComputerAct ⑧ 段两支：canFocus=false ⇒ 拒且说"不接受聚焦"；同角色 + canFocus=true ⇒ 放行（没有这条对照，上面那条拒绝可能只是"反正都拒"）。
20
scroll：方向是独立参数，落点是四档搜索，成败靠回读百分比
方向不许猜：direction 与 op 分开两个参数、解码阶段不填默认值（填了就等于替模型决定"往下滚"，而它可能已经到底了）。判据先判参数、再判能力 —— 顺序是判据本身：没说方向是"重发一次就好"，没有滚动条是"换节点或换 App"，两句话导出的下一步不同。
落点四档（AXAdapter.scrollBar(of:)）：① 自己就是 AXScrollBar ② 自己的 AXVerticalScrollBar 属性（AXVerticalScrollBar 常量在 Swift 里没导出 ⇒ 用字面量，同 AXSheets / AXProtectedContent）③ 子树里第一个滚动条（有预算：网页树几千节点，整棵搜一遍会让一次 scroll 慢到几百毫秒）④ 再往上找四层。④ 是实测逼出来的：模型手里有编号的通常不是滚动容器本身，而是页面里的某个控件，滚动条挂在它上面那层 —— 只往下找的话，最常见的"长网页滚一屏"永远滚不动，而回执还会把原因说成"这个 App 不交给系统"（说错话比不动更糟）。
一步 = 0.1 段：拿不到内容高度与视口高度，假装知道比说不知道更糟（模型会以为一次就到底）⇒ 回执写百分比，要更多就再叫一次。
⚠️ 必须回读：写完AXValue 后重新读一遍，位移 < 0.001 就回"这个 App 不吃 AX 滚动，别重试同一个节点"。不回读的后果是模型接着读还是那 120 行，它只会以为这一页本来就短。
状态：已做（未发版） —— CaseComputerAct ⑧ 段四支（缺方向 ⇒ 拒且说"往哪滚"；没滚动条 ⇒ 拒且说"它自己和上面几层都没有"；两者同时成立时报参数；有滚动条 + 有方向 ⇒ 放行）+ ComputerScrollDirection.parse 的认/不认（Up 认，left 不认 —— 横向多半是表太宽，那是"读"能解决的）。反例：摘掉方向判据 ⇒ 2 条红，退码 1。
真机端到端（真 helper 二进制 + unix socket + TextEdit 400 行长文档）：focus ⇒ "聚焦了 #1「textarea」"；scroll down ⇒ 0% → 10%；再一次 ⇒ 10% → 20%；up ⇒ 20% → 10%；不带 direction ⇒ "scroll 要说清往哪滚(up / down) ⇒ 没动"。⚠️ 一个诚实的观察：TextEdit 整个文档都在 AXValue 里，滚动不改变那棵树 ⇒ 差分如实回"界面没动"，回执的价值只在百分比。scroll 真正的收益在虚拟化列表（网页 / 大 NSTableView）—— 那里滚出来的行才是新信息。别拿 TextEdit 这类反推"滚动没用"。

代价说明
TCC 授权要手动点，且可能重授辅助功能 + 屏幕录制两项;ad-hoc 签名 ⇒ 重装可能清。这与钥匙串那条同因(README 已写)。
AX 覆盖率是天花板自绘 / 画布 / 部分 Electron 应用的 AX 树稀薄 ⇒ 落到坐标兜底 ⇒ 速度与脆度回到截屏派。不能假装没有这条。
多显示器坐标原点NSScreen 与 CGEventPost 的坐标系原点约定不同,多屏下会点错。必须本机验。
AX 消息会超时目标 App 无响应时 AXUIElementCopyAttributeValue 挂住或返回 kAXErrorCannotComplete ⇒ 必须有超时与"跳过"语义,不能无限等。
对抗性界面视觉上骗过 AX 的恶意元素(同形异义的标题)存在 ⇒ 可加 OCR 双模复核,但那是另一批的事。
动作级判据有误判面同一个按钮在不同 App 里含义不同("删除"在邮件里是归档、在文件管理器里是进废纸篓) ⇒ 三条恒拒判据一定会先误伤一批,只能靠"误伤了加一条豁免"逐轮收敛。豁免必须能变红 —— 按名字记的豁免等于悄悄把门卸掉(本仓 10-14 已踩过一次)。
上下文仍会累积即便有差分,一场长 GUI 任务的快照仍会堆 ⇒ 照样会触发压缩。
辅助进程是一个新的生命周期面常驻 ⇒ App 退出 / 崩溃时得有人收:socket 文件、helper 进程、AX 句柄。本仓对「删会话与删项目同一清理半径」有过纪律,这里同一族 —— 漏了就是孤儿进程一直握着辅助功能权限。
CGEventTap 会被系统静默踢掉回调超时 ⇒ 系统把 tap 置为 disabled(kCGEventTapDisabledByTimeout),不报错、不留痕。人类接管检测会假死 ⇒ 必须在回调里自检并重装 tap,否则"你抢回控制权"这件事会悄悄失效。

一条会撞碎的不变量

「MangoX 装的扩展是哑的」这条会被打破 —— 所以判据必须留在 Swift 侧

本仓现有立场:扩展"故意是哑的",判断全在 Swift 纯函数里(同 PiRpcTransport.swift:436-439)。computer 的作用域、遮蔽、不可逆红线,一个都不能写在 TS 里 —— 写在 TS 里的判据进不了门禁(冒烟跑的是 Swift)。

⇒ 辅助进程存在的理由不只是"node 拿不到 AX API",更是"让判据落回能被断言的那一侧"。

红线

computer use 不得成为"一条远程邮件就能做的事"

远程驱动档（autoJudge,邮箱哨兵）下,computer 只读、不动作。这条不许用"以后加个开关"绕过去 —— 这一档的全部意义就是"没人能点" ⇒ 没有人能点的场景里,界面操作必须为零。

它是唯一一个保留"只读"的档(定时任务档 autoAllow 已拍板给完整权限)。判据不是权限大小,是输入源:定时任务的指令是你自己写的,邮件正文可能是任何人写的。

会话工具面会被钉住:老会话看不到后来加的工具

pi 把工具清单钉在会话首轮 —— 新加的工具只对新会话生效

pi 把「本会话有哪些工具」写进首轮那条 system 消息的 toolsAdded,之后每次加载会话都用它覆盖当前工具集(_restoreToolsFromTranscript ⇒ _setActiveTools(names),覆盖而不是合并)。于是批 2b 新加的 computer_act 在存量会话里永远进不来:模型会回「这个工具不在我的列表里」—— 而那与「功能压根没做」长得一模一样。

而且它会自锁:pi 本来有「当前工具集 ≠ 会话里那份 ⇒ 追加一条增量声明」的机制(getToolStateChanges + withToolChanges),但恢复那一步先把 active 压回旧清单 ⇒ 变化检测永远看不到差异 ⇒ 那条增量永远不写。

处置:只读不改,然后说出来

会话文件是 pi 的内部格式,写错就毁会话 ⇒ MangoX 不写它,只读其中的 toolsAdded 声明,与 MangoX 自己那几张工具表比对,缺了就在输入框上方常驻一行:「这个对话建立时就钉住了工具表,看不到后来新增的 computer_act。新建一个会话就能用。」并给一个「新建会话」按钮(在当前项目下开,档位按项目级记忆自动继承)。提示可关,关掉只在内存里记住 —— 重启后再提一次是有意的:那时多半已经忘了,而代价只是一行字。

判据为什么必须是这一条
按行序,同一条 system 里先删后加与 pi 的 getCurrentTools 逐条对齐。反过来(先加后删)会让同一批里刚加的被吃掉 ⇒ 本该「不缺」却报缺。
只认 role == "system"jsonl 里还有 thinking_level_change / user / assistant 等行型,它们不携带工具面;认错就等于「用户把工具名贴进对话 ⇒ 提示闭嘴」。
钉住的清单为空 ⇒ 不算缺空 = 这个会话还没被钉住(首轮没写 / 旧格式),那时 spawn 按当前工具集设置 ⇒ 全部可见。少了这一条,每新建一个会话都先弹一句假警报。
只说 MangoX 自己知道的工具第三方扩展注册了什么,MangoX 不知道 ⇒ 不猜(猜了就是「每装一个扩展都误报」)。web-search 的挂载判据跨模块、dream 只在 fire 那一次挂 ⇒ 都不算进来。
档位把扩展工具裁掉时不算缺挂载与档位无关(10-29 定案),但看得见由 --tools 决定:minimal 的 allowlist 会裁掉扩展工具、codemode 只剩一个工具 ⇒ 那两档的会话里 toolsAdded 天然没有 computer_*。算进去的话,每一个极简会话都会被报「缺两个工具」,而新建一个极简会话照样没有 ⇒ 一条永远修不好的假警报。判据用 AgentMode.exposesExtensionTools,并连同档位本身一起进缓存键(切档位时 jsonl 一个字节都没变)。
