三个必须记住的推论

① 「描述里没列」≠「调不到」。inlineBudget 只管列不列（tool.d.ts：装不下的工具 "left out, like deferred tools"），装不下照样能经 searchTools 找出来调（tool.js:64 的原话就是 "find unlisted tools"）。
② mode=only 改的是声明面，不是可调面 —— 直调工具的声明被摘掉，但它们在脚本里照旧可调（only 形态下 listed = callable，全部可调工具反而都写进描述里了）。
③ 只有 hidden 曝光会被踢出可调面。所以"关不关得掉"取决于注册不注册，不取决于"描述里写没写"。

⇒ 直接回答「codemode 能不能调业务扩展」

能 —— 但条件只有一个："那个层级挂不挂业务扩展"

可调面就是 ctx.tools，所以业务扩展的工具一旦挂载（注册进会话），codemode 就能调，不需要额外配置、也不需要额外开关。
在我们的四档里：codemode 层不挂业务扩展 ⇒ 那些工具根本没注册 ⇒ 调不到（不是"能调但被禁"，是不存在）；全工具档挂 ⇒ 调得到。
⇒ 所以「codemode 能不能调业务扩展」这个问题，等价于「那一档挂不挂业务扩展」—— 而这正是两个层级在显式回答的事。

顺带一个必须承认的既存事实

业务扩展的工具名是任意的，而 MangoX 的审批桥是白名单式的（SENSITIVE = Set(["bash","write","edit"])）⇒ 扩展工具名命不中策略 ⇒ 本来就不经审批。
这不是 codemode 新增的洞（今天它们被直接声明给模型、直接调，也一样不过审批）。codemode 改变的是形态：原本 N 次独立的工具调用，现在包在一次 codemode 调用里 ⇒ 用户看到的卡会变少。所以这条要和 门 6（工具卡展示）一起定。

本版唯一的实现途径。上一版方案走的是物化 settings.json，实测后整条被换掉 —— 因为存在一条短得多的路，而且它让前面那些洞全部变成"不适用"。

  • 没有 CLI 开关：pi --help 里与 codemode / tool-search / exposure 相关的项一个都没有（--mode 是输出模式，不是这个）。⇒ mode 不能从参数直传，但能从扩展的 options 传。
  • 关键发现：createCodemodeExtension 从包根导出（dist/index.js:34），而它内部是 getMode: () => options.mode ?? readMode(pi) ⇒ 传进来的 mode 优先于 settings.json。
    于是只需要在托管扩展目录里放一个三行文件： 
    import { createCodemodeExtension } from "@earendil-works/pi-coding-agent";
export default createCodemodeExtension({ mode: "only" });
  • ⇒ mode 变成纯 spawn 参数（挂哪个扩展由档位决定），与 --tools 在同一次组装里。那三条（PI_CODING_AGENT_DIR 的条件注入 / 目录锁 / 内容指纹）一条都不适用。
  • 裸模块名为什么能解析（这是这条路唯一的依赖）：pi 用动态 import() 加载扩展，解析基点是 pi 自己的 dist/bundle/cli.js（launchSpec() 已把它 realpath 出来用 node 跑）⇒ 向上必然命中 @earendil-works/pi-coding-agent 自身所在的那层 node_modules。与扩展文件放在哪无关 —— 已实测：同一个扩展放到 5 层深的目录仍可解析。

两组的五个段（preamble / tools / rules / docs / cwd）长度与内容全部相同，<tools> 段都只剩 - codemode: Run JavaScript that calls other tools。

但它有信号：扩展加载失败会写 stderr，而 P12.1a 的启动归因通道本来就在收 stderr（R4）。

做法为什么不

codemode 插在 standard 与 full 之间（上一版方案）它把 codemode 表达成"比常规多、比全工具少"，方向就错了 —— 它是正交维度，不是单调序列上的一格
给 standard 也加 codemodestandard 是默认档 ⇒ 静默改变默认行为，且新层没有存在意义
只用 --tools +codemode（官方配方）在 -ne 前提下是空操作（C 组实测：与基线逐字节相同）
只加 -e builtin:codemode装载 ≠ 激活（E 组实测：仍退回 4 条）
用 --no-tools + --tools +codemode 代替 mode=only-nt 会把直调工具整个停用 ⇒ 它们掉出 callable ⇒ 脚本也调不到 ⇒ codemode 变成废的。只有 mode 能"只摘声明、不动可调面"
用 settings.defaultTools 做层级激活它是全局设置，与 --tools 的合并语义需要额外核实；且会让"能力边界"藏进一个不在 spawn 参数里的地方。保持 --tools（纯函数里可见可断言）
mode 写进 settings.json（上一版方案的实现途径）不是错，而是绕远：要连着处理"注入有前置条件 / 目录锁 / 内容指纹"三件事，而自建扩展一条都不需要。两条路已实测等价 ⇒ 选短的那条
按档位写不同的 PI_CODING_AGENT_DIR该目录同时承载 models.json/auth.json/指纹缓存；按档位分目录要复刻整个物化链，成本远超收益。实测证明不必

T11MCP 确实关着断言 + 若有 mcp.json 则实测描述与 ALL_TOOLS 里都不含 mcp__= 门 4
T12mode 经自建扩展真生效读 sections.tools声明面 = 1 条（codemode）= 门 5

依赖与阻塞

  • 门 1 / 2 / 3 需要一个真模型跑一轮 —— 这是本版最大的阻塞点，也是唯一能推翻"安全上可开"结论的东西。
  • 门 5 是本版新增的硬前置：整个 codemode 层只有一个实现途径，它一旦失效形态就退化 —— 而且"扩展挂了"与"扩展生效了"在 spawn 参数里长得一模一样（差别只在 pi 侧读没读它）⇒ 判据只能落在 pi 的读回面（sections.tools），不能落在我们写出去的东西上。
  • 无外部依赖：不依赖 MCP、不依赖 tool-search、不依赖新服务。

05风险与边界RISK & BOUNDARY

风险

#风险现状结法
R1档位静默漂移（老用户 full 变 standard）只要排到前面就一定会发生，不改存储表示就躲不掉。零红灯门 8：存储改 rawValue + 冻结旧顺序表 + 迁移断言（含造反例）
R2"写 settings.json"这条实现途径已整条不采用它有三个零红灯的静默退化口：PI_CODING_AGENT_DIR 的注入有前置条件（modelCount > 0）+ 目录锁失败即整文件读不到 + 指纹不判存在性改走自建扩展 + options.mode ⇒ 三条全部不适用；生效判据仍读 sections.tools（门 5）
R3物化壳的指纹是内容指纹，不是存在性判据（既存缝）models.json / auth.json 被外部删掉或从旧版升级上来时指纹不变 ⇒ 永远不补写本版不动它 —— 换路之后 P13 已经不碰这个壳了 ⇒ 单独立账，不夹带
R4脚本失败不回滚官方明写 "calls made before a failure are not undone" —— 是特性不是缺陷在 UI 上说清：工具卡标"来自脚本"，让用户知道这张卡之前可能已经动过别的东西
R5脚本里 bash 能拿 1 MiB 输出绕过模型直调的 2000 行 / 50KB 截断 ⇒ 对 P10 无人值守是新的数据面在注入的指引里限制"不要把大输出直接 return"，要求先在沙箱里 filter／map
R6timeout_ms 无默认无期限门 2：给默认值（产品决策）
R7models.* 不经审批的花费计会话成本但不经审批门 3：先把账算清，再选"禁用 / 明说 / 接受"
R8store() 往会话写 custom entry已核兼容，但会话文件会变大观测即可；单值 ≤262144、总和 ≤1048576 是上游硬上限
R9业务扩展工具本就不经审批，codemode 让它们能被脚本连起来一次调审批桥是名字白名单（SENSITIVE = bash/write/edit）⇒ 扩展工具名命不中 ⇒ 静默执行。不是 codemode 新增的洞（今天直接调也一样），但形态变了：N 张卡变成 1 张与门 6 一起定：至少要能看出"这张 codemode 卡里调过扩展工具"，否则连"发生了"都看不见
R10行为指引"搬家"（新）only 把 4 条直调工具的 declaration 摘掉 ⇒ 它们的 8 条 guideline 从 <rules> 段（11 → 3 条）搬进 codemode 的描述。实测确认没丢，但位置从"全局规则"变成"单工具描述里的一节"门 1 那轮真模型跑一轮，观察模型是否照旧遵守这些规则；若退化，就把关键几条用 --append-system-prompt 补回规则段（不预设，先看）
R11上游改默认值defaultActive: false 与 mode 默认 on 都是上游事实，我们没有写下来门 5：显式钉住；并沿用 P12 的"引擎升级时复核基线"纪律
R12codemode 的代价说明只在 composer 看得见（新）另两处选择器是原生 Menu：只有名字，没有 subtitle、没有勾、没有底色 ⇒ 在定时任务 / Sparse 编辑器里选 codemode，用户既看不到"模型只能经脚本调工具"，也看不到"会多占上下文"，切换前零提示§04 待拍板 ①：建议统一成自绘 popover。若不统一，至少把那两处的 Button 文案从 displayName 换成带上说明的纯文本（能做的上限就在这儿）

四档覆盖不到的缺口（必须承认）

缺口 · 没有"codemode + 业务扩展"这一格

两条轴本可以组合出更多种，本方案覆盖的是 {四件套 / 内置全量} × {不挂扩展 / 挂扩展} + codemode层。
⚠️ 上一版的缺口（"业务扩展但不要 codemode"）已被本方案修掉：full 回到纯老档 ⇒ 邮箱哨兵（默认 .full）要的那一格正好就是 full，它不会再被顺带塞进 codemode。
缺口因此翻了面：现在缺的是 "codemode 且挂业务扩展"。今天没有消费者要这一格（哨兵要的是前者）。
触发条件：出现第二个需要"脚本编排 + 业务扩展"的消费者时，层级列表就该改成两个正交开关（扩展 × codemode），而不是继续加层。
⚠️ 届时 mode 要能按层取值（今天只有一层挂 codemode，所以写死 only 够用）。自建扩展路已经天然留好了这个口子 —— 换个 options.mode 就是新层，机制不用动。

缺口 · 层级的"代价"无法在 UI 上表达

codemode 层比常规档多花 +4439 字符 system prompt（其中 2185 是"只留 codemode"这个形态本身的开销），四档的 subtitle 只是文字说明，用户看不到这条价。本版处置：至少在 subtitle 里点一句"会占用更多上下文"，不做量化 UI。

上游暴露面（我们的能力面依赖了哪些上游行为）

  • codemode.mode 的默认值 on，与 only 的语义（"只摘声明、不动 callable"）—— 改了它，我们的形态就直接消失。
  • codemode 的 exposure: "model-only" —— 它既不在 callable（所以脚本不能套娃），也不受 hiddenDeclarations 影响（所以 only 下它自己还在）。这两个性质同时撑着本层的形态。
  • codemode 默认 defaultActive: false —— 改了它，codemode 会变成默认激活，"两层缺一不可"的断言要重判。
  • 包根导出 createCodemodeExtension 的存在性，以及 options.mode ?? readMode(pi) 这个优先级顺序 —— 本版唯一实现途径整个架在它上面。
  • builtin: 前缀与 -ne / --tools 的合并语义 —— --no-mcp 就是靠"merge 之后按 builtin: 过滤"实现的，这套语义一改，我们的 spawn 参数构造规则要重判。
  • _allowlistFiltersMcp 的语义（agent-session.js:147-151）—— 它的默认分支是"保留 MCP 工具给 codemode"，即"不设防"是上游的缺省。
  • codemode 的描述里带一条指向 pi 安装目录的绝对路径（…/docs/codemode.md）⇒ 模型会被引导去读 pi 自己的文档；该路径随安装位置变化。本版不处理（上游文案，且读文档本身无害）。

与其它版本的边界

  • 与 P3（引擎对接）：本版改的是 spawn 参数的构造规则（同 P12.1b 的位置）、一处档位存储表示、以及物化产物多一个文件；不动事件投影。
  • 与 P7（模式档）：这是模式档的第一次"分层" —— 三档之上加一层正交维度，并新增"内置扩展挂载"这条轴。枚举新增 rawValue = "codemode"（只新增值，不改变已有值的含义）；⚠️ 但存储表示要改（storageIndex → rawValue + 冻结旧表）。
  • 与 P10（无人值守）：R6 / R7 都落在 P10 场景 ⇒ 门 2、3 本质是 P10 的延伸。好消息：哨兵默认 .full 不再被牵连（不含 codemode）。
  • 与 P11（注入与记忆）：codemode 的声明不进 MangoX 的注入预算 ⇒ 载荷表会低估真实 prompt。要么在载荷表里说明，要么接受这个偏差（本版选说明）。
  • 与 P12（引擎基线）：P12 §七"不接 codemode"的理由已更正并迁到本文件；P12 不再持有 codemode 的任何结论。
