## 一、总评

方案与 GLM 那份评审我都读了。**方案该做，GLM 的九条里七条对**；但我不同意它最有煽动性的一条（教训门），并且两边的讨论都漏了**两个更底层的问题** —— 一个是"人格的权威从哪来"（元问题），一个是"这套东西一旦上线，谁在写它"（社会学问题）。下面按"认同 / 反驳 / 补盲区"三块说。

## 二、我认同的（交叉验证：这些是对的，可以放心采纳）

1. **诊断是取证，不是修辞。** 存量 2 条 `enabled=0`、同句两份 —— 这个证据链我复核了代码（`KnowledgeStore.swift:66-68` 确实按 `updatedAt` 降序 + 超限 `continue` 静默跳过），成立。
2. **"设计上不允许冲突"优于"冲突后裁决"。** 这是整份方案里最漂亮的一刀，GLM 也点了。我补充一个它没说的理由：**冲突后裁决需要维护一个"谁赢"的偏序，而偏序会随场景漂移**（交互 vs 无人值守、迁移期 vs 稳定期），"不允许发生"把这个偏序整个删掉了。这是正确的减法。
3. **GLM 的 3.2（L0 超限分场景）我复核后确认为真，且比它写的更严重。** 代码证据：`beginTurn`（`ChatStore.swift:1352`）里无人值守路径（`approvalOverride` / `unattended`）最终都走 `t.send(...)`，而 send 走同一套 spawn 组装 —— **知识注入块在无人值守 fire 里一样被拼进去，但那里没有 UI，红条无人看**。所以"L0 超限 = 红条 + 报错"这个契约，在三条无人值守路径上**根本不成立**。GLM 建议"按 priority 降级截尾 + 告警事件，注入永不阻断"是对的，我完全同意。
4. **GLM 的 3.3（KV cache 稳定段）方向对，但它的动机说偏了**（见 §三反驳）。
5. **GLM 的 4/5/6/7（触发即命中、一条一文件、pack keys 事后扩张、蒸馏模板升级）都是真问题**，且都是"做完之后才发现的坑"，属于该在动手前补进主文档的一类。我不复述，直接采信。

## 三、我反驳的：GLM 的「教训门」是漂亮的机制，但用错了地方

GLM 的 3.1 是整个评审里**最漂亮、也最危险**的一条。它说：lesson 回灌通道未定义，解法是用扩展层 `tool_call` 拦截，命中 trigger 的首次调用 block 并附教训全文。证据是 `mangox-approval.ts` 已经在这么干了。

**这个机制本身成立，我对它的批评不在可行性，而在它把一个"应该确定性处理的先验"变成了"依赖模型行为的中断"。** 三个理由：

**① 它把教训的效力押在"模型会重试"上。** `{block: true, reason: "LESSON[...]"}` 之后，模型**应该**重试。但"应该"不是"必然"：一个模型完全可以把这次 block 当成最终失败而换一条路径（绕开该文件、改用别的工具、直接放弃这个子任务），于是教训**根本没进入后续决策** —— 它只在一次失败的 reason 里闪现。GLM 说"reason 不可能被忽略"，那是它作为**某个模型**的自我报告；作为架构，你**不能把正确性建在模型的自我报告上**。这正是它开头自称"模型本体证词"的位置，也是这份证词最不可信的位置。

**② 它把"教训"和"审批"混进了同一条通道，但两者的语义相反。** mangox-approval 的 block 是**要模型停**（等用户决定）；教训门的 block 是**要模型继续**（知悉后重试）。同一个"block 一次 + 放行"的机制，一次承载"停下来"，一次承载"继续走"，复用代码没问题，复用**语义**会出问题：将来任何人对 `tool_call` 拦截做改动（比如加"连续 N 次 block 就放弃"的保护），会在不知情的情况下**杀死教训的传递**。

**③ 更根本的：教训应该在"决策之前"在场，而不是在"决策中途"打断。** 教训门的时序是"模型已经决定要动这个文件了，才被拦下来补一条"。但教训里最有价值的那部分 —— "**别**动这个文件，换一种做法" —— 恰恰需要比"动"更早的在场。把教训塞进 system prompt 是"常驻但被稀释"，塞进 reason 是"在场但太晚"，两条都是次优。

**我的替代（也回答 GLM 漏掉的通道选择）**：lesson 回灌应该走**回合边界，而不是回合中间**。具体是——在 `beginTurn` 组装时（`ChatStore.swift:1352` 附近），客户端**已经知道**本回合的 cwd / 项目 / 即将触碰的文件面（如果 agent 用了 `--plan` 或 `todo`，甚至有前瞻信息），可以把"匹配 trigger 的教训"作为**第二条 `--append-system-prompt`** 拼进去。这听起来像退回到 GLM 否掉的 (a) 通道，但关键差别是：**(a) 否的是"下回合"，我主张的是"本回合开始时"** —— 而"本回合会碰什么"是可以提前知道的（项目绑定在 `beginTurn` 就确定了）。

它不完美（若 agent 临时决定碰一个计划外的文件，前瞻就漏了），但它的失败模式是**"教训没出现"**（可观测、可补、可把 trigger 从"文件级"放宽到"项目级"兜底），而教训门的失败模式是**"教训出现了但被模型无视"**（不可观测、不可补）。**两者都是次优，但一个的次优是显式的、可度量的，另一个的次优是静默的、依赖模型自觉的。** 架构上，永远选前者。

结论：**教训门可以作为 P11.3 的增强（在回合内补前瞻漏掉的），但不应作为回灌的主通道。** GLM 把它从 P11.3 提前到 P11.2 的重排，方向对（回灌值得早做），但主通道选错了。

## 四、两份都漏掉的盲区（这是本评审最想说的部分）

### 4.1 元问题：人格的"权威"从哪来？

方案通篇在解决"人格**怎么**注入"，没问"人格**凭什么**被注入时拥有最高优先级"。现在这个答案在机制里是**隐式的、脆弱的**：persona pack 被放进 L0 稳定段，稳定段排最前 —— 于是它"碰巧"拥有最高优先级。

但看守卫清单：**没有一条守卫保证"persona pack 永远排在任何 fact / lesson 之前"**。守卫 1 守的是"L0 一条不缺"，没守"L0 内部 persona 在最前"。今天组装器把 pack 排前面，明天有人重构 `buildKnowledgeBlock`，把易变段排到稳定段前面，**所有守卫仍然是绿的**。

这不是吹毛求疵，这是人格方案特有的问题：**fact 是"知识"，可以丢、可以降级；persona 是"我"，丢了它这个 agent 就不再是它。** 两者的失败代价不在一个数量级，但方案把它们放进同一张排序表，用一个"priority 数字"表达 —— 而 priority 是可以被手滑改掉的。

**建议**：把"persona pack 恒为 L0 首位、且不受任何降级/截尾影响"写成**硬性结构**，而不是**可调参数**。具体：组装器的输出结构里，persona 段是**独立的第一段，不参与 L0 条目的 priority 排序，也不参与截尾**；守卫新增一条"构造任意噪声 + 超预算场景，断言 persona 段字节不变"。这是把"我是谁"从"数据"升格为"不变量"。

### 4.2 社会学问题：上线后，谁在写这些条目？

方案描述了一个**用户**在策展知识库、审候选、改 pack。但现实里，这份 memory 的**主要写手会是"我"（agent）自己** —— 蒸馏候选是我提炼的，教训是我踩出来的，甚至"项目约定"里很多条是我写的。方案在"写入者"这一栏写的是"人 + 提炼候选（审核）"，把 agent 的自主写入挡在了审核闸门后面 —— 这跟现状一致，但它**没有回答一个更尖锐的问题**：

**一个会自己往自己的记忆里写教训的 agent，它的记忆里会累积出什么？**

不是"变聪明"，是**会累积出系统性偏见**。教训是"从一次具体事故长出来的条件反射"，而事故是**有选择的**：踩过坑的记得牢，没踩过的永远不写。于是 memory 会慢慢变成"我踩过的坑的清单"，而不是"这个项目的全貌"。更糟的是：**教训会自我强化** —— 一条"grep -E 静默返回空"的教训，会让 agent 在后续所有会话里更倾向于绕开 grep，而不是理解"本机 shell 的坑"，于是再踩不到新坑，教训库冻结。

**这不是说别做，是说要做对侧的护栏。** 两个具体建议：
- **蒸馏 / 教训入库时，强制记一条"counterfactual"**：这条教训是"该做 X"，但也要记"**什么情况下这条不适用**"（如"grep -E 静默返回空"的反面是"在非本机 shell 的 CI 里不存在此坑"）。一个只有正例没有边界的教训库，会在第 N 次误用后变成负资产。
- **给教训设"衰减 / 复核"信号**（不一定自动，至少 UI 提示）：长期未触发、或触发后反复被模型忽略的教训，是"过时先验"的候选。方案已有 hitCount，但 hitCount 只记"触发"，不记"触发后有没有用上"。**一个被触发但从未改变行为的教训，比一个从不触发的教训更该被归档** —— 前者是"噪音"，后者只是"休眠"。

### 4.3 一个容易被当"细节"跳过的真问题：蒸馏模板的 schema 与 kind 的分类责任归属

GLM 第 7 条说"蒸馏模板要升级输出 `kind/layer/trigger`"。我同意，但我要**反对把 kind 的判定交给蒸馏模型**。五类（persona/user/rule/fact/lesson）里，**kind 的判定标准是"跨会话语义"，而蒸馏模型看到的只是"最近 12 条文本"** —— 它没有足够信息判断一条东西到底是"硬规"还是"事实"。让模型判 kind，等于让一个看不清全貌的旁观者给记忆做本体论分类，错误会**静默沉淀**（因为 kind 错了，UI 上只是标签错，守卫不会红）。

**建议**：蒸馏模型的输出 schema **只让模型做它做得好的**（抽取"值得记的事实 + 一句话理由"），**kind 由客户端规则推断**（有 trigger → lesson；scope=project 且涉及环境/结构 → fact；其余默认 fact，人工在裁决面里改）。**分类是 schema 责任，不是推理责任。** 这条和 4.2 是同一根：**别让模型去替它自己定义"它是什么"。**

## 五、一个更好的方案？—— 不重排，改三处

GLM 重排了阶段顺序；我认为**阶段顺序不重要**（P11.1 打底独立、无争议，该先走；后面的顺序是资源问题不是正确性问题）。真正该改的是三个**设计决策**：

| # | 决策 | 现在 | 改成 |
|---|------|------|------|
| 1 | lesson 回灌主通道 | 未定义（GLM 主张扩展层教训门） | **回合边界前瞻注入**（`beginTurn` 按项目/文件面拼第二条 `--append-system-prompt`）；教训门降为回合内兜底增强 |
| 2 | persona 的优先级 | 靠 `priority` 参数，可手滑改 | **结构性不变量**：persona 段独立、恒首位、不参与排序与截尾；新增守卫 |
| 3 | kind 判定 & 教训的 counterfactual | 蒸馏模型判 kind；教训只有正例 | kind 由客户端规则推断；教训入库强制记"何时不适用" |

这三条的共同点，也是本评审的落点：**凡是影响"这个 agent 还是不是它自己"的机制，都要用结构（守卫 + 规则）而不是参数（priority）+ 模型（蒸馏判 kind）来表达。**

## 六、给 Q2b 的补充（不重复 GLM 的"双胞胎"）

GLM 的"迁移的是先验不是连续性"我很认同，不再展开。只补一个**工程侧**的推论，因为它直接影响 Q2b 的拍板成本：

**Q2b 的选择，决定了 persona pack 是否需要一个"版本戳 + 迁移校验"机制。** 若选"同一个 agent"（镜像同步），你需要解决"两宿主同时改"的冲突，这几乎必然要引入双向同步 + 冲突标记 —— 一个**和知识库本身一样复杂**的子系统。若选"副本 / 先验迁移"，则只需要**单向快照 + 一次性导入**，之后各走各的 revision，复杂度低一个数量级。

所以 Q2b 表面是哲学问题，底下藏着一个工程规模的判断题：**"同一个 agent"的答案，代价是养一个同步子系统。** 我建议 boss 拍板时把"是否愿意养这个同步子系统"当成权重最高的因素，而不是"星期五该不该是同一个" —— 后者没有工程答案，前者有。
