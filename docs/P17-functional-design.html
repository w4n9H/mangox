00结论先行VERDICT

一句话

dream 装给模型的上下文和它要做的判断对不上：会话侧 12,000 字符上限、笔记侧只有一份目录，而它要回答的是"哪篇笔记该改、哪篇该删"。这一版把输入重拼到 256k 预算（会话全量 + 笔记目录 + 笔记正文），把"删除"做成第四类提案。但动工前必须先修一条断链 —— 见下 ①。

另：本版一并落实了运行可靠性 —— 防 App Nap 降频（把被系统推迟的定时器拉回来）+ 睡眠期间的漏跑清单（补不补由人拍板）。它与 dream 无关，是独立的一节：见 §06。

①
先修断链：merge / replace 的采纳从来没成功过。指令要求 base_hash = 你 read 到的那篇笔记全文的 sha256（SchedulerService.swift:152），但 pi 的 read 工具只返回正文（dist/core/tools/read.d.ts：详情类型只有 truncation，read.js 里 sha|hash|md5 零命中），[笔记] 索引段的行也没有任何指纹（KnowledgeBase.swift:435-441）—— 模型没有任何途径拿到这个值。而客户端校验只查它非空（PiRpcTransport.swift:492）⇒ 编一个字符串就过闸、入库、一路走到人点采纳，撞上 KnowledgeStore.swift:1599 的比对 ⇒ .baseHashMismatch。修法：让扩展自己算 —— 它跑在 node 里，一步 createHash，而且记的是"写下这条提案那一刻"的指纹，比模型的 read 更准。
②
输入重拼不是"调大数字"，是三个语义变化。① 从「先截断再拼」改成「全文优先、预算兜底」；② 会话侧取消「最多 8 个」，改由窗口决定看几个；③ 笔记侧新增正文段（目录保留）。只改数字的话，省钱逻辑仍然会先把内容切碎。
③
会话摘录按回合整对丢，不切字符串。现在的单会话裁剪是 body.suffix(2000)（SchedulerService.swift:285-287）—— 一场正常会话必超 2000 ⇒ 开头的用户提问整段消失，且切点落在半句话中间。喂进去的是"没有提问的回答"，模型会把那些回答当成凭空冒出的结论。
④
笔记的来源指针在采纳那一刻就没了。note_proposals.sources 记着"这条结论来自哪几个会话"，但 P15.8/5f「拍过板就删行」⇒ 采纳即删行；而落地的 note_revisions 六列没有 sources（PersistenceStore.swift:135-144）。⇒ 判断"这篇的依据现在还成立吗"没有依据。会话本身还在库里，丢的是链接，事后补不回来。
⑤
重复可以接受，丢失不行。窗口取 36 小时，但下限是"上次 fire 至今"：scheduled_tasks.last_run_at 是现成的（PersistenceStore.swift:77），每次 fire 起来时写（SchedulerService.swift:519）、被跳过的 fire 不写（:529）⇒ 漏跑一天料不会掉出窗口。零新列、零新状态，一个 max 的钱。

为什么窗口取 36 小时而不是 24：日更的两次 fire 之间总有抖动，卡死 24h 会让"昨天下午到今早"的会话反复掉在缝里。多出来的 12 小时造成的重叠（重复读）是可以接受的代价。

但重复不等于丢失：固定窗口的固有毛病是"漏跑一天 ⇒ 那天的料永久掉出窗口"。取 max(36h, lastRunAt) 就同时解决：正常每天都跑 = 36h；漏一天 = 窗口自动拉长到"上次 fire 至今"，料还在。被跳过的 fire 不写 lastRunAt ⇒ 窗口自动延长，正是想要的。

回合结构：一条 user 消息 + 它之后到下一个 user 之前的消息 = 一个回合。超预算时从最旧的回合整对丢，留下的每一段都是完整的「用户: … / 助手: …」。现在的 suffix 会把开头的提问全切掉，还会从半句话说起。

05风险与边界RISK & BOUNDARY

06运行可靠性DAEMON

一句话

boss 说的「常驻」其实是三个互不相干的问题：① App Nap 降频（app 还在，定时器被合并 / 推迟，漏掉的不补）② 重启后不自动起③ Mac 睡眠。三者的严重度与修法完全不同。本版只修 ①；②③ 明确不做，改为把"睡过去期间漏了哪些任务"列成一张清单 —— 补不补由人拍板。

A · 三个问题，三套代价

#问题症状本版
①App Nap 降频app 还在，但「窗口不可见 + 无音频 + 在后台 + 没声明"我还在干活"」四条全中 ⇒ 定时器被推到几秒一跳，漏掉的不补已修
②重启后不自动起登录项 / SMAppService 零命中 ⇒ 重启之后没有任何东西在跑不做
③Mac 睡眠系统层面睡着，app 无能为力（合盖 / 手动睡眠 / 关机全都挡不住）不做 · 出清单

实测（不是推论）：App Nap 激活后，100ms 与 200ms 两个定时器双双变成 5 秒一跳，且那份复现记录的注释明写 does not make up for missed timers by firing multiple times —— 漏掉的那几次不会补。这就是"该在 03:00 跑、醒来发现没跑"的机制。

B · 为什么 ②③ 不做

代价与收益倒挂

② 技术上能注册登录项（ServiceManagement.framework，本仓 deployment target 够），但本 app 未签名（mangox.entitlements 是空 dict ⇒ 非沙盒）⇒ register 可能失败或落 .requiresApproval。收益不确定 + 要动签名链路 ⇒ 挂起。

③「防空闲睡眠」那条断言的类型名里 UserIdle 三个字就是答案 —— 它只防空闲。合盖 / 手动睡眠 / 关机 / 退出 app 全都不在它的覆盖里。这不是实现问题，是系统没开这个口子。而本机是笔记本（MacBookPro17,1，有电池）⇒ 代价是全天候的，覆盖的却只是 5 种漏跑场景里的 1 种。

C · 方案：只防降频 + 一张清单

防降频：一条常驻断言调 beginActivity 向系统声明"我还在干活"。选项刻意不含 IdleSystemSleepDisabled —— 那一档会让 Mac 永不休眠（.userInitiated 的定义里就带着它）。用 .userInitiatedAllowingIdleSystemSleep：只防降频，不碰睡眠。⚠️ 这一条已不再由冒烟守 —— 见 §06 E。
已落地
断言必须强持有头文件明写：对象一被释放，断言就自动结束。存局部变量 = 没加。所以它是一条 private(set) 属性，并且 start / stop 严格对称（重复 start 不许越堆越多）。
已落地
清单：该跑却没跑的每次 tick 发现"这一分钟跳了不止一分钟"（睡眠 / 长挂起）就重算一遍。判据是确定的而非猜的：lastRunAt 只在 fire 真起来时写 ⇒ 窗口内任何 cron 点只要真跑过，lastRunAt 必比它更晚 —— 反证。
已落地
零新列、零新状态地基全是现成的：scheduled_tasks.last_run_at 已落库 · createdAt 已存在 · CronExpr.matches 是纯函数 · 认账走 settings KV。整个功能一行 DB 都没动。
已落地
窗口起点 = 四个候选里最晚的那个

max(回溯上限, createdAt, lastRunAt, ackAt) —— 三种来源（真跑 / 出生 / 认账）叠加一个上限，是并集关系。createdAt 兜"新建但从没跑过"（否则会误报它出生之前的每一个 cron 点）；7 天的上限兜"从没跑过、且很久以前建的"（否则一路回到它出生那天）。回溯是逐分钟扫的 —— 先在分钟位上筛一道，再交给日历分解。

口径：漏跑 ≠ 只因为睡眠

调度那条路上有三条"到点了但跳过"的分支：项目已删 · 该任务回合在途 · 并发已满。后两条也算漏跑 —— 它们同样是"这次没跑"，而且用户点开那个日志会话能看到跳过原因。项目已删的不算：那不是漏跑，是配置坏了，另有提示位。

左侧两行（任务名 + 档期 · 漏 N 次 · 最近 X），右侧两个纯文字按钮。没有漏跑时整块不画 —— 不是画一个空卡。
两个按钮都是必需的

「忽略」一定要有 —— boss 原话"有时候我觉得漏了就漏了，可以忽略"。它是认账：把"我认下这批"的时刻记进 settings KV，窗口起点随之前移 ⇒ 不再提示。

「补跑」只跑最近一次 —— 不是省事，是经济学：dream 的水位本来就会把窗口拉长（min(now − 36h, lastRunAt)），补一次就把漏掉那几天的料一起捞回来；补 N 次反而会在同一个日志会话里连投 N 个回合，后面几个全被"该任务回合在途"挡掉 —— 白点。

⚠️ 补跑必须认账，否则"点了没反应"：调度那条路有在途保护，补跑可能当场被跳过、lastRunAt 不动 ⇒ 条目刷新后原样留着。所以无论这次真的跑没跑成，都要把认账一并落下去。

E · 门禁缺口与未采纳的路

⚠️ 门禁缺口（不假装它被盖住了）

冒烟证不了 App Nap 真的被压住了 —— 那需要"窗口不可见 + 真进 napping"，测试进程里无法复现。它能守的只有两条："代码在"与"选项还在防降频那一档"。真机验收 = pmset -g assertions 里出现那条 reason。同 §02 那条"门的绿盖不到模型判断对不对"。

② 撤掉的一格（2026-10-15）：原来还有一条断言守"选项不含 IdleSystemSleepDisabled"（即"没被偷偷换成会禁睡眠的 .userInitiated"）。已按 boss 拍板移除 —— 它是全仓唯一用代码引用那个符号的地方（生产代码只在 SchedulerService.swift:119 的注释里提它），boss 担心 CI 那条 scripts/smoke/run.sh 在别的 SDK 上编不过。

⛔ 留下的缺口，别以为被邻居盖住了：剩下那条 contains(.userInitiatedAllowing…) 守不了这件事 —— 两个常量的位是交叠的（UserInitiated = 0x00FFFFFF | (1<<20) = 0x00FFFFFF；AllowingIdleSystemSleep = 0x00FFFFFF & ~(1<<20) = 0x00EFFFFF），而 OptionSet.contains 判的是"位有交集" ⇒ 真换成 .userInitiated，它照样绿。⇒ 这条性质现在只能靠 review 看那段注释与常量本身。

要补回同一道守卫、又不碰任何 SDK 符号，一行就够：napSuppressionOptions.rawValue & (1 << 20) == 0（1 << 20 就是 NSActivityIdleSystemSleepDisabled 那一位，纯 UInt64 运算，与符号的可用性 / 弃用标注完全无关）。待 boss 定，当前未加。

未采纳为什么不
SMAppService 登录项app 未签名 ⇒ register 可能失败 / 需人工批准。见 B。
菜单栏常驻图标要新增一个 MenuBarExtra 场景 —— 那是"多一个入口"的产品决策，不是"让定时器准点"的技术手段。
唤醒后自动补跑会破 cron 语义：cron 说"03:00 跑"，睡到 11:00 醒来补一次，任务的时间点就变成"看机器什么时候醒"。boss 拍的是交给清单、由人决定。
launchd 定时唤醒那是环境外的东西（要写用户级 plist）—— App 不代管用户系统里的其它配置（同"两根都可写、但不代改 .gitignore"那条边界）。
