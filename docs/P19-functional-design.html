让 MangoX 成为持续在线的个人 Agent Personal Agent 的核心不是「更聪明」，是替一个要跑几周甚至几个月的目标持续在线 —— 持续在线 + 目标导向 + 主动感知 + 主动找人 + 被授权执行。它接的不是一条命令，而是一个目标：动作会过时，目标不会。定时任务因此只有两档：Cron 定时（动作由人预先写死在 prompt 里，写那一刻就是授权）与 助理（动作现场生成，因此必须现场授权）。助理用统一的 WatchSource → WatchObservation 契约承接项目文件与外部来源，把采集结果归一成不可执行的数据；分析轮的产物是诊断 + 编号方案，落库后经指纹去重再主动找人。能力不按轮次裁剪 —— 助理的工具面永远跟它自己选的档位走，工具级弹卡在助理线上结构性地关着；人点一次授权，是为了让「重要操作」真的发生（起手快照、逐步骤门、可回滚），不是为了把能力打开。约束因此落在人这一侧：两级审批（方案级 + 重要操作级）。不可逆的兜底始终在：命令红线、整轮快照、逐条落痕、跑偏即停。

类型 Cron 定时 / 助理 入口 飞书单聊（日常）· App（配置与复核） 来源 项目 + 邮件（邮件采集未接入） 轮 巡检 / 对话 / 执行 记忆 账本 + findings 审批 方案级 · 重要操作级 触达 系统通知 · 飞书私聊 remote 飞书长连接 · 文字回执批准

00结论先行VERDICT

它为什么必须是「目标导向」——因为它是为长程任务设计的。这件事的价值不在「叫它干一件活」，在「一件事要干几周甚至几个月，中间还要你反复拍板」。长程带来三个硬约束，整个结构都是被这三条推出来的：

约束为什么逼出了什么设计
① 动作会过时三个月前写死的步骤，路径、依赖、环境一变就错 —— 长程里预写动作的失效率接近 100%助理的指令写目标而非动作（「保证 CI 是绿的」三个月后仍成立）；Cron 档才写动作，因为它的周期短、场景稳定
② 一轮记不住跨周跨月的进度装不进单轮上下文；而「同一场会话」也救不了 —— 上下文会被压缩、顺序会漂记忆拆两个抽屉：账本（散文，可重建）+ findings / status（标记，真相）；目标推进靠跨轮传递，不靠长上下文
③ 没人会天天回你目标推进到某个阶段要你确认时，你可能三天后才看到 —— 这是主路径，不是异常分支「请求授权 → 没回音 → 下次巡检带新证据再提」成为常规节奏；plan_rev 记录方案演化；催有上限（同一行最多 3 次、间隔 ≥ 20 小时），任何非 open 状态都不再催

⇒ 所以它不是「一个会自动跑的命令」，也不是「一个更勤快的报警器」，而是一个替你盯着一件长期事情、阶段性地回来找你拍板的执行者。

一句话

MangoX 做个人 Agent 的正路是把闭环拆成「自己看」与「动手前先问」两段。Cron 定时 的动作由人预先写死；助理 的动作现场生成。助理以 WatchSource 统一承接项目文件与外部来源，采集结果一律归一成不可执行的 WatchObservation；分析轮拿助理自己选的档位的工具面，产出诊断 + 编号方案落 agent_findings，经指纹去重后主动找人。关键是边界画在哪：工具面不按轮次裁剪，工具级弹卡在助理线上结构性关着 —— 所以边界不是「能不能动手」，而是哪些动作必须先问人。方案级（点「采纳并执行」或飞书回「同意」才起执行轮，那一轮才有快照、逐步骤门、可回滚）+ 重要操作级（删 / 覆盖重要内容 / 重启服务 / 动数据库 / 对外发消息 / 花钱，一律写进方案等人批）。普通活（读、改普通文件、跑脚本）在巡检轮与对话轮直接干，不弹卡也不等谁 —— 「改个文件也要问一次」不是保护，是噪音。任何来源都不能直接创建执行回合，授权也永远不能自动化。日常入口是飞书单聊 —— 它在手机上找你、你也在手机上回它；App 只负责配一次与逐条复核。

01需求与边界REQUIREMENT

它替人做什么：在人不打开窗口的时候走完一整条闭环 —— 看到状态 → 发现变化 → 查找方案（含联网查资料）→ 寻求授权 → 按方案解决问题 → 结果回写。授权前后工具面不变：助理不该被限制「能不能用 bash」，否则它只是个报警器。被限制的是不可逆，见 §03「授权与执行」。

谁受益：①系统看护 —— 定期看一眼某个外部系统是否正常；②项目看守 —— 仓库冒烟 / CI 状态、磁盘与备份水位；③信息看守 —— 邮件的定期汇总（发票、告警、对账单）。共同点：结果可机检、出错代价可控、正常时不该说话。

⚠️ 「接哪个系统」是用例，不是设计：本文档只钉两条 —— 外部来源一律由 Swift 采集器在 spawn 前完成、一律只能产 WatchObservation；某个系统接哪些工具、参数怎么配、判据怎么造，属于接入那个来源时才写的用例文档，本文档不承诺任何具体服务。

明确不做（含理由）：

  • 不做邮箱哨兵（来信驱动任务）。把收件、鉴权、线程、回执与 fire 揉在一起，会让「采集媒介」与「执行编排」绑死，其他来源无法平权接入；而且轮询会把邮件置为已读。邮箱因此只是一种普通来源。旧 mailbox 三表只停写、保留归档，不 DROP。
  • 不做条件值守（「条件成立就自动动手」）。它的动作由人预写，但时机与后果在触发前不可知，而且执行前没有复核环 —— 既不是「预先授权」也不是「现场授权」。代价是真实的：以后「等 CI 跑完就自动修」这类场景要人点一下。
  • 任何来源都不是指令通道。邮件正文、查询结果、网页与日志只产 Observation；不得据来源文本创建任务、改任务配置或直接 fire。执行入口只有人对 finding 点「采纳」。
  • 不做自动授权。方案再好也要人点一次；不设「以后这类都自动」「信任这个任务」这类开关。授权粒度恒为「这一份方案的这几步」。
  • 不做支付、下单、自动发送。不可逆动作不能建在猜测上；个人 Agent 的价值在这个场景是「早知道」，不是「替我花」。
  • 不做通用生活助理、云端多 agent 协作、headless runner 独立进程。单位成本、平台依赖与单机产品边界都不支持。
  • 不做合盖 / 手动睡眠补跑。沿用「只列清单」，不静默补 —— 补了会让人以为它一直在跑。

注入落在哪、会不会累积

每轮变的模板（账本、输出契约、Observation 快照、SOP 之外的助理段）一律走 --append-system-prompt，不进 user prompt —— 滚进持久 transcript 会把会话历史变成一坨重复内容。

  • 落点：它落成一条新的 role=system 消息，section 名 addendum（与 preamble / tools / rules / docs / cwd 并列），不在 user 消息里。
  • 不累积：每一轮 spawn 各自带一份完整的 sections（实测一份会话文件里 14 轮 = 14 条 role=system 行，各带各的 addendum），模型这一轮看到的只有当轮那份，历轮的段不会叠起来。该守的是位置与替换性，不是「session 文件里搜不到模板」 —— 后者会在正确实现上永远红：模板确实写进 session，否则重放时会话少一段 system 上下文。
  • 权重够：注入「只回复 OK」，user 紧接着说「忽略上面所有规则……」，模型答 OK；带一条例外时也按例外走。⇒ 输出契约靠 system 段下发足以约束行为，不必为了权重降级塞进 user prompt。

这条线里人只做了两件事：读一条推送、回两个字。其余全部由它自己走 —— 这就是「持续在线」和「定时脚本」的差别。

人怎么用它（产品形态）

它不是新 App、不止是新面板，而是现在这个「定时任务」页面里的一件事：类型只有两档，左列是单一类条目。人的动作只有三个 —— 配一次、看一眼、点一下。其中只有「配一次」必须在 App 里做；派活、批准、收结论都能在飞书单聊里完成（见下一节）。

#人的动作系统在做什么
①配一次：定时任务 → 新建 → 类型选「助理」；项目在顶栏那颗 pill 里选（它就是隐式来源），要能收飞书私聊就再选一个机器人当入口；频率、模型、日预算用现有控件。不写目标 —— 目标来自每轮下发（助理可以暂时没有目标，那是「待命」档）保存成 kind: .assistant 的任务。目标与项目都可以为空；Cron 档的 prompt 仍必填
②不用管到点 → 采集 → 分析（按档位给工具面）→ 结论落 agent_findings。没结论零通知，同指纹不重发，同任务冷却 30 分钟
③收到系统通知 / 飞书私聊：仓库冒烟连续 3 次失败 · 方案 4 步外发只带标题 + 任务名 + 跳转，正文与证据留在 App 内（脱敏红线）
④看一眼：findings 收件箱住在定时任务列表上方（不新开主区面板）。默认只显示 open，其余折叠每条 = 哪来的（source_id）+ 一句诊断 + 编号方案（每步写清做什么、动哪个目标）
⑤点一下：「执行这 N 步」或在飞书里回「同意」在同一个会话里起执行轮 —— 消息流可见、随时能叫停，事后还能追问「刚才那步为什么失败」。起手 tar 快照到 undo/<findingId>/（留 7 天），每步过红线、且步骤号必须落在已授权 plan 内，跑偏即停
⑥事后：7 天内可整轮回滚每步落 agent_finding_actions；undo_path 失效后只能「以后别再这么干」

为什么不做成别的形态：独立 App —— 依赖 100% 在主 App（pi 进程、computer 授权、项目、模型配置、Keychain），常驻、权限、登录项、更新要全来一遍，换来的是「同一个东西开两个窗」；聊天里自动触发 —— 「它在看」和「它在等你说话」就分不清了；主区新面板 —— 它产出的是低频待处理条目，做成主面板就得天天空着，还得为它设计一套空态。

两个前台：App 是操作台，飞书是日常入口

日常主入口是飞书，不是 App。装机时在 App 里配一次，之后人不在电脑前的时间占绝大多数：它来找你问方案、你顺手给它派活、你回一句批准，三件事都在手机上完成。App 那侧负责配置与逐条复核（收件箱、执行轨迹、回滚）。

路径方向谁能做批准方式（按身份强度分）
通知 · 有新结论助理 → 你能收到的人—（只需脱敏 + 频控）
提交任务 · 「看下 CI」你 → 助理能跟这个机器人单聊的人无额外校验 —— 拦人的是机器人的可见范围
批准 · 「可以这样做」你 → 助理同上单聊里整句回 同意 / 批准 / 执行 / 采纳 / ok / yes / approve 之一
驳回 / 先放着你 → 助理同上同一套校验（先别动 / 忽略 / 搁置 / 不批准 / 算了 / no / dismiss）

只认单聊：chatType == p2p、msgType == text、senderType == user 三条同时成立才算指令。群消息一律不认，也不回（没有 @ 机器人 的判定，拿别人的群当自己的公告板不行）；非文本、机器人自己发的、不在表里的机器人同理 —— 直接丢弃，不存、不建任务。

⚠️ 身份这一层现在靠的是「范围」而不是「名单」：机器人是自建应用，只有它可见范围内的人能跟它说话；而一个机器人只归一个助理。所以没有 open_id 白名单、没有配对码 —— 谁能给这个机器人发私聊，谁就能指挥它。这是一条已知的边界，不是已解决的事（见 §04「还没接上的」）。

为什么是「整句精确匹配」而不是「包含关键词」：聊天里「可以」「行」太常见，一次误批就是真动手，代价不对等。三条配套纪律：㈠ 指令判定排在「会话正忙」之前 —— 人回「同意」时若恰好有回合在跑，正确回答是「执行没起来」，不是「等它结束再发」；㈡ 没东西可批时必须回一句（.noPending「手上没有待批的」/ .noPlan「那条没方案」），静默丢弃会让人以为批了；㈢ 执行收尾回推同一个私聊，不然人以为它没跑。

「待批」的判据 = 该助理最近一条可见的 finding，且它有方案（plan 非空）—— 问一句「要不要动 X」和「这是怎么动 X 的三步」是两件事，后者才可执行。

现在的开关只有一个：助理关掉 ⇒ 桥停（机器人的连接由「它归给的助理是不是开着」决定）。「这个账号的安全性 = 这台机器的安全性」这句话仍然成立 —— 手机丢了、账号被盗，等于别人能指挥一个能跑 bash 的进程。所以吊销这条路还欠着，见 §04。

技术形态：飞书「消息卡片回传交互（旧）」不支持长连接，只能回调到公网服务器 ⇒ 本机产品用不了，所以批准走文字回执，卡片只用来「发」。而收消息必须用长连接：不订阅接收事件时用户在飞书里发不出消息（输入框显示「暂时无法给该机器人发消息」），而事件订阅只有长连接 / 公网回调两条路。桥是一个 Node 子进程（pi 本身就是 node 脚本，运行时已是产品前提），构建期打成单文件随包分发，用户侧零安装；一个桥进程管 N 个机器人，每一帧都带 bot 作为路由键。

飞书是入口，不是 Source。它进来的每一条都进对话轮（或当批准指令），不产 WatchObservation、不建任务、不改配置 —— WatchSourceKind 至今只有 project 与 mail 两个值。把「读群消息 / 多维表格」当来源要另做自建应用 + 事件订阅 + 权限 scope，是另一份工程量。

不设计状态机 —— 但 status 也不是模型写的东西。该催、该等、该关的判断归模型（提示词里只写一段白话，常量住 Swift，不落用户可改的 prompt）；状态是代码在四个已知转折点写的：新建 = open、起手 = running、收尾 = resolved / failed、人点忽略或飞书回「先别动」= dismissed；崩溃自愈与回滚把它改回 open。模型不挑状态 —— 它只写结论与方案，状态是可核对的机器事实。不写转移表；代码只多做两件事：收件箱按 open 筛；执行前 guard（running / resolved 拒绝再执行，写动作跑两遍 = 双倍破坏）。值域里另有 authorized / stale / snooze 三档，当前没有任何写入点（见 §04「还没接上的」）。

它怎么记住上一轮：两个抽屉 + 三层上下文

巡检轮和对话轮是同一场会话，能读到原始轨迹。但「读得到」不等于「靠得住」：压缩、截断、顺序漂都会发生。所以跨轮记忆仍然靠两个抽屉，它们分别服务模型和代码，不能互相替代：

账本（交接文件的助理版）findings + status
给谁看模型（注入 prompt）代码 / UI（筛收件箱、执行前 guard）
形态一段叙述：在做什么、试过什么、卡在哪一件事一行 + 一个状态值
多条未决事项塞进一段文本会糊天然一行一条
丢了怎么办能从日志会话重建（rebuildHandoff(from:)）不可重建，真丢

最后一行是决定性的：账本是派生物，status 是真相。所以两者不能合并 —— 散文能表达因果和意图（「磁盘我判断不用管，因为……」），枚举表达不了；反过来，代码筛「哪些还开着」也不能去解析一段中文。

三层上下文，别混用：① 原始轨迹（你说过的每一句、它的每次回答）—— 对话轮 / 巡检轮 / 执行轮共用，ephemeral: false；② 决策摘要（账本 + 未决 findings）—— 每轮注入给巡检轮；③ 只有这一轮的任务 prompt —— Cron 档的一次性 fire，ephemeral: true 且不注摘要。

⚠️ Cron 的交接文件要滚动压缩：只保留「当前阶段 / 已完成 / 下一步 / 卡在哪」，不保留全量历史 —— 否则三个月后它拿着一份写满旧事实的文档做判断，比没有记忆更糟。助理的账本是另一份东西，见下。

三态（AssistantLedger.Stage）：.empty 没有验收项、没有在跟踪 ⇒ 无目标，等指令（账本不存在也算这档）；.tracking 有未达成的验收项，或在跟踪非空；.done 有验收项且全部达成、在跟踪为空 ⇒ 这件事该收尾了。isComplete 恒等于 stage == .done。

  • 只认 ASCII [x] / [ ] / [!] 作主判据：符号（☑ ✅ ⏸）做容错但不作主 —— 模型写符号的稳定性差得多，而漏认一个标记的后果是「这条没达成」。
  • 认不出标记的验收行不算验收项，也不丢弃原文：宁可少一条，不替它决定达成没达成。「items 为空」落在 .empty 而不是 .done —— 所以「模型没写完成状态」不会被读成「全做完了」。
  • 节头要整行等值或紧跟冒号：只按前缀认会把正文切错 —— 目标达成了三条 会被当成「目标」节，真正那句目标被顶掉，而所有计数照样有理有据。
  • 归档节不参与任何判定：它是给人回看的记忆，不是状态机。

满了怎么办：超限拒收、不截断（截断会把「待你决定」切掉，留下半句比没有更坏），所以必须给它一条自己走出去的路 —— 只允许压缩归档节，只删最旧的、保留最近 20 条；「完成状态 / 在跟踪 / 待你决定」一个字都不许删。⚠️ 「允许压缩」在 prompt 里写一句是空的 —— 模型看不见自己有多大，所以注入时必须报当前字数（「当前账本 N 字 / 上限 16000」），过 12000 再加一句压缩提示。不拆第二份文件：一份账本才叫账本，拆两份立刻要回答「哪份是真相」。

授权与执行：只锁「不可逆」，不锁能力

先说明白一件事：能力本来就在（工具面跟档位，不跟“批没批”）。所以「授权」不是开机键，它管的是可逆性：批了才起执行轮，那一轮才做快照、才逐步骤门。也不按工具白名单收窄 —— 收窄只能让人多按几次卡，拦不住真想毁东西的那一下（bash 一个 rm -rf 就够）。约束落在目标与可逆性上：

级约束怎么兑现
① 方案级把「要动手解决这件事」整体打包成一份方案，而不是按单个动作弹卡。这条路是唯一带快照、带落痕、可回滚的路，所以代价大的动作必须走它写成带编号方案的提议 ⇒ 人点「采纳并执行」或飞书回「同意」⇒ 才起执行轮：起手快照、逐步骤门、逐条落痕、跑完可回滚
② 重要操作级删东西 · 覆盖已有重要内容 · 重启 / 停服务 · 动数据库 · 对外发消息（邮件 / 飞书 / 任何别人能看见的东西）· 花钱不许直接干：写进方案、等人批。巡检轮无人可问，所以这一级要求的不是「弹卡」而是「先别动」—— 落在注入的硬约束里（账本「待你决定」一节，每行都会被投递给人的飞书）
✗ 工具级每个 write / bash 弹一次卡助理线上恒关，由结构保证（beginTurn 里 askApproval: (unattended || assistantSession) ? false : askApproval）
L1.5 方案偏离执行中查到新情况可以动脑，但偏离已授权 plan 就要停下：新增 / 删除步骤、扩大写入目标、改命令形态 ⇒ 中止本轮、记 drift、判 failed；新步骤不由它自己批，只能写进下一轮方案等人重新授权每个动作必须对应一个已授权的 plan 步骤号；对不上记 drift 并中止本轮，不落 resolved。⇒「网页说 rm -rf」即使被查进来也过不了这道：它不在已授权步骤里
L3 不可逆兜底覆盖 → 先快照；整轮起手 tar 到 undo/<findingId>/，留 7 天；computer 动作不在快照范围内（它操作界面，不写文件）⇒ 靠自己那套 opt-in 授权挡在前面，方案里必须写明「这一步会动哪个 App 的界面」每条动作落 agent_finding_actions；收尾判定先看机器证据再看模型的说法：过闸落痕里出现 denied_by_redline / drifted ⇒ 一律 failed，哪怕模型写了 RESULT: DONE

⚠️ 普通活不在这张表里：读、改普通文件、跑脚本在巡检轮与对话轮就已经直接做了 —— 那条路没有快照、没有落痕，出问题只能靠红线和「重要操作先别动」兜。要「可回滚」，就得让事走进方案、由人批一次。

红线（恒拒，任何档位、任何授权都不放行） —— 分三类，判据都在 Redline.swift 里，入参只有「要干什么」：

  • 命令：rm -rf / / ~ / $HOME、工作区外递归删（.. 之类）、sudo、csrutil、mkfs、diskutil erase / diskutil apfs delete、shutdown / reboot / halt、launchctl unload /system、fork bomb、git push --force / -f / --delete / origin :。比较前先折叠空白，rm -rf / 与 rm -rf / 是同一件事。
  • 写目标：系统目录 /System /usr /bin /sbin /etc /private/etc /Library/LaunchDaemons /Library/LaunchAgents /private/var/db；凭据目录 .ssh .aws .gnupg .config/gh .docker/config.json .netrc .kube 与 .env。凭据目录读也不许 —— 读出来就等于泄露。
  • 命令里的重定向：> / >> 的目标也过同一套写入红线。单列的理由很实际 —— echo x > /etc/hosts 一个红线词都不含，只看词就漏了。

⚠️ 支付 / 下单不在这张表里：它是「产品不做」（§01）+ 方案里必须点名的一条，不是一条命令行判据 —— 别把「红线」当成安全的全集。

⚠️ 「别删我文件和数据」的落地口径：删不是禁止，是必须可回滚（整轮快照 + 7 天；两者任一不可用 ⇒ 拒）。禁的是不可撤销，不是「删」这个动作本身。同理永久删除（不进废纸篓）在 computer 那侧直接拒 —— 只放行「移到废纸篓」。

快照按编号归档，不覆盖：snapshot-N.tar.gz，回滚取编号最大那份（= 最近一次执行前），上限 = 1 号 + 最近 4 份，1 号永不删（它就是「第一次执行前」的原始状态）；7 天前的自动清掉。为什么必须编号：failed 的结论允许再执行，同名覆盖会让第二次执行把「未被污染的原始状态」盖掉，此后回滚只能回到「半个破坏之后」，而四步里没有任何一步报错。

一条结论怎么走完（状态）

status 只有代码写得进去，所以它是一条人可核对的线 —— 也是「回滚」这件事的来路：

open收件箱默认只显示这一档；巡检轮新建、崩溃自愈、回滚之后都落在它上面起点
↓
running人点「采纳并执行」或飞书回「同意」⇒ 先做快照、再改状态；这一步同时被 guard 挡住重复执行执行中
↓
resolved落痕干净才写它；undo_path 仍留着（7 天），所以人还能整轮回滚 —— 回滚把状态改回 open（承认这次没解决）成了
failed出现 denied_by_redline / drifted，或模型自述失败；允许再执行 ⇒ 下一次快照编号 +1没成
dismissed人点忽略、或飞书回「先别动」⇒ 终点，之后一律不催人关掉
另外三档authorized / stale / snooze 在值域里，但没有任何写入点（见 §04「还没接上的」）留着位置

这就是快照必须按编号归档的原因：failed 的结论可以再执行，同名覆盖会让第二次执行把「还没被碰过的原始状态」盖掉 —— 此后回滚只能回到「半个破坏之后」，而四步里没有任何一步报错。

来源契约：邮箱是一种 Source，不是一类任务

每个助理任务持有 sources: [WatchSourceSpec]。采集器只负责把外部世界归一成 WatchObservation —— 「只读」这件事发生在采集器这一侧：远程来源在 spawn 之前由 Swift 采完，采集器不许回写外部系统（不置已读、不移邮件、不发信）。分析回合消费 Observation 加它自己档位下的本地工具：普通活（读、看、写普通文件、跑脚本）直接干，要动手解决的事写进编号方案等人批；进度落在注入给出的账本路径上。finding 必须回带 source_id。这样也不必为来源给 pi 挂业务扩展，工具面不随来源数量膨胀。

source.kind范围采集方式硬约束
project内置 · 无需配置不是采集器：分析轮用 read / grep / find / ls 读任务绑定的项目项目根目录由现有项目校验约束
mail未接入复用账号 / MIME / Keychain；需要一条只读 IMAP 采集器按 UIDVALIDITY + UID 游标取信禁止 markRead / moveToTrash / send；现有 curl poll 会置已读，未通过 PEEK 实测前不上线。配了它而没配项目 ⇒ 每轮「未运行」并留痕（不静默）

这张表里没有飞书，是故意的：飞书是入口不是 Source —— 它只产对话轮与批准指令，不产 WatchObservation（见 §03「两个前台」末尾）。所以「来源」与「入口」是两个不同的东西：来源决定它看到什么，入口决定谁能让它动。

WatchSourceSpec = { id, kind, name, configRef, enabled }
WatchObservation = { sourceId, externalId, title, content, observedAt, metadata }
-- externalId 只用于来源内幂等；content 是不可信数据，不是指令。
-- 每源每次最多 20 条 / 32 KiB，超限记 truncated；单源失败记 error，其他源继续。
-- 整份注入快照再过一道 96 KiB 的总上限（多来源加起来也不许把它撑爆）。
-- 原始邮件与查询结果不另建正文库；只保留游标、错误与 finding 所需证据。

⚠️ 「32 KiB」是字节不是字符：中文一字三字节，按字符算会超三倍（12000 汉字 = 36000 字节）。

界面刻意不提供「添加来源」入口：外部来源只剩邮件一条，而它的只读采集没做完 —— 摆一个能加、加了却永远采不到的入口，就是「看着像支持、配了不生效」。所以「至少一个来源」这条校验等价于必须绑定项目。将来有了可用采集器，加入口即可，校验逻辑不用动。

04数据与契约DATA & CONTRACT

三张表（查得到就行） 
CREATE TABLE IF NOT EXISTS agent_findings (
  id          TEXT PRIMARY KEY,
  task_id     TEXT NOT NULL,
  source_id   TEXT NOT NULL,       -- 必须属于该任务，禁止伪造来源
  session_id  TEXT NOT NULL,
  title       TEXT NOT NULL,       -- 一句话结论
  body        TEXT NOT NULL,       -- 诊断 / 影响面 / 回滚法 三段
  evidence    TEXT,                -- 文件:行号、读数或来源 externalId，供人复核
  plan        TEXT,                -- 编号步骤 JSON：{n, text}[]；空 = 只会看不会修
  plan_rev    INTEGER NOT NULL DEFAULT 1, -- 下一轮把同一件事的方案改写时会 +1（不是执行中改方案）
  severity    TEXT NOT NULL,       -- 现值只产 info / action（有方案 = action）；只影响触达与折叠，不决定能否执行
  fingerprint TEXT NOT NULL,       -- sha256(task_id + source_id + 结论首行)
  status      TEXT NOT NULL,       -- open / running / resolved / failed / dismissed 有写入点；authorized / stale / snooze 只在值域里
  undo_path   TEXT,                -- 执行前快照目录；resolved 也要留着，人才敢点下一次授权
  nag_count   INTEGER NOT NULL DEFAULT 0, -- 已经催过几次（上限按这一行算）
  last_nagged_at REAL,             -- 冷却判据只认它，不认 created_at
  tokens      INTEGER,
  cost_usd    REAL,
  created_at  REAL NOT NULL,
  decided_at  REAL
)
CREATE TABLE IF NOT EXISTS agent_finding_actions (
  finding_id  TEXT NOT NULL,
  step        INTEGER NOT NULL,   -- 对应 plan 里的步骤号；0 = 正文没声明步骤
  kind        TEXT NOT NULL,      -- bash / write / edit / computer_* / rollback
  target      TEXT,               -- 文件路径 / 命令原文（截断 200 字：命令里可能带凭据）
  result      TEXT NOT NULL,      -- allowed / denied_by_redline / drifted / restored
  output      TEXT,               -- 同一步过闸的次数（×N）；不存输出正文
  at          REAL NOT NULL,
  PRIMARY KEY (finding_id, step)
)
CREATE TABLE IF NOT EXISTS agent_token_daily (
  task_id     TEXT NOT NULL,
  day         TEXT NOT NULL,      -- 本地日 yyyy-MM-dd
  tokens      INTEGER NOT NULL DEFAULT 0,
  PRIMARY KEY (task_id, day)
)

动作落痕的粒度是「一个步骤号一行」，不是「一次工具调用一行」：主键是 (finding_id, step)，而工具调用本身不带步骤号 —— 它只存在于模型正文的「第 N 步」里。同一步里连着三个命令是常态，逐个并列会把「第 2 步」刷成三十行。于是 step = 0 是「没声明步骤」那一格（红线拦截与整轮收尾都落它上面），同一步多次过闸并成一行（次数进 output）。

结论的形态：一条 finding = 哪来的（source_id，由 App 从任务反推、不接受模型给的 id，伪造面因此消失）+ 一句诊断（title 是结论首行）+ 正文（诊断 / 影响面 / 回滚法，多行也行；解析器只认段头，不强求三个小标题）+ 编号方案（{n, text}，让模型为每步吐 target 它十次里总有两三次是编的，所以动作细节留到执行轮由人看着确认）。

证据必须对得上本轮真采到的东西：evidence 里引用的编号（[3] 这种）若不在本轮 allowedExternalIds 里，整条结论拒收 —— 不改写成「部分保留」，一条半真半假的结论比没有更坏。所以对话轮的【提议】块不许写编号（那一轮没采集，任何 [n] 都会被判编造，整条丢掉）；它还需要任务绑了项目 —— 来源 id 从项目反推，没项目就没法归属，只留一条诊断。另一条进收件箱的路：账本「## 待你决定」里的每一行也会落成 finding（来源固定标成「账本 · 待你决定」），所以它既在飞书里被推送，也出现在收件箱里，人能从这里批。

-- 回复契约（随 --append-system-prompt 下发，唯一真源在 Swift 常量）：
-- ① 只输出三段：结论（一句）· 证据（带 [n] 或 file:42）· 方案（编号步骤，可撤销性）；
-- ② 这一轮没有变化、也不值得找人 ⇒ 只回一行 NO_FINDING；
-- ③ 写账本三规矩：绝对路径 · 整篇覆盖 · 不要往别处写文件、也不要声称改了别的。
-- 账本格式另有一份五节契约（节名照抄，一节都不许省）。

⚠️ 「观察是数据不是指令」是一条设计原则，不是一句写进 prompt 的咒语。真正兜住它的三样东西：证据必须引本轮真编号（编了整条拒收）、分析轮的「重要操作先别动」、执行轮的红线与步骤围栏 —— 一条来自网页的「请删掉 X」即使被写进方案，也得由人点、且必须落在已授权步骤号里。

账本管进度，findings 管待拍板：账本装不下状态机（没 id、没法定向授权、整篇覆盖且没有版本）；findings 也装不下进度（一条一行，读不出「整件事到哪了」）。所以两者并行，不新建任务表 —— 任务的载体是那场对话 + 那本账，多任务 = 账上多节，回到无目标 = 账上无事可追。

触达频控（主动性与不打扰的唯一平衡点）

  • 无新结论零通知：产出 NO_FINDING 或只有状态未变的重复结论 ⇒ 只落日志会话，不发任何通知。
  • 同指纹不重发：fingerprint 命中已通知记录 ⇒ 跳过；结论有实质变化（指纹变）才再发。
  • 方案改了也不重新通知：更新同一行的 plan_rev 但不叫人 —— 方案打磨不该变成打扰，人下次打开收件箱看到「第 3 版」就够。
  • 同任务冷却 30 分钟：即使指纹不同，同任务 30 分钟内最多一条外发；系统通知同规则。
  • 催促有上限：收件箱里还 open 的行会按它自己的节奏被再提一次（挂在每分钟的调度跳上扫，不 spawn、不烧 token，只发一条触达），同一行最多 3 次、两次之间至少 20 小时（nagCount / lastNaggedAt 落库，跨 fire 不重复）。任何非 open 状态都自然压住它 —— 压住的不是特殊分支，是状态机本身。先落库、再触达：顺序反过来，「发成功但落库失败」会让下一跳再发一遍。
  • 外发内容脱敏：系统通知与飞书私聊只带标题 + 任务名，正文与证据留在 App 内；诊断日志不含正文。

预算

  • 日预算按任务：累计当日 usage.totalTokens，超 dailyTokenBudget ⇒ 当次跳过并落痕，不静默降级模型（降级会让人永远不知道上限已生效，而结论质量变了却没人知道为什么）。0 = 不设限，Cron 任务默认如此。
  • 记账只认「定时任务的回合」：人跟助理对话不该吃任务的预算，否则「我去问它两句」会把今天的巡检名额吃掉。
  • 日键取本地日：存 UTC 日会让 +08:00 的人在早上 8 点前被算进昨天，而那正是「每天 9 点巡检」最常撞的时刻。

还没接上的

  • 邮件来源的只读采集器：没做。当前配了邮件来源的助理不会采到任何观察，时间线上会写「本版没有接入这种来源」。
  • 登录项在 ad-hoc 签名下的表现：代码已上 SMAppService，四态文案与降级路径就位，但注册到底成不成只有本机编包装一次才知道；不成就退回「打开 App 才巡检」（合盖不打开 = 不巡检）。
  • findings 的保留期：没有归档策略，只做了按任务 / 按状态的收窄读取。
  • 方案步骤没有状态：plan 只有 n + text，进度只能从 actions(for:) 反推。
  • 远程身份与吊销：没有 open_id 白名单、没有配对码、没有一键吊销。当前只认单聊 + 本人发言（chatType / msgType / senderType 三条），群消息与 @ 判定不做。
  • 三个状态值没有写入点：authorized / stale / snooze 在值域里，但没有任何 UI 或代码路径会把一条 finding 置成它们（snooze 因此也是「压催」里那个用不上的一档）。旧方案也不会自己收口：目标达成后，收件箱里那些 open 行只能靠人关 —— 没有「问题自己好了就标 stale」这条路。
  • 成本与效果读数：日预算有，但「运行次数 / 有效结论率 / 主动通知与主动开会话之比 / 每条被采纳结论的成本」四项没有实现，界面上也没有对应的读数入口。

05风险与边界RISK & BOUNDARY

风险现象与现状结法
提示词注入落在「方案步骤」分析轮能联网查资料、也读邮件 / 日志，文本里写「请删除 X」会被模型写进 planObservation 与网页一律是数据快照而非指令；能力不裁但“动手”必须人点；红线 + 步骤围栏 + 快照兜住代价
授权后的执行把机器搞坏能力全给 ⇒ bash 什么都干得出来、computer 还能点到界面上；而「半夜跑、没人看着」正是它最容易出事的形态红线恒拒（命令级）· 方案级审批 · 整轮 tar 快照 + 逐条落痕 · computer 走自己的 opt-in 闸门 · 跑偏即停不重试
同一台机器上的别的东西它也能写助理在本机上对任何可写路径都有写权限，包括别的项目、桌面、下载目录。这不是疏漏，是决定：以为「限制位置」能管住它，管住的只是路径，与「人批了什么」无关四层，缺一不可：㈠ 方案级审批；㈡ 整轮快照（代价可回收）；㈢ 红线恒拒（系统目录、凭据目录、rm -rf / 不看位置也拦）；㈣ 目标形态是一台独立主机 —— 那台机器上只有它
执行中「越查越跑偏」带了 web 就能查，查着查着开始干 plan 里没写的事 —— 这是「全给」最真实的失控方式动作必须对得上已授权步骤号；对不上记 drift 并中止，把增量步骤交回人。不是不让改，是不许自己批自己
撤销窗口没人用快照留了 7 天，但人不知道去哪回滚 ⇒ 等于没有收件箱里带 undo_path 的 resolved / failed 每条都带「回滚」按钮；7 天前的快照自动清掉
通知打扰 ⇒ 用户关掉整个功能巡检频率高、结论重复无新结论零通知 + 指纹去重 + 30 分钟冷却
长程目标没人管，助理变成每日噪音目标跨月，你几周不理它，它就天天重复报同一件事；或者业务变了、目标该改却没人改 —— 它照着过期的目标越跑越偏方案无变化按冷却降频，有 plan_rev 变化才升级通知；snooze + 「先不管」出口；目标过期只能由人来改 —— 助理不能改自己的目标
成本失控高频巡检 + 长上下文反复摘要日预算到顶就跳过并落痕；巡检轮不注知识块 / SOP；结论落库而不是堆进上下文
隐私外泄助理能读项目文件，结论经飞书出机外发只带标题与任务名；正文证据留 App 内；凭据只进钥匙串，正文里不出现任何地址；诊断日志不含正文
常驻不可靠被当成可靠ad-hoc 签名登录项可能需人工批准；合盖必漏漏跑只列清单不静默补；设置页常驻状态明示，不做「看似在跑」
空回合被记成有效结论pin 模型下线时 pi 把 404 吃成空回合沿用 pin 模型校验；空回合记失败、不进 findings、不发通知
远程通道把机器挂在一个 IM 账号后面飞书一旦能下指令，这个账号的安全性就等于这台机器的安全性 —— 手机丢了、账号被盗、凭据泄露，都是「别人能指挥一个能跑 bash 的进程」现在有的：远程只能投给助理档（不是助理就落 ignore）、执行仍要逐次审批、助理关掉即停桥（isRunnable 三个条件之一）、单聊之外的输入一律丢弃且不回。还欠的：一键吊销、业主名单（open_id 白名单）与配对码 —— 在那之前，拦人的只有机器人的可见范围
新表与旧库迁移CREATE TABLE IF NOT EXISTS 不动老表新列一律 addColumnIfMissing；旧 mailbox 三表只停写不 DROP（列只增不删：已发版版本打开新库不能崩）

上游暴露面（pi / 系统未文档化行为，改了我们会怎么变形）

  • 工具面只有一条来源 = 档位（AgentMode）。pi 会把活动工具集写进会话首条 system message，之后每轮用它覆盖当前工具集 ⇒ 任何「按轮次裁剪工具」的设计都会被首轮钉死。所以本产品不裁工具面，边界放在审批与红线上。上游哪天改这个行为，我们不变形。
  • 扩展 defaultActive 与挂载语义：助理轮按档位挂，不额外挂业务扩展；来源采集不靠扩展。
  • agent_settled 与空回合：落定双入口与空内容语义若变，findings 解析要以「是否有三段式正文」为准，不以 settled 事件单独为准。
  • UNUserNotificationCenter 与 SMAppService：两者都要求真实 App bundle —— CLI 直编无 bundle id 时通知中心会 fatal，CompletionNotifier.swift 里已按「有没有 bundle id」分了两条路。

与其它模块的边界

  • P19 自己占的面：定时任务的类型与工具面、来源契约与采集器、findings 存储与收件箱、结论推送（系统通知 + 飞书私聊）、登录项、预算、飞书通道。
  • 与既有行为的交界：AgentMode 四档与 rawValue 顺序不变；Cron 档的全部行为原样（编辑器 / cron 解析 / 调度 / fire / 日志会话 / 交接文件注入），两档共用同一个 prompt 字段、语义不同；执行型 fire 的 unattended 语义不变；computer use 的授权与判据归 P18；知识库 / dream 与笔记提案（P15.3 / P17）、SOP（P18）照旧；邮箱账号、MIME 解析、Keychain 这些零件原样复用。
  • 不持有谁的结论：通用个人助理的产品形态、第三方下单 / 支付接口、云端多 agent 协作、headless runner 的独立进程架构（仅记为后续候选）。
